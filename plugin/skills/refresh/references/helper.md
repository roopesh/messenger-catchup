# Helper: commands, browsers, versions, warnings and stalls

Read the part SKILL.md points you to: Commands (before your first command in each conversation), Tabs (every run, step 2), Which Chrome (more than one Chrome is connected), Versions (the installed helper is older than `assets/helper.user.js`), Warnings (`selfcheck` or a scan returned `warn`), Scan results (`err:"stalled"`, `top`, `scroller`), or Injecting (no helper installed).

## Commands
Start each with the bridge in SKILL.md › Helper, with a fresh id, and poll until it's no longer running.
- `ping` → `{v}`, the helper's version.
- `probe{anchor}` → `{vis,n,found,after}`.
- `scan{stops}` or `scan{first:{count}}`; `verify`; `capture{base}`: the steps `full` runs, one at a time (Injecting, below).
- `full{stops|first, base, run}`: scan, reload, verify, capture. Pass a fresh `run` id; after the reload, poll `sessionStorage.mc_result` in new calls (the first poll often fails with "Inspected target navigated": expected, poll again) and accept it only when its `run` equals yours: `stage:'captured'`, `'verify-failed'`, or `'scan'` (with `err` = scan error; with `err:null, win:0` = nothing new since the last run), or `'captured'` with `rxOnly:true` (nothing new, reactions changed: below). Results carry `warn`, `top` and `scroller` (Warnings, Scan results). Messages that arrive during the run (`extra>0`) wait for the next run.
- `me`, `rxw`, `rxwMs` (4.0; for `full` and `scan`): `me` is the user's names (`ownerName` and `ownerAliases`). During the scan the helper opens Messenger's "see who reacted" list on each new message with reactions that replies to you, names you or ends a sentence with "?", reads who reacted with what into `xw` (`references/reactions.md`), and closes it with Escape, never clicking inside it: at most `rxw` messages (default 30; 0 reads none) and `rxwMs` (45 s) a run, newest first. The scan result's `rxw` `{want, read, noopen, empty, cap, stuck}` counts them.
- `rxBack`, `rxIds`, `rxSum` (4.1, B69; for `full` and `scan`; the caps `rxMax` 400, `rxMs` 60 s, `rxIdMax` 20, `rxIdMs` 45 s): reactions read again on stored messages, back `rxBack` stored messages from the newest (newest first) and on each `rxIds` message found by id, with who reacted; the capture carries them as `rx`. Pass what `catchup.py recheck` prints. The result's `rx` counts them; with nothing new and reactions that differ from `rxSum` ("N:hex": the newest N compared), `full` captures them at once (`stage:'captured'`, `rxOnly:true`, no reload or verify). All of it: `references/reactions.md` › Late reactions.
- `selfcheck` → `{ok,missing,warn,counts}` (SKILL.md › Refresh steps, step 2).
- `jump{mid,reply}`: opens that message, with Reply open unless `reply:false` (`references/open-message.md`, `references/outbox.md`).
- `people{count}`: `references/people.md`.
- `post` only when `meta/chat.helperPost` is true (`references/posting-with-helper.md`); it tags `mentions` (2.7) and waits for `photos` Claude attaches (2.9).
- `groupFeed{known,cap,extra,run}`, `groupPost{newest,known,run}`, `notifs{since,more,run}` (3.0, F25): read a Facebook group's feed (post cards while on screen), an open post's comments, and the notifications page, without clicking anything in a post or any notification. With `run` (3.1) they keep the text in a buffer and answer with a summary; `groupCapture{run,group}` (3.1) then puts the run's posts, comments and that group's notifications behind COPY CAPTURE for the page (`references/groups.md`).
- `react{mid,emoji,search,remove,approved:true}` (2.7; `remove` 2.8): adds an approved reaction, or with `remove:true` takes it away (`references/outbox.md` › Reactions).

## Tabs
Runs used to open a new tab on the page for every import and leave some behind, so the user found a pile of "Messenger Catch-up" tabs in Claude's tab group (B61, Nov 25). The user's rule: the page tab is open only while a run imports.
- **Only Claude's tab group:** the tabs `tabs_context_mcp` lists. Never close or touch any other tab of the user's.
- **At the start (step 2):** keep one Messenger tab (the one on a chat in `meta/chat.chats`, else the most recent `facebook.com` tab); close every other `facebook.com` tab in the group, and every page tab except one still storing photos (below).
- **Step 4:** paste into a page tab left storing photos by an earlier run if there is one (don't reload it), else open a page tab. A run over several chats pastes every chat's capture into that same tab, picking each chat in its title (`references/chats.md` › The paste), and uses the one Messenger tab for every chat.
- **At the end of the run** (step 5 for each import, and wherever the run stops, early stops included): close the page tab, unless its import is still storing photos (`refresh/lastImport.state` is `uploading`, `references/photos.md` › Waiting): then leave it open, never reloaded, until the upload ends; the next run closes it once it's done.
- Keep the one Messenger tab between runs.

## Which Chrome
- Claude in Chrome's `list_connected_browsers` lists every connected Chrome with its `deviceId` and display name, and marks the one this session uses (`inUse`). One browser, or one already in use: use it.
- Several and none in use: the Chrome tools ask the user to choose, and you must never pick one yourself. When you ask, recommend the Chrome whose Messenger tab has the newest helper (`data-mc-helper`; older helpers lack checks: `selfcheck` came in 1.8, full names in 1.6, warnings, More actions › Reply and `post` in 2.0). If the user asks you to pick the one with the newest helper, you may select each in turn (`select_browser`), read `data-mc-helper` on its Messenger tab, and keep the newest.
- During a scheduled run with no one to ask: don't choose. Set `refresh/status` `{state:"error",message:"several Chrome browsers connected: choose one"}`, keep the schedule, and say so in the report.
- Every report names the browser used and its helper version, for example "Chrome 'Work Mac', helper 2.1". The same version goes into `meta/chat.versions.browsers` under that Chrome's `deviceId`, with its name alongside (`references/database.md` › Versions), and `"none"` when you injected the helper. The names ("Browser 1", "Browser 2") can swap when the extension reconnects; the `deviceId` doesn't.

## Versions
Install link (also on the page; steps in the setup skill): https://github.com/roopesh/messenger-catchup/releases/latest/download/helper.user.js

An installed helper reports its version in `data-mc-helper` (and `ping`). When it's older than `@version` in `assets/helper.user.js` (compare number by number), keep using it, and in the report:
- **older than 1.5:** it was installed by pasting and can't update itself. Tell the user to open the install link (below) once and press Install. It replaces the old copy and updates itself from then on.
- **1.5 or later:** it updates itself within a day. To get it now: the extension's menu › Check for updates, or open the install link again.
- The page shows it too, from `meta/chat.versions.browsers` (`references/database.md` › Versions): below 1.5 until a refresh in that Chrome finds it up to date, 1.5 or later only while that Chrome ran the last refresh; the user can dismiss either.
- What an older helper can't do: before 1.6, no full names (`fn`); before 1.7, no `people` scan; before 1.8, no `selfcheck` (skip that check and say so); before 2.0, no warnings, no `top`, no stall timeout, no More actions › Reply, and no `post`; before 2.1, photos carry no Messenger id, `skip` is ignored (a backfill fetches every photo again), a photo it couldn't fetch is only counted in `FAILED` (never owed or retried), and an image that hadn't loaded during the scan was left out, shifting the photos after it to the wrong slot (`references/photos.md`); before 4.0, no who reacted (`xw`): reactions carry only their count (`x`, `references/reactions.md`); before 4.1, no reactions read again on stored messages (`rxBack`, `rxIds` are ignored), so a reaction added after a message was stored isn't seen.

## Warnings
`warn` (from `selfcheck`, or a scan: `mc_result.warn`, or the `scan` command's result) never stops a run. Put each in the report in one line, with what it means:
- **`page language is "…"`**: Facebook isn't set to English. Reading goes on, but labels may not be recognized. If `selfcheck` also has `missing` items, tell the user the language is the likely cause (not "Messenger changed") and to switch Facebook to English.
- **`24-hour clock`**: times like 17:52 are read and stored as 12-hour times. Glance at a few new messages' times on the page.
- **`reply link(s) without an "X replied to Y" line`** or **`"Original message:" quote but no reply link`**: Messenger reworded a reply marker. Those replies get no Messenger link (`perr:"noreplyline"`, or nothing), and the build prints a CHECK for each (`CHECK reply with no readable reply line`): read them in context and set `links` by hand.
- **`photo link(s) with no Facebook image`**: those photos are missing from the capture.
- **`message(s) whose photos share one Messenger id`**: the helper can't tell those photos apart by id, so they're stored by position, as before helper 2.1 (a slot may shift if an image loads late). Messenger may have changed its photo links.
- **`time labels go backwards`** or **`dated in the future`**: some dates were read wrong (for example a time-only label that isn't today). Name the messages in the report; check them in Messenger before relying on their dates.
- **`"X" shows as A and B`**: one full name may come from the wrong avatar. Don't use it to tell people apart until a later capture agrees.
- **`no full names`** or **`sender avatars (full names)`**: avatars can't be read, so new messages carry no `fn` (`references/people.md`).
- **`who reacted: … didn't close with Escape`**: a "Message reactions" list stayed open, so the helper read no more of them in that scan (the reload that follows closes it). Say so in the report; the messages it didn't read keep only their count (`x`).
- **`who reacted: … didn't open`** or **`had no rows the helper could read`**: Messenger's who-reacted list may have changed. Those messages keep only their count (`x`), and the build falls back to "probably" (`references/reactions.md`).
- **`date labels (n of m unreadable)`**, or a capture summary (`mc_result.capture`, or the `capture` command's result) ending with `DATES-GUESSED #…`: those messages' date labels couldn't be read and took the previous message's date. List them in the report, since Messenger may have changed its labels.

## Scan results
- **`err:"stalled"`**: nothing new loaded for 30 s (Messenger stopped loading older messages). Navigate the tab to `chatUrl` again, wait about 5 s, and start the scan (`full` with a new `run` id) once more. If it stalls again, stop with `refresh/status` `{state:"error",message:"Messenger stopped loading older messages"}`; the next run tries again.
- **`top:true`**: the scan reached the start of the chat. On a first run that means the chat is shorter than the count asked for, and `win` is all of it. Helper 3.8 and later confirm the top first: at a quiet pause at the top they nudge the list (scroll down and back up, so Messenger asks again) and wait once more (`nudges` counts them); older helpers could take a pause for the top. A run with stops that reaches the top fails with "None of the stored anchor messages was found … (reached the top of the chat)" (`references/troubleshooting.md`).
- **`scroller`**: which element was scrolled. `message` (the nearest scrollable ancestor of a message that holds nearly all the messages) is normal. `first-div` (helper 1.9's rule: the first scrollable element in the chat log), `message-short` or `message-outside-log` mean Messenger's layout changed: mention it, and on a first run check that `win` is what you asked for.
- **`err:"top-spinner"`**: at the top of what loaded, Messenger's loading spinner stayed for 30 s and nothing older came. Handle it like `stalled` (reload, retry once), and if it happens again, say so in the report: Messenger may be failing to load that chat's history.
- **`verify.err:"stalled"`** or **`"top-spinner"`**: as for the scan: run the whole `full` once more. Helper 3.6 and later have already retried the verify once themselves (`verify.mode:"retry"`); put `verify.seen` (how many messages each pass saw) in the report.
- **`people`** stops early with `stalled` (and `spinner`) when nothing older loads for 30 s; treat it like `top:false` (`references/people.md`).

## Injecting (no helper installed)
Also for an added chat when the installed helper is older than 2.3 (`references/chats.md`): the injected copy (2.4 and later) takes over the bridge from an older installed one until the tab reloads, so `data-mc-helper` and `ping` show the injected version; name the installed version in the report. Never run `full` then: its reload brings back the installed copy, which verifies and captures without `thread`. Use the steps below (or have the owner update the helper first). Inject it on each step: Read `assets/helper.user.js` and pass its entire text to `javascript_tool` on the Messenger tab, followed by the bridge *start* call only (end the code with `'started'`; never wait inside the injecting call). The injected code is lost when the page reloads, so run the steps one at a time: inject + start `scan` (poll until done; require `err:null`), reload the tab (navigate to the chat URL), wait about 5 s, inject + start `verify` (poll), then start `capture{base}` in that same page (poll). A scan with nothing new (`win:0`) whose `rx` has `n` above 0 and `same:false` goes straight to `capture{base}` in the same page, with no reload or verify (`references/reactions.md` › Late reactions). Never paste only part of the file.
