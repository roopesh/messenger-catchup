# Photos

Read this on a refresh when the capture summary shows `photos` above 0 or `FAILED` (step 4 › Waiting, step 5 › Looking), when `meta/chat.photosOwed` is set (step 3 › Backfill), when a storage warning shows (Storage), or when the user asks to tidy up photo storage (Cleanup).

## How the page stores them
- After the "IMPORT OK" toast the messages are saved. The page then uploads the photos one at a time and indexes each one as it lands (`photos/b<start>`, `references/database.md`). The toast reads "Storing photos n/N… keep this tab open" until it's done.
- `refresh/lastImport` shows the progress: `state:"uploading"`, `beat` (a heartbeat the page writes every 10 s, also during a slow upload), and `photos.done` of `photos.todo`. It ends with `state:"done"` or `state:"partial"` plus `stop`.
- A photo not stored yet is **owed**: its slot is `null` and `meta/chat.photosOwed` counts it. A paste of the same capture, or the next refresh's backfill, stores it. The page gives up on owed photos more than 300 messages behind the newest (they come back in `gaveUp` with `e:"gave-up"`), because a refresh can't scan back further for them.
- A photo the helper couldn't get (`FAILED #…` in the capture summary: the fetch failed, or the image never loaded) is owed too, with helper 2.1 and later (the capture lists it in `phfail`). Each refresh run that reaches its message without getting it counts one try (`tries` in its block; runs are told apart by the `run` id you give `full`, else by `meta/chat.lastRefresh`, so pasting again in the same run doesn't count again). After 3 runs the page gives it up (`e:"no-fetch"`); `refresh/lastImport.retry` lists the ones still being tried. An older helper's `FAILED` photos have no slot, so nothing retries them.
- Helper 2.1 records each new photo's Messenger attachment id with its slot (`aids` in the block), and the page matches a photo to its slot by that id, so a photo is stored once, in its own slot, however a later scan numbers it. A photo whose id changed is found by a short hash of its content (`h`). Slots stored before then have neither and still match by position `k`. If one message's photos share one id, the helper drops their ids (they match by position) and the scan warns (`references/helper.md` › Warnings).
- **Never close the page tab, reload it, or take the Messenger tab off COPY CAPTURE while `state` is `uploading`**, except where Waiting says so. Closing it loses nothing already stored, but stops the rest.

## Waiting (step 4, after the paste)
1. Before you paste, `get` `refresh/lastImport` and note its `at` (there may be none). After the paste, keep the page tab in front (Chrome slows timers in background tabs) and leave the Messenger tab on COPY CAPTURE. Wait about 10 s, then `get` it again. It belongs to this paste only if its `sha` starts with the 8 characters after `sha` in the capture summary **and** its `at` differs from the one you noted (the same capture pasted twice has the same `sha`). If not, the page didn't take the paste: check again once after 5 s, then paste again (safe: stored messages and photos are skipped). Never import twice blindly: a paste while photos are still storing changes nothing and the toast says "Still storing photos from the last paste".
2. `uploading`: read it again every 20–30 s. If two of your reads at least 60 s apart show the same `beat`, the page stalled: reload the page tab, wait 10 s and paste again (if nothing reacts, click COPY CAPTURE again first). If the toast says another import is running, the stalled tab's lease hasn't lapsed yet, or the page is packing a day's photos (Storage): wait until the time it names (to the second; about a minute) and paste again. Do this at most twice per run. Compare your own reads only, never `beat` with your clock.
3. Wait at most 10 minutes in total, even while photos keep arriving. Then carry on with step 5 but **leave the page tab open** so it keeps storing, take the Messenger tab back to the chat, and `get` `meta/chat` again just before step 7's last batch, since the page writes it when it finishes. At the end of the run, close the page tab only if `refresh/lastImport` is no longer `uploading`; otherwise say in the report that photos are still storing in the open page tab. Anything it doesn't finish stays owed for the next run.
4. `done`: carry on. Report `gaveUp` in one line ("2 photos couldn't be stored: #812 (too large), #640 (given up: too old)"; `e` is `too_large`, `unsupported_type`, `invalid_request`, `gave-up`, `no-backfill` or `no-fetch`: Messenger didn't give it in 3 refreshes), and the storage level if Storage below says so.
5. `partial`, by `stop`:
   - `rate_limited`: wait 2 minutes, then paste again once.
   - `unavailable`, `timeout` or `index`: paste again once. (`unavailable` means the store failed: `store_unavailable` twice, or once `upstream_error`, `transform_error` or an unknown code, which the page never retries since the photo may have been stored.) If the toast says "the photo index for #… is full … Tell Claude", don't paste again: report it (a block of 500 messages outgrew 256 KiB).
   - `lease`: another page tab took over the import. Close any other page tabs you opened, then paste again once.
   - `auth`: reload the page tab, wait 10 s, then paste again once.
   - `quota` (`quota_or_state`): the page refused uploads: its photo storage is full, or it's unpublished or being deleted. Don't paste again. Report it with `usage` (full if `files` or `bytes` is at its limit; otherwise say the page can't take uploads right now), tell the user even in a scheduled run, and offer Cleanup when it's full.
   - `no_assets`: this view can't upload. Don't paste again; tell the user to open the page on claude.ai as its owner. The photos stay owed until a run can store them.
   - If the second try is also `partial`, report how many are still owed and carry on: the next run backfills them.
6. `refused` or `failed`: nothing about photos; do what `references/troubleshooting.md` › Import toasts says.
7. Then go on to step 5 (keep the page tab, `references/helper.md` › Tabs, and take the Messenger tab back to the chat).

## Backfill (step 3, when `meta/chat.photosOwed` is set)
`photosOwed` is `{n, fromI, toI, at}`: `n` photos owed between messages `fromI` and `toI`, left by an earlier run that stopped.
- Start the scan at `S = max(fromI, meta.lastI − 300, 3)`. If `S > toI`, skip the backfill and scan as usual: owed photos on messages #0–#2 can't be reached (a scan needs the 3 stored messages before its start), and the page gives them up at the next import (`e:"no-backfill"`), which the report lists.
- `get` the chunks holding messages `S−3` to `S−1` (each is in the chunk with the highest `start` at or below it), then scan with `STOPS` = their `m`, newest first, and `BASE = S−1`. Everything else in step 3 is unchanged.
- **Skip list** (helper 2.1+): also pass `skip` to `full`, so the helper doesn't fetch the photos the page already holds. `get` the `photos/b<start>` blocks covering `S` to `meta.lastI` (`b0` for 0–499, `b500`, …), and `photos/index` if it exists. For each message `i` from `S` on, each slot `k` whose value is a string (stored) or an object (given up) goes in as its id, the string `aids[i][k]`, when the block has one, and otherwise as the number `k` (the old index has no ids: its `byK`, or `byI` by position). Leave out owed (`null`) slots. `skip:{"812":[0,"1234567890123456"],"815":[1]}`. An older helper ignores it and fetches them all, which is safe: the page skips what it holds. The capture summary says `skipped n`. If `refresh/lastImport.skipOwed` lists photos, the list named photos the page doesn't hold stored (a `null` slot, or none): the page keeps them owed for the next run and counts a try. Say so in the report, and check that your list leaves out `null` slots.
- After the paste, follow Waiting even if the summary shows `photos 0`: the page may still store or give up owed photos, and Waiting's `done` reports them.
- The window now holds stored messages too, so `win > 0` doesn't mean there are new messages; the import toast decides. "Nothing new: … n photos stored" takes step 3's nothing-new path for the build (and the report says the photos were stored); "IMPORT OK" builds as usual. `refresh/lastImport.backfill` is true when it stored owed photos.
- If the scan or verify fails, or the import is refused with "#… doesn't match the stored message" (a message was deleted since), scan again the normal way (`anchorMids`, `lastI`) and report the photos as still owed. The page gives up on them once they're more than 300 messages old.

## Looking (step 5)
- The new photos are the `stored` lists (`[{i,k,id}]`: message `i`, photo slot `k`, asset `id`) of this run's final `refresh/lastImport` reads, one per paste, joined.
- Open every one: `Artifact read` with path = the `id` (one id per call), then Read the saved file. Use what you saw in the build; never guess what's in a photo you didn't open.
- **Caption each one** while you look at it: the page's search finds photos by their captions. One line, at most about 160 characters, saying what the photo shows: the item, its brand or model when the photo or the messages around it name it, colors, notable details and any readable text ("green Ultra Monolith pack, side view, coyote straps, price tag $180"). Read the photo with its own message, what that replies to, its thread or conversation, and the messages a few minutes either side: a photo-only post in a thread about someone's Monolith shows that Monolith, as the thread says. Never guess beyond what's seen or said; when nothing names the item, describe it ("green roll-top backpack").
- Put them in the build spec as `captions`: `{"<i>": {"<k>": "…"}}` (message `i` and slot `k` from the `stored` list). Also `list captions` (limit 1000) into RUN; if the collection is empty and the list leaves no folder, make an empty `RUN/captions`. The build merges each caption into its block (`captions/b<start>`, `references/database.md`), pinned when the listing holds it, and refuses one over 200 characters, with a line break, or on a message with no photo. A refused `captions` write: `references/writing-the-build.md` › Refused writes.
- With nothing new to build (step 3's nothing-new path stored owed photos), caption them with `catchup.py captions` instead: Captions for older photos, steps 1, 3 and 4.
- Photos stored after your last read (you stopped waiting at 10 minutes) aren't in the list: describe those messages from their text and replies only, and leave them uncaptioned (Captions for older photos finds them later).
- New photos aren't packed while your run holds the lock, so their ids open as photos. If one says the file is gone, its slot now holds `/_blob/<pack id>#<n>`: open it from the pack (Storage › One photo from a pack).

## Storage
- With each import the page records the page's photo storage in `refresh/lastImport.usage` and `meta/chat.assetUsage`: `{files, bytes, maxFiles, maxBytes}`. On claude.ai a page holds at most 5,000 files and 1 GiB.
- At 80% of either limit the page shows a warning under the status line and adds it to the toast. Say it in the report in one line ("Photo storage: 4,100 of 5,000 files (82%)") and offer Cleanup. When `meta/chat.photoPack` isn't on, add that the page's Photo storage box (under Refreshing, at the foot of the page) can pack each finished day's photos into 2 files (Storage › Day packs). In a scheduled run, just report it.
- There are often more files than indexed photos: copies left by re-pastes and by uploads that landed as a tab closed. Cleanup finds them.
- **Day packs (R13).** When the user has switched on packing (the page's Photo storage box, `meta/chat.photoPack.on`), an open copy of the page packs each finished day's photos into two files: a full pack (every photo's bytes exactly as stored) and a preview pack (small JPEGs the page shows inline; a click shows the full size). A day is finished once it's over before yesterday began (the chat's time zone, by each message's `d`) and none of its photos is owed, so a photo stays its own file for at least two days. The page checks the full pack against every original's SHA-256 before it points the slots at the pack (`/_blob/<pack id>#<n>` in `byK`, the preview's in `pv`), then deletes each original that nothing in the `photos` documents uses any more: about 70 files a day become 2. It packs one day at a time under the import lease, never while a refresh holds the run lock or a paste's photos are uploading, and lists every pack in `photos/packs` (`references/database.md`), with the last error and the count of originals it couldn't delete. Never pack, repoint or delete pack files yourself.
- **Leftover originals (v1.31.3).** Pages up to v1.31.2 kept the originals of a packed day whose photos sat in more than one block (unused files, so the page's file count barely fell). With packing on and no day ready to pack, the page removes them itself, a few at a time under the same lease and waits: only an original that nothing in the `photos` documents uses, that is an item of a listed pack which checks out against every photo's SHA-256, whose slot shows that very item, and whose own bytes match the item's. A pack that doesn't check out gives up nothing, and what the page keeps is recorded in `photos/swept-<pack>` as in use (`references/database.md`); a pack that's missing or unreadable is `lost`, which limits Cleanup to duplicates. Its progress is `photos/packs.reclaim`; the Photo storage box says how many it removed, how many packs are still to check, what it kept and why, and any pack that's missing. When the user asks why the file count rose after packing, say this, and that the page clears them while it's open.
- **One photo from a pack:** `Artifact read` with the page's `url` and path = the pack's id (the part of the slot before `#`) saves the pack's JSON. Item `n` (the number after `#`) of its `items` is the photo: decode its `b64` (base64) to a file named for its `type` (for example `python3 -c 'import json,base64,sys; it=json.load(open(sys.argv[1]))["items"][int(sys.argv[2])]; open(sys.argv[3],"wb").write(base64.b64decode(it["b64"]))' pack.json 3 photo.jpg`), then Read that file. Use the preview pack (`pv`) when a small copy is enough: it's much smaller.

## Cleanup (only when the user asks)
Run this only when the user asks (for example "tidy up photo storage"), never on your own and never in a scheduled run. Deleting a file can't be undone, so nothing is deleted before the user confirms the counts, and **never delete a file any `photos` document references**. The page's chats share one store of files: an added chat's `KEY_photos` documents count exactly like `photos`.
1. Take the run lock as a refresh does: `refresh/status` `{state:"running",startedAt,step:"photo cleanup",by:"photo cleanup"}`, pinned (skip and tell the user if another run holds it). `get` `refresh/lastImport`: if it's `uploading`, `get` it again at least 60 s later. If `beat` changed, photos are storing: release the lock and stop (try later). If it didn't, the tab that wrote it is gone: carry on. When you stop, at any point, update `refresh/status` to `{state:"done",finishedAt,added:0}`, pinned.
2. `ArtifactData list photos` (limit 1000; continue with `next_cursor` until it ends), and the same for `KEY_photos` of every chat in `meta/chat.chats` that isn't `deleted` (active, paused, pending or hidden: a hidden chat can come back). Referenced = every id in any of these documents: every `/_blob/<id>` string with any `#<n>` after it removed (the blocks' `byK` **and `pv`**, the old `index`'s `byI` and `byK`, and the `kept` and `own` lists of `photos/swept-<pack>`: originals the page kept because a check didn't pass, which may be the only good copy), plus the bare ids `full` and `pv` of every entry in `photos/packs` › `list`. If any `photos/swept-<pack>` document has `lost: true` (a pack that's missing or unreadable: the originals it held can't be named, and one may be the only copy of its photos), delete only duplicates (step 4) this time, never offer the other unused files, and tell the user which day's pack is missing. **A pack file is always referenced, never unused**, even when only one slot points at it: deleting it loses a whole day of photos. (Originals the old index still names after their day was packed count as referenced here; the page removes those itself, Storage › Leftover originals.)
3. `Artifact list` with the page's `url` and `scope:"assets"` (continue with `after` until it ends): every file's id and size.
4. Unused = listed ids that aren't referenced. Among them, **duplicates** have the same SHA-256 as a referenced file: for each unused file whose size equals a referenced file's, `Artifact read` with the page's `url` and path = each id, then `shasum -a 256` the saved files. The other unused files are uploads that were never indexed (a tab closed or timed out as they landed); one may be the only copy of a photo that's owed or given up.
5. Report the counts and sizes: referenced files, duplicates, other unused files, and what deleting each group frees (files and MB). Ask which to delete: the duplicates (recommended), or every unused file. Without a clear yes, release the lock and stop.
6. List `photos` again (and every `KEY_photos`) and drop any id that's referenced now. Delete each remaining id with `Artifact` `action:"delete"`, the page's `url` and path = the id. Release the lock and report what was deleted. The page's warning updates the next time it's opened.

## Captions for older photos (only when the user asks, e.g. "caption my old photos")
Photos stored before Looking wrote captions, or after a run stopped waiting, have none, so the page's search can't find them by what they show. Run this only when the user asks, never on your own and never in a scheduled run. It writes only `captions` documents, each pinned, so it takes no run lock: if a refresh writes the same block in between, your write is refused and nothing is lost.
1. Bootstrap WORK as a refresh does (or use this session's WORK if it's current). In a fresh RUN folder, `list photos` and `list captions` (limit 1000 each) with `out_dir` RUN, and note the captions versions. If the captions collection is empty and the list leaves no folder, make an empty `RUN/captions`.
2. Run `python3 catchup.py captions WORK RUN`. It lists the next 50 stored photos with no caption, oldest first (`--max=N` for another size), in `RUN/out/captions-todo.txt`: each with how to open it and the messages around it (its own marked `*`, its conversation's title above). It also says how many are left, and "done" when none are.
3. Open each one:
   - `asset <id>`: `Artifact read` with the page's `url` and path = the id, then Read the saved file.
   - `preview <id> item <n>`: a packed photo. `Artifact read` with the page's `url` and path = that id saves a JSON file `{items:[{i,k,type,b64,…}]}`. Don't Read that file (it's all base64): with a short script, check that `items[n]` has the photo's `i` and `k` and decode its `b64` to an image file named for its `type`, then Read the image. Previews are small (320 px), about 100 tokens a photo. Fetch each preview pack once per batch, not once per photo.
   - `pack <id> item <n> (no preview)`: the same with the full pack, which is larger.
4. Caption each photo as Looking says, from the photo and the messages printed with it. Write `{"captions": {"<i>": {"<k>": "…"}}}` to a spec file and run `python3 catchup.py captions WORK RUN spec.json`: it checks that every slot holds a stored photo and writes `RUN/out/manifest.json`. Write what it lists as step 7 does (one `ArtifactData batch` per entry, `if_version` from step 1's versions where it has `pin`), with no `meta/chat` or `refresh/status` write. WORK doesn't move.
5. Refused (a refresh wrote that block since): `list captions` into RUN again and repeat step 4's command and write with the same spec.
6. After each batch, tell the user the progress in one line ("Captioned 50 photos, #120–#655; 712 to go"). Then `list captions` into RUN again (fresh versions, and the batch just written) and go on from step 2, until it says done or the user asked for fewer. To resume later, even in another conversation, start again at step 1: the list always begins at the oldest photo still without a caption.
