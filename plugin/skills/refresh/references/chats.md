# Several chats on one page

Read this when `meta/chat.chats` lists more than one chat, when the user names a chat ("refresh Book Club", "refresh book"), or when `meta/chat` has no `chats` yet (the upgrade below, once).

The owner manages their chats on the page (title ▾ › Add a chat, and Settings ⚙ › Your chats): adding, tags, pausing, removing and each chat's reply setting all work without Claude. Don't add, remove, pause or retag a chat yourself unless the user asks; the page writes what they choose and the next refresh of that chat does the rest.

## The data
- `meta/chat.chats` (written by the page, and once by the upgrade): `{<key>: {name, tag, color, order, state, home?, url?, thread?, days?, start?, photos?, auto?, every?, addedAt, reason?, deletedAt?}}`. The key is fixed for life (1-6 lowercase letters and digits); `tag` is what the owner sees in citations and can rename. `state`: `active`, `pending` (added on the page, not read yet), `paused` (refreshes skip it), `hidden` (removed, kept; it can come back) or `deleted` (removed, its documents and photos deleted by the page; the key is never reused).
- **Order and How often** (the owner sets both in Settings › Your chats): `order` is the chats' order after the first chat, which always comes first (Move up / Move down, or dragging a row, rewrite it; a chat without one comes last); the title's chat list and All chats follow it, and so does a run, except that it takes the chats the last run didn't reach first and pending chats last. How often a scheduled run refreshes a chat other than the first (which it always refreshes): its `every` in minutes (0: every run; 120, 240 or 1440; null or missing: the page default), else `meta/chat.chatEvery` (missing or 0: every scheduled run). Only a scheduled run follows it (`run-plan --scheduled`); a run the user asks for refreshes every chat.
- The **first chat** (`home:true`) keeps the page's own documents: `meta/chat`, `chunks/*`, `threading/*`, `summary/*` and the rest, exactly as a one-chat page. A page without `chats` is that one chat.
- An **added chat** `KEY` has its own: collections `KEY_chunks`, `KEY_threading`, `KEY_summary`, `KEY_digests`, `KEY_reports`, `KEY_photos`, `KEY_captions`, `KEY_people`, `KEY_outbox`, `KEY_rangeSummaries`; `meta/chat-KEY` (that chat's own fields: `key`, `thread`, `chatUrl`, `threadName`, `shortName`, `topic`, `firstCount`, `firstDays`, `chunkSize`, `lastI` … `markerTo`, `lastRefresh`, `coverage`, `photosOwed`); `refresh/lastImport-KEY`.
- Shared by every chat: `meta/chat`'s page-wide fields (`ownerName`, `ownerAliases`, `tz`, `refreshPhrase`, `outboxAuto`, `chatEvery`, `helperPost`, `schedule`, `versions`, `pageVersion`, `assetUsage`, `photoPack`, `ideasSeenAt`), `refresh/status` (the one run lock), `refresh/skipped`, `refresh/importLock`, `refresh/schedule`, `refresh/packing`, `allchats/summary` (the summary across chats, below), `notes/*`, and `qa/*` and `views/*` (an added chat's rows carry `chat: KEY`; the first chat's have none; a question asked on All chats' Ask covers every chat: `scope: "chats"`, with `chats` and citations `[KEY#n]`, see `references/database.md`).
- `python3 catchup.py chats META.json KEY` (META.json: `meta/chat` as you read it) prints where chat KEY's documents live, its `--chat` argument (empty for the first chat), `auto` (below) and, for a pending chat, the `meta/chat-KEY` to seed.

## The upgrade (once per page)
If `meta/chat` has no `chats`: `python3 catchup.py chats META.json` prints the one write that adds it (`{}` when there's nothing to do). Write it as a `meta/chat` update pinned with the version you read. Refused: read `meta/chat` again and retry once. If that fails too, say so in the report and go on: the page reads a page without `chats` as one chat, so nothing is lost and the next refresh tries again. It changes nothing else.

## Which chat a refresh is for
- A **scheduled run** and "refresh my catch-up" (`refreshPhrase`): every `active` chat (a scheduled run: those due by How often), then every `pending` one's first refresh, by A run over every chat (below).
- "**Refresh** <name or tag>": that chat only, under the same lock. `paused` or `hidden`: say so and ask before refreshing it. `pending`: its first refresh (below). Several named: one after another, one at a time. After each chat it refreshed, `update` `refresh/skipped` with `{last:{"<key>":"<its lock's startedAt>"}}` (an update merges, so the rest of the document stays; no document yet: `set` `{keys:[],last:{…}}`), so How often counts from this refresh.
- Never two chats at once: one Messenger tab, one clipboard, one paste at a time.

## A run over every chat
One run, one lock, the chats one after another (one Messenger tab: never in parallel). **Only a scheduled run** (scheduling.md › A scheduled run) **has a 15-minute limit:** it passes `--scheduled` to every `run-plan`, no new chat starts once 15 minutes have passed since the run began, and the next run starts with the chats this one didn't reach, so none is left out for long. A chat already started always finishes. **How often** too applies only with `--scheduled`: a chat a run refreshed less than its interval before this run started (less 15 minutes, since each chain run starts a little early) waits for a later run; the first chat and a pending chat never wait. **A run the user asked for** ("refresh my catch-up") never passes `--scheduled`: it refreshes every chat to the end and writes `refresh/skipped` `[]` at its end, unless a failure that stops the run (step 4) leaves chats unreached.
1. Before each run (SKILL.md) as usual, plus `ArtifactData get refresh/skipped` (keep its version). Save `meta/chat` as META.json and `refresh/skipped` as SKIPPED.json (`{}` if there's none). `python3 catchup.py run-plan META.json SKIPPED.json` (plus `--scheduled` in a scheduled run, here and in steps 3 and 4) prints `order` (the first chat, then the chats the last run left, then the others by `order`, pending ones last), `next` (the first chat to refresh), its `chatArg`, `pending`, `later` (chats not due yet by How often), `runAt` (keep it) and `status`: step 1's lock. Write that as step 1 says, with `set`. No `next`: nothing is due (`status` is `{state:"done",…,due:0}`: `set` it, so the page shows the run happened) or nothing is active or pending (no `status`); either way stop quietly and reschedule.
2. Refresh chat `next` by SKILL.md's Refresh steps. Chats after the first skip Before each run's lock check, because the run holds the lock (it renews it at each chat): do only its WORK part, then steps 2–8 (step 1 too is the run's). The first chat as written there, an added chat by Refreshing an added chat KEY, a `pending` one by A pending chat's first refresh. Its WORK, RUN and spec are its own. While the run goes on, every place where its steps 7 and 8 would write `refresh/status` `state:"done"` writes `{state:"running",step:"outbox",added}` instead: the lock stays held between chats.
3. After each chat: `python3 catchup.py run-plan META.json SKIPPED.json --done=<keys refreshed or tried, in order> --started=<runAt>` (plus `--failed=<keys>` once a chat has failed, step 4). With a `next`: update `refresh/status` (pinned) with its `status` (it renews `startedAt`, so a run that works through several chats never looks stale), then step 2 for it. Without one, the run ends: update `refresh/status` (pinned) with its `status` plus `added` (the run's total), and `set` `refresh/skipped` to its `skippedDoc` (pinned with the version from step 1; refused: another run wrote it, so leave it). `skippedDoc.keys` lists the chats a scheduled run's time limit left (`[]` when every chat was refreshed, always so in a run the user asked for unless step 4 stopped it): the page shows them as not refreshed in the last run, and the next run takes them right after the first chat. `skippedDoc.last` records the run's start for each chat it refreshed (not for `--failed` ones): How often reads it. Only a run's end writes `refresh/skipped`, so the lock's own writes (a refresh's, a reply run's, an error) never lose it.
4. **A chat that fails** (a scan error after its retry, verify failing twice, a refused write its steps can't recover, a pending chat that can't be read): don't write `state:"error"` for it; note it for the report, add it to `--done` and `--failed`, and go on to the next chat; the next run tries it again. A failure that stops every chat stops the run: Chrome unreachable or the Messenger tab hidden, `selfcheck` not ok, the tab on a chat that isn't on the page, or the lock taken by another run. Run `run-plan` with the chats finished so far in `--done` (and `--failed`), `--started` and `--stop`: update `refresh/status` (pinned) with its `status` (`state:"error"`) plus `message` and `added` (the run's total so far), and `set` `refresh/skipped` to its `skippedDoc` as step 3 does, so the next run starts with the chats not reached. With the lock taken by another run, write only `refresh/skipped`: the lock is theirs.
5. **Once per run, after the last chat:** the summary across chats (below), Method ideas, the `people/index` check (step 8) for the chats refreshed, and scheduling.md's end of the run.
6. **The report:** one report for the run. Each chat refreshed gets its own bullets, the first naming it ("Book Club: 12 new messages", then its spec's `report`); chats with nothing new share one line ("Nothing new: Camera Club, Trail Crew"); then any chat that failed, with why; then, in a scheduled run, the chats the time limit left: "Not reached (15-minute limit): Chess Club. The next run starts with it." Chats not due yet (`later`) aren't named.

## The summary across chats
All chats' Summary opens with "Across your chats", from `allchats/summary`. Write it at the end of every run over every chat (step 5) in which at least one chat brought new messages; otherwise leave it. A refresh of one named chat doesn't write it.
1. Draft DRAFT.json `{"points":[{"h":"<heading, a few words>","t":"<the point>"}]}`: at most 10 points, each at most 45 words, from what each chat's summary now holds after that chat's catch-up point (`caughtUpI`): its conversations with new messages, open questions, deals and mentions of the user (not a settled one, with `answered`: the user answered it with their own reaction, B69), plus what this run's refreshes reported. What matters most first (mentions of the user and open questions to them, then deals and plans); things in several chats together; the same person named the same way in every chat (their full name). Every point cites the messages it rests on as `[KEY#n]`, the chat's fixed key (`[cam#412]`, `[cam#412, tea#88]`), never a bare `[#n]`: numbers restart in each chat. A chat with nothing since its catch-up point adds no point.
2. `python3 catchup.py allchats META.json DRAFT.json --done=<the run's --done> --new=<chats that brought new messages> --failed=<the run's --failed> --later=<run-plan's later> --started=<runAt>`. It checks the draft (fix what it names and run it again) and prints `doc`, with each chat's state in that run (`new`, `nothing`, `failed`, `later`, `paused`, or `skipped` when not reached); `doc` null: nothing to write.
3. `get` `allchats/summary` (keep its version), then `set` it to `doc`, pinned with that version (none yet: unpinned). The page names every chat the run didn't refresh, saying its part is from its last refresh. Refused: read it again and set once more; refused twice: say so in the report and go on.

## Refreshing an added chat KEY
Follow SKILL.md's Refresh steps with these changes. Everything not named here is as written there.
- **Names.** Every collection and document is chat KEY's (`catchup.py chats` prints them): read `meta/chat` (page-wide fields, `chats`) **and** `meta/chat-KEY` (the chat's `thread`, `chatUrl`, `lastI`, `anchorMids`, `firstCount`, `photosOwed`); step 1's lock is the shared `refresh/status` with `by:"refresh KEY"`; list `KEY_chunks`, `KEY_threading`, `KEY_summary`, `KEY_digests` and query `KEY_reports` and `KEY_outbox`.
- **catchup.py**: add `--chat=KEY` to every command, and keep a separate WORK for each chat (`WORK-KEY`). The out_dirs hold the chat's documents under their own names (`KEY_chunks/`, `meta/chat-KEY.json`), which is what `--chat=KEY` reads; manifests name KEY's collections. catchup.py refuses a WORK or RUN of another chat.
- **The Messenger tab (step 2).** One Messenger tab in Claude's tab group serves every chat of the page: navigate it to the chat's `chatUrl` and wait only for the helper to load, never for the tab to be on a chat by itself. A tab on one of the page's chats is Claude's to move; a tab on a chat that isn't on the page is the user's (SKILL.md step 2). Run `selfcheck` once per chat per run.
- **The scan (step 3).** The helper's results carry `thread` (helper 2.3 and later): accept a result only when it equals the chat's `thread`. An added chat refuses a capture without it, so with an older installed helper (`data-mc-helper` 2.2 or lower) inject the current one for that chat's steps (`references/helper.md` › Injecting: it takes over from the installed copy until the tab reloads, so never run `full` then; run the injected steps one at a time), and tell the user to update the helper (`references/helper.md` › Versions). The first chat takes a capture without `thread`, as before several chats, so its refreshes (scheduled ones too) work with any helper. `full` returning `stage:"wrong-thread"` means the tab was moved to another chat mid-scan: navigate back to `chatUrl` and start again with a fresh `run` id.
- **The paste (step 4).** Every chat's capture goes into one page tab, open while the run imports (`references/helper.md` › Tabs): never a new tab per chat. The page opens on All chats, with the first chat loaded under it. Before pasting, click the title (it reads "All chats", or the chat last pasted into) and pick the chat (a pending chat opens too, saying it waits for its first refresh), then paste. The picker doesn't switch while the page tab is still storing photos or packing: wait, as photos.md › Waiting says. The page refuses a capture from another chat ("This capture is from …, not …"): pick the right chat and paste again. A chat whose `photos` is false stores no photos: skip the photo steps.
- **Writes (step 7).** `lastRefresh` and `coverage` go to `meta/chat-KEY` (pinned). `versions` belongs to the first chat (the page compares it with `meta/chat.lastRefresh`): don't write it for an added chat. **Nothing new:** only `meta/chat-KEY`'s `lastRefresh`, and `refresh/status`.
- **Full names (step 8).** Step 8's `people/index` check is per chat: `get` `KEY_people/index`, and when it has no `scannedAt`, run `references/people.md` › One-time name scan for this chat (its `chatUrl`, `count` = its `lastI` + 1, `KEY_people/index`; the shared lock with `by:"names scan"`). In a scheduled run it waits when the run has reached its 15-minute limit (`run-plan`'s `next` is empty because of the limit), and the next run tries again. Until it has run, the chat's senders show only the names Messenger printed.
- **Report:** name the chat in the first bullet ("Book Club: 12 new messages").

## A pending chat's first refresh
1. `python3 catchup.py chats META.json KEY` for its seed. Take the lock as step 1 does (in a run over every chat, the run holds it already).
2. Navigate the Messenger tab to its `url`. Check it opens a group chat the user is in (a message box, the chat's name in the header; no "not available", no PIN prompt). If not, update `meta/chat` (pinned) `{chats:{KEY:{reason:"<what you saw, one short sentence>"}}}`, leave it `pending`, release the lock with `{state:"done",finishedAt,added:0}` (in a run over every chat: go on to the next chat instead), and tell the user. Other chats are unaffected.
3. Seed in one batch: `meta/chat-KEY` from the seed with `threadName` (the header's name), `shortName` and `topic` (a few words, from the messages you see); `KEY_threading/current` `{convs:[],links:{},to:-1,note:""}`; `KEY_summary/current` `{version:2,convs:[],open:[],answered:[],deals:[],mentions:[],toI:-1}`.
4. Run the first refresh for it by `references/first-run.md`, with the changes above (`catchup.py chats` seeds `firstDays` from its `days`, how far back the page asked to read, or `firstCount` from an older entry's `start`, a message count).
5. Then update `meta/chat` (pinned) `{chats:{KEY:{state:"active", name:"<threadName>", reason:null}}}`, keeping the tag the owner chose.

## Replies in several chats
- Whether a queued reply goes out without asking follows the chat's own `auto` when it's `true` or `false`, else the page default `meta/chat.outboxAuto` (`catchup.py chats` prints the result as `auto`). The rest of the approval rule is SKILL.md's.
- Step 2's "Replies first" and step 8 handle the chat being refreshed: its `KEY_outbox`. A reply is posted only with the tab on that chat's `chatUrl`, after `selfcheck` and outbox.md's checks, so it never lands in another chat.
- "Send replies" (`messenger-catchup:replies`) covers every live chat; its SKILL.md says how. A reply check (`messenger-catchup:reply-check`) reads each `active` chat's outbox and hands only the chats with a queued row to replies.
