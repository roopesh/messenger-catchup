# Per-day digests

Read this the first time you write digests in a session (step 6 of a refresh), when a build says digests are still due, and when the user asks for digests of past days (Backfill, below).

A digest is a few bullets on what happened on one finished day, each citing the messages it covers. The page's Ask Claude sends them for days older than its conversation lines reach (about three weeks back), in place of a bare "460 messages. Busiest: …" line, so questions about older things get real answers with message numbers. The page only reads them; nothing else shows them yet.

## Where they're stored
One document per month: `digests/m<YYYY-MM>` `{month, days:{"<YYYY-MM-DD>": {bullets:[{t, refs}], fromI, toI, n, at, final}}}` (`fromI`, `toI`, `n`: the day's first and last stored message and how many there were when it was written; `at`: when; `final`: a later day was already stored then, so the day is never digested again). A day is a message's date label `d`, as the helper read it in the browser's time zone (which may differ from `meta/chat.tz`). A day never goes back: a message dated before the one before it (the browser's zone changed between captures) counts in that one's day, and so does a message without a label, so each day is one run of numbers; the page groups days the same way. A month at every cap is under 90 KB, well inside the 256 KiB a document holds; years of history are a few dozen documents. Only `catchup.py` writes them, through its manifest; never edit them by hand, and the page never writes them.

## During a refresh
1. Step 5 lists the collection into RUN with the others: `list digests` (limit 1000). `catchup.py` needs the `RUN/digests/` folder to know which days have a digest: if the collection is empty and the list leaves no folder, create an empty one.
2. Before writing the spec, run `python3 catchup.py days WORK RUN`. It prints a `DIGEST <day> #a-#b (n messages): <file>` line for each day due, and writes that day's messages, one per line, to `RUN/out/days/<day>.txt`. Due: finished days after the newest digest (when there's none yet, only the newest finished day: older days are the backfill's), and a day whose digest isn't `final` and that gained messages, once a later day is stored (it was written while the browser's zone was still on that day, say with `meta/chat.tz` ahead of the browser; the second digest is final, so a day is digested twice at most). Oldest first, 3 at most; the next refresh carries on. A day has finished when a later day is stored, or it's before today in `meta/chat.tz` (only the first when this Python has no time zone database).
3. Read each file and add the day to the spec's `digests`: `{"2026-11-12": [["Ana sold the stove to Ben", [6120, 6131]], ["Cy asked about permits; Dee answered", [6200, 6214]]]}`.
4. Build as usual (a refresh with nothing new skips step 6, so its days wait for the next one that builds). The digests go into the manifest's first batch: a month that exists is pinned (`pin:true`, with its version from step 5's listing), a new one isn't. The build's `build ok` line says how many it wrote, and which days are still due, if any.

## Writing the bullets
- 1 to 8 bullets a day; fewer on a quiet day. Each ≤15 words (and 240 bytes) of plain text on one line, citing 1 to 10 messages of that day (`refs`).
- What someone would want to find later: what was offered, sold, decided, asked and answered, plans, who did what. Skip greetings and chatter.
- The same naming and wording rules as the spec's bullets (SKILL.md › Writing the spec).

## What catchup.py checks
`RUN/digests/` exists (step 5's listing); each key is a real date with stored messages; the day has finished; it has no digest yet, or the one it has isn't final and the day gained messages; 1–8 bullets, each ≤15 words and ≤240 bytes, with no line breaks or control characters; each bullet cites 1–10 message numbers, all stored messages of that day. A failed check stops the build before anything is written or WORK moves: fix the spec and build again. A refused write of a `digests` document: `list digests` into RUN again, `catchup.py restore WORK`, and build again; a day it then says already has a digest has landed: drop it from the spec.

## Backfill
Only when the user asks (for example after updating to a version with digests): digests for every past day, in batches. It's safe to stop between batches and resume later, in this session or another; nothing here changes threading or the summary.

**Cost:** a batch reads up to 2,000 messages (about 35,000 tokens), so a long history doesn't fit one session: 75 days of a busy chat (about 9,000 messages) is 8 batches and over 270,000 tokens. Do 2 or 3 batches in a session, then stop and tell the user how many days are left (the last check says) and that asking again carries on.
1. Bootstrap WORK if this session has none (SKILL.md › Refresh steps).
2. `list digests` (limit 1000) into a fresh folder RUN (an empty collection: create an empty `RUN/digests`), then `python3 catchup.py days WORK RUN --backfill`. It picks the finished days that need a digest, newest first, up to 10 days and 2,000 messages (one day at least), writes their files, and says how many days are left. Nothing to digest: the backfill is complete; tell the user.
3. Read each file (a day of more than 2,000 lines: read it in parts, with the Read tool's `offset` and `limit`) and write the spec `{"digests": {...}}` (only that key), then `python3 catchup.py digests WORK RUN spec.json`. It checks the spec as a build would and first saves every month document as listed, and which days they held, in `RUN/out/backup/` (the backup). It touches only the days in the spec, and refuses one whose digest stays (a final one, or one whose day gained no messages since).
4. Take the run lock just before the write, as a refresh does, so a scheduled refresh skips instead of racing it: `get` `refresh/status`; if its `state` is `"running"` and `startedAt` is under 20 minutes old, a run is in progress: stop here and try this batch later (from step 2). Otherwise set it to `{state:"running",startedAt,step:"digests",by:"digest backfill"}`, pinned with the version you just read; if that's refused, `get` it again, and if another run took it, stop as above. Then write what `RUN/out/manifest.json` lists, one `batch` per entry, `pin:true` entries with their version from step 2's listing. Release the lock right after, whatever happened: update `refresh/status` (pinned) to `{state:"done",finishedAt}`.
   - **A refused write** (a month changed since step 2's listing, usually because a refresh wrote the current month): nothing of that batch landed. Don't run the check: release the lock and go back to step 2 with a fresh folder; the same days come up again.
5. Check it: `list digests` into another fresh folder AFTER and run `python3 catchup.py check-digests WORK RUN AFTER`. "check ok" says how many days were written, how many were kept, and how many are left. Anything else (a day changed or missing since the backup, or not as written): stop, write nothing more, and tell the user; the backup in `RUN/out/backup/digests/` holds the month documents as they were.
6. Tell the user the batch's days in one line. To carry on, AFTER is the next batch's listing: run step 2's `days` on it and go on from there. A batch whose write never landed is simply found again by the next `days`.
