# Facebook groups (F25)

Read this when `meta/chat.chats` holds an entry with `kind:"group"` and a run reaches it (`catchup.py run-plan`), or when the user asks about groups. A group lives on the page next to the chats: its own key, tag and collections (`KEY_posts/p<postId>`, `KEY_comments/p<postId>`, `meta/chat-KEY`, `refresh/lastImport-KEY`, `KEY_outbox`). Reading is read-only on Facebook; the one exception is a comment the user queued and approved (Comments, below).

## Hard rules for groups
- Never click inside a post: polls vote on a click, and like, react, comment and share buttons sit next to everything. The helper only scrolls, sends pointer events to a post's time link (that fills in its address), opens "View N replies", and uses a post's own comment-sort menu (which changes only your view). The only other clicks are the helper's `groupComment` for an approved comment: a comment's Reply, and the comment box it types in (`references/outbox.md` › Group comments).
- **Never post a comment** unless the user approved it: they said yes in chat to that exact text, or auto-posting is on for that group (its own `auto` in `meta/chat.chats` when set, else `meta/chat.outboxAuto`) and they queued it on their own page. Only with helper posting on (`meta/chat.helperPost`).
- Never open a notification (a click marks it read). Reading the notifications page clears the user's red badge on Facebook; the user accepted that (every refresh).
- Groups need the helper 3.1 or later (`data-mc-helper`), installed or injected (SKILL.md › Helper).

## The entry (`meta/chat.chats.KEY`)
`{kind:"group", name, tag, color, order, state, url, group (the id or name in its address), chat? (a chat key it goes with), start:{days} (the first read, 3, 7 or 30), read:"all"|"mine", rollup (Show in All), auto? (its queued comments post without asking; missing or null: `outboxAuto`), addedAt, reason?}`. The page writes it (Settings › Add a group) as `pending`; `chat`, `read`, `rollup` and `auto` can be changed later on the group's Settings screen, each a write of that one field.

## A refresh of a group
Use one run id (`run`, e.g. `g` + the current time in ms) for every command of this group's refresh, and the bridge from SKILL.md › Helper. Navigation ends a running command, so start each command after its page has loaded.
0. **Comments first:** `ArtifactData query KEY_outbox` for `queued` and `sending` rows. If any `queued` row is approved (the hard rule above), read `references/outbox.md` in full and post those now by its Group comments section. Keep the `pid` of every row left in `sending`: step 5 opens those posts too, and step 6's import settles them.
1. **Known posts:** `ArtifactData query KEY_posts` (fields `pid`, `count`, `who`) into a map `{pid: count}`. A post stored without `who` is a stub: known only from its comments or a notification (the page shows "a post not read yet"). None (the first read): see First read.
2. **Notifications (once per run, for all groups):** navigate the Messenger tab to `https://www.facebook.com/notifications/`, start `notifs{since: meta/chat.notifSeenTo, more: 3, run}`. Its `byGroup` lists posts to open in each group. Keep its `newest` to write as `meta/chat.notifSeenTo` at the end of the run (pinned).
3. **New posts:** navigate to the group's `url` + `?sorting_setting=CHRONOLOGICAL`, start `groupFeed{known, cap: 50, run}`. It stops at the first known post.
4. **New comments on older posts:** navigate to `url` + `?sorting_setting=RECENT_ACTIVITY`, start `groupFeed{known, cap: 50, run}` again. It stops two cards after the first unchanged post.
5. **Each changed post** (in either feed result's `changed`, plus the notification posts for this group and the posts of step 0's `sending` rows, then the stubs from step 1), at most 50 in all: navigate to `https://www.facebook.com/groups/<group>/posts/<pid>/`, start `groupPost{run, known: the post's stored comment ids}`. With helper 4.3 it also reads the post's own author and text (`body:true` in its answer), so the capture fills a stub, keeping its number; stubs left over wait for the next run. Each answer carries `buf` (the run buffer's counts; `store:"gm"` with helper 4.2+): if `buf.posts` ever drops below the feed's, stop and report it (the buffer was lost, #103) rather than capture.
6. **Capture:** start `groupCapture{run, group}`, click COPY CAPTURE, then paste on the page with that group picked (as for a chat, SKILL.md step 4). The page stores new posts (their `p` numbers) and new comments (their `c` numbers within the post) and says "IMPORT OK: N new posts and M new comments". Then settle step 0's `sending` rows from the stored comments (`references/outbox.md` › Group comments, its settling bullet), pinned.
7. **Write** `meta/chat-KEY` `{lastRefresh, coverage, versions}` (pinned; `versions` as in `references/database.md` › Versions), and for a `pending` group `state:"active", reason:null` in `meta/chat.chats` (one pinned update: a failed first read's note goes with it).
8. **Report** in a bullet named for the group: new posts, threads that moved, deals (item, price, sold or not), questions to the user, and each comment posted, failed, left `sending` or waiting (with why).

## Comments (G3a)
The user queues a comment on a post, or a reply to a comment, on the group's Posts (Comment here, Reply here): a `kind:"comment"` row in `KEY_outbox`. A refresh posts the approved ones at step 0 and settles them after its import; "send replies" (`messenger-catchup:replies`) posts them too, and a reply check finds them. How: `references/outbox.md` › Group comments. Text only for now; photos come with G3b.

## First read and big groups
- A pending group's first read covers its `start.days` (by New posts, up to 300 posts per run): `groupFeed{cap: 300, maxDays: start.days, run}` with no `known` (helper 3.2; it stops at the first post older than that, `stop:"age"`). Comments: up to the 50 newest per post. If it stopped at the cap (`stop:"cap"`), write `catchingUp:true` in `meta/chat-KEY` (the page says "Catching up"); the next runs read on with `groupFeed{known, through: true, maxDays: start.days, cap: 300, run}` (helper 3.3: known posts don't stop it or count toward the cap) until it stops by age or at the end (`stop:"age"` or `"end"`), then write `catchingUp:false`.
- After that, 50 changed posts per run; the rest wait for the next run.
- "Read: only mine" (`read:"mine"`): open only posts the user wrote or commented on, and the notification posts.
