# Day summaries

Read this the first time a refresh in this session reaches step 6 (`catchup.py days`), when a build says day summaries are still due or stops on `daySummaries`, and when the user asks for summaries of past days (Backfill, below).

A day summary is the fuller account of one day of the chat: topic sections, each a heading with bullets citing the messages they cover, then what's still open. The page's By day tab shows a card per day, newest first, with a "Copy for chat" button that copies it as plain text without the message numbers. Ask Claude reads the summaries for older days (in its day lines and its `day_summaries` tool). The day in progress is kept current by every refresh that builds; once the day has ended it's rewritten once from all its messages, so it reads as one piece.

## Where they're stored
One document per day: `daySummaries/d<YYYY-MM-DD>` `{day, fromI, toI, n, at, full, fullToI, final, sections:[{h, bullets:[{t, refs}]}], open:[{t, refs}]}`. `fromI`, `toI` and `n`: the day's first and last stored message and how many there were when it was written (the summary covers them); `at`: when (ISO time); `full`: rewritten from all the day's messages after it ended, through `fullToI` (an update after that keeps both); `final`: a later day was already stored at that rewrite, so it's never written again. A day is a message's date label `d`, as the helper read it in the browser's time zone (which may differ from `meta/chat.tz`). A day never goes back: a message dated before the one before it (the browser's zone changed between captures) counts in that one's day, and so does a message without a label, so each day is one run of numbers; the page groups days the same way. A busy day's summary is a few tens of KB, well inside the 256 KiB a document holds. Only `catchup.py` writes them, through its manifest; never edit them by hand, and the page never writes them.

**Older digests:** pages from before v1.32.0 also have `digests/m<YYYY-MM>`, a few short bullets per finished day. Refreshes no longer write them (a build refuses `digests`), and there's no digest backfill any more. They stay: the page shows a day's digest only while that day has no summary. Never delete them.

## During a refresh
1. **Step 5:** `ArtifactData query` the `daySummaries` collection with `query: {order_by: {field: "day", direction: "desc"}, limit: 5}` and `out_dir` RUN: the newest five days, with their versions in the result. If that leaves no `RUN/daySummaries/` folder (the collection is empty), create an empty one. `catchup.py` needs the folder to know which days have a summary. When it holds no summary at all (the first refresh after the update), also `list digests` (limit 1000) into RUN, so `catchup.py` can tell whether the day that just ended already has an older digest.
2. **Step 6,** before writing the spec: run `python3 catchup.py days WORK RUN`. It prints a `DAY <day> <KIND> #a-#b (n messages to read): <file>` line for each day due and writes what to read to `RUN/out/days/<day>.txt`:
   - `UPDATE`: the day gained messages since its summary was written: the day in progress, or a day that has ended in `meta/chat.tz` while the browser still dates new messages with it. The file holds its summary so far, as the spec writes it, then only the messages stored after it. Fold them in: add bullets to a section or start a new one, extend a bullet whose story moved on (keep its refs, add the new ones), take what got answered out of Still open and add what's newly open. Then write the whole summary, not just the changes.
   - `NEW`: the day in progress has no summary yet: all its messages so far.
   - `FINAL`: the day has ended: all its messages. Write it afresh as one piece, not as a patch of the summary so far, which it replaces. A final day is never written again.

   Due: the days after the newest summary (when there's none yet, the newest day and the newest day that has ended, unless an older digest covers that one; older days are the backfill's), and any summarized day that needs writing again. Oldest first, 3 at most; the next refresh carries on. A day has ended when a later day is stored, or it's before today in `meta/chat.tz` (only the first when this Python has no time zone database). A day that ended in `meta/chat.tz` before the browser's day did (the chat's zone ahead of the browser's) is rewritten then, gets the messages still dated with it as updates, and is rewritten once more, as final, once a later day is stored and it gained messages since its rewrite; so no message waits, and a day is rewritten twice at most.
3. Read each file (a file of more than 2,000 lines: read it in parts, with the Read tool's `offset` and `limit`) and add the day to the spec's `daySummaries` (below).
4. **Build** as usual. The documents go into the manifest's first batch, pinned (`pin:true`, with the version from step 5's query) when the query held that day. `build ok` says what it wrote, as `1 day summary (2026-11-22 in progress (#6205))`, and which days are still due, if any. A day rewritten after it ended by the clock, with nothing stored for it since, is marked final by the first build after a later day is stored, without a rewrite (`marked final, as rewritten: <day>`): its document goes in the manifest unchanged but for `final`. A refresh with nothing new skips step 6, so its days wait for the next refresh that builds.

## Writing a day's summary
The spec's `daySummaries`, one key per day:
```json
{"2026-11-22": {
  "sections": [
    {"h": "Stove sale", "bullets": [["Ana offered her stove for $40; Ben claimed it and they set a pickup for Saturday", [6120, 6124, 6131]]]},
    {"h": "Trip planning", "bullets": [["Cy proposed the ridge loop; Dee and Ben are in", [6150, 6152, 6160]], ["Dee shared the permit page", [6163]]]}
  ],
  "open": [["Cy asked you whether the permit covers two cars; no answer yet", [6200]]]
}}
```
- Like a good answer to "summarize that day": one section per topic of the day (a deal, a plan, a question, a long thread), in the order the day took them up, each with a short heading. A busy topic gets more bullets. No length limit: cover what someone who missed the day would want to know, and skip greetings and chatter.
- Each bullet is one line of plain text, citing the messages it covers (`refs`: at least one, all of that day). Who did what, prices, decisions, answers, plans, links shared.
- `open` ("Still open" on the page): questions nobody answered, asks to the user, deals still pending at the end of the day; `[]` when nothing is.
- The same naming and wording rules as the spec's bullets (SKILL.md › Writing the spec). "Copy for chat" leaves out the message numbers, and the owner may paste the text into the chat, so each bullet must read on its own: never write message numbers in the text, and check each line against the messages it cites.

## What catchup.py checks
`RUN/daySummaries/` exists (step 5's query); each key is a real date with stored messages; the day's summary isn't final; it needs writing (messages stored after its `toI`; a day that has ended: not rewritten since it ended, or a later day is stored and it gained messages since its rewrite, `fullToI`); the backfill takes only days that need their rewrite; a day older than all five the query returned is refused (query again with `limit: 30` into RUN and write `30` into a file `RUN/daySummaries/.limit`: fewer than 30 back means that's the whole collection); each day holds only `sections` and `open`; at least one section, each a one-line heading and at least one bullet; each bullet one line of plain text (no line breaks or control characters) citing at least one message number, all stored messages of that day; `open` a list of the same; the document within the build's 240 KiB. A spec with the old `digests` is refused. A failed check stops the build before anything is written or WORK moves: fix the spec and build again.

## A refused write
A `daySummaries` document changed since step 5's query, or one exists that the query didn't return. Refreshes hold the run lock, so this is rare. Query the summaries into RUN again, `catchup.py restore WORK`, run `catchup.py days WORK RUN` again (an update now starts from the newer summary), and build again (`references/writing-the-build.md` › Refused writes).

## Backfill
Only when the user asks (the owner said to wait until they like a few days' summaries): final summaries for every past day, in batches. It's safe to stop between batches and resume later, in this session or another; nothing here changes threading or the summary.

**Cost:** a batch reads up to 2,000 messages (about 35,000 tokens) and writes up to 5 fuller summaries, so a long history doesn't fit one session: 75 days of a busy chat (about 9,000 messages) is 15 batches or more. Do 2 or 3 batches in a session, then stop and tell the user how many days are left (the last check says) and that asking again carries on.
1. Bootstrap WORK if this session has none (SKILL.md › Refresh steps).
2. List the whole collection into a fresh folder RUN, a page at a time: `ArtifactData list` `daySummaries` with `query: {limit: 1000}` and `out_dir` RUN; while a result gives a `next_cursor`, list again with `query: {limit: 1000, cursor: <next_cursor>}` into the same RUN. One document per day, so a history over 1,000 days needs more than one page, and a day missing from the listing would look like a day without a summary. When a page comes back with no `next_cursor`, create an empty file `RUN/daySummaries/.all` (and the folder first, if the collection is empty): every backfill command refuses a listing without it. Then run `python3 catchup.py days WORK RUN --backfill`. It picks the finished days without their final summary, newest first, up to 5 days and 2,000 messages (one day at least), writes their files (each `FINAL`), and says how many days are left. Nothing to write: the backfill is complete; tell the user.
3. Read each file and write the spec `{"daySummaries": {...}}` (only that key) as above, then `python3 catchup.py day-summaries WORK RUN spec.json`. It checks the spec as a build would (days that have ended only), first saves each summary it replaces, and a record of every day the listing held, in `RUN/out/backup/` (the backup), and writes the manifest. It refuses a final day.
4. Take the run lock just before the write, as a refresh does, so a scheduled refresh skips instead of racing it: `get` `refresh/status`; if its `state` is `"running"` and `startedAt` is under 20 minutes old, a run is in progress: stop here and try this batch later (from step 2). Otherwise set it to `{state:"running",startedAt,step:"daySummaries",by:"day summary backfill"}`, pinned with the version you just read; if that's refused, `get` it again, and if another run took it, stop as above. Then write what `RUN/out/manifest.json` lists, one `batch` per entry, `pin:true` entries with their version from step 2's listing. Release the lock right after, whatever happened: update `refresh/status` (pinned) to `{state:"done",finishedAt}`.
   - **A refused write** (a day changed since step 2's listing, usually a refresh's final rewrite of yesterday): nothing of that batch landed. Don't run the check: release the lock and go back to step 2 with a fresh folder; the days still due come up again. If the same batch is refused again from a fresh, whole listing, stop and tell the user instead of trying once more.
5. Check it: list the whole collection into another fresh folder AFTER, page by page and with `AFTER/daySummaries/.all` as in step 2, and run `python3 catchup.py check-day-summaries WORK RUN AFTER`. "check ok" says how many days were written, how many were kept, and how many are left. Anything else (a final day changed or missing since the backup, a day missing, or a day not as written): stop, write nothing more, and tell the user; `RUN/out/backup/daySummaries/` holds the summaries the batch replaced. A refresh between the write and the check may update the day in progress, fold later messages into a backfilled day (its `toI` further on) or mark it final; that's fine. A day that lost messages from its summary, or changed without reaching further, is reported.
6. Tell the user the batch's days in one line. To carry on, AFTER is the next batch's listing: run step 2's `days` on it and go on from there. A batch whose write never landed is simply found again by the next `days`.
