# Database (ArtifactData on the user's page)

The full reference. The refresh skill's SKILL.md lists what a refresh needs.

- `meta/chat`: `kind:"messenger-catchup"`, `pageVersion`, `thread` (Messenger thread id), `chatUrl` (full chat URL), `threadName`, `shortName`, `ownerName`, `ownerAliases` (names others call them), `topic`, `outboxAuto`, `helperPost` (true lets the helper post approved replies; off unless the user asks Claude to turn it on: the refresh skill's `references/posting-with-helper.md`), `refreshPhrase`, `tz` (IANA), `firstCount` (the history size chosen at setup: how many messages the first capture reads), `helper` ("installed" | "inject"), `chunkSize:82`, `lastI`, `lastMid`, `lastT`, `anchorMids` (newest 3 ids; reversed = STOPS), `caughtUpI`, `caughtUpAt`, `ownLastI`, `ownLastMid`, `markerMode` (`caught` | `own` | `time`), `markerSetAt`, `markerFrom`, `markerTo`, `lastRefresh`, `coverage` (one short sentence the page shows after "Stored: N messages, #a to #b.", such as how far back the stored history goes; it ends with a period), `schedule` (`{mode, every, hours, tz}`, the user's choice, `hours` as `{from, to}`: `references/scheduling.md`), `ideasSeenAt`, `aliasesAskedAt` (when the user was asked which aliases count; the refresh skill's `references/people.md`). The page writes `lastI` … `ownLastMid` when it imports, and the marker fields when the user picks a catch-up start; Claude writes the rest.
- `meta/chat.versions` (Claude; with every `lastRefresh`, in the same update): what that refresh's skill ships and the helper each Chrome ran, so the page can say what to update (below, under Versions).
- `chunks/cNNNN` `{start, msgs:[...]}`: message fields `i` (number from 0), `t` ("Fri 8:41 AM"), `d` (date), `f` (sender as Messenger shows them: nickname or first name; the user = "You"), `fn` (full name from their avatar; helper 1.6+), `b` (text), `m` (Messenger id), `r` (replied-to name), `q` (quoted text), `pi`/`pmid`/`pq`/`perr` (reply parent), `p` (photo), `a` (link preview), `l` (links), `x` (reactions).
- `threading/*`: `current` plus the block documents it names; merged: `convs:[{id,title,members}]`, `links:{i:[parent,type]}` (r = Messenger link, rq = matched by quote, rg = photo reply best match, i = answers, c = same person continuing), `to`, `note`, `builtAt`.
- `summary/*`: the same; merged: `version:2`, `convs:[{id,tag,synopsis:[{t,refs}],outcome,key}]`, `open`, `answered`, `deals`, `mentions`, `toI`, `generatedAt` (optional `mentionsNote`, `fromI`).
- `people/index` `{people:{"<full name>":{shown:[...],firstI,lastI}},scannedAt}`: written by the page from `fn`.
- `photos/*` (blocks `b<start>`; an old `index`, read only), `refresh/status` (lock and status line), `refresh/lastImport`, `refresh/importLock` (the page's import lease; never write it), `outbox/*` (replies queued on the page).
- `refresh/schedule`: the schedule's live state, `armId` (the token in the current follow-up or recurring prompt), `nextAt`, `tool`, `lastRunAt`, `misses`, `problem` and `switchAskedAt` (shapes in `references/scheduling.md`). Only scheduling writes it; the page never reads it.
- `photos/b<start>` (written only by the page, one per 500 messages: `b0`, `b500`, …): `{start, byK:{"<i>":{"<k>": "/_blob/<id>" | null | {e}}}, gifs:[i…]}`. Slot `k` of message `i` is a stored photo (`/_blob/<id>`; `<id>` is the asset id), owed (`null`: not stored yet) or given up (`{e:"too_large"}`, `"unsupported_type"`, `"invalid_request"`, `"gave-up"` for an owed photo more than 300 messages behind the newest, or `"no-backfill"` for one on messages #0–#2, which no backfill scan can reach). `gifs` lists messages that hold a GIF. See the refresh skill's `references/photos.md`.
- `photos/index` `{byI,byK,gifs}` (pages before v1.22): the old single document. The page still reads it, merged under the blocks, and never writes it again.
- `meta/chat.photosOwed` (written by the page): `{n, fromI, toI, at}`, the photos still owed across the chat (`n` slots from message `fromI` to `toI`), or `null`. The next refresh backfills them (the refresh skill's `references/photos.md` › Backfill).
- `meta/chat.assetUsage` (written by the page with each import): `{files, bytes, maxFiles, maxBytes, at}`, the page's photo storage against its limits (on claude.ai 5,000 files and 1 GiB). The page warns from 80% of either.
- `refresh/lastImport` (written by the page on each paste): `at`, `src`, `ok`, `msg` (the toast), `dry`, `sha`, `count`, `lock`, `fresh`, `chunks`, `repaired`, and `state`: `uploading` (messages saved, photos storing; `beat` is its heartbeat, every 10 s) → `done` | `partial` (stopped, `stop` says why: `rate_limited`, `unavailable`, `timeout`, `lease`, `index`, `auth`, `quota`, `no_assets`); or `refused` (a check failed, nothing saved) or `failed`. With photos: `photos` `{total, todo, done, skipped, failed, bytes}`, `stored` `[{i,k,id}]` (uploaded by this paste), `owed` `[{i,k}]`, `gaveUp` `[{i,k,e}]`, `backfill` (true when it stored photos owed from before), `usage` (as `assetUsage`).
- `outbox/r<ms>` (one per queued reply; the refresh skill's `references/outbox.md`): `i`, `mid` (Messenger id; may be null: mark the row `failed`, "no Messenger id"), `to` (the sender as Messenger shows them, `f`), `snip` (their message with whitespace collapsed, cut to 120 characters ending "…", or "[photo]"), `text` (the reply, trimmed, line breaks kept), `state`, `queuedAt`; then `cancelledAt` or `dismissedAt` (page), `sentAt`, `sentMid`, `error` (Claude). `state`: `queued` → `cancelled` (page) | `sending` | `failed` (Claude); `sending` → `sent` | `failed` | `unconfirmed` (Claude); `failed`/`unconfirmed` → `dismissed` (page or Claude) | `sent` (Claude, when the user says it went out). `sent` always has both `sentAt` (a real time) and `sentMid` (null only when the user said it went out and it isn't in the saved messages).
- `backups/*`: copies of the summary saved by sessions before v1.17 (below, under Threading and summary documents).
- Written by the page: `qa/*` `{q,a,at,scope,toI}` (questions asked on the page's Ask tab), `views/*` (`kind:"view"`: a view the user built; `kind:"idea"`: a method idea left for Claude, `{prompt,at}`), `rangeSummaries/*` (summaries the page wrote for a past span). Written by Claude: `notes/*` `{title, when, at, intro?, table?:{cols,rows}, sections?:[{h,items:[{b?,t}]}], footer?}` (see What the page saves for Claude).
- `sent` on `qa/*` and `views/*` (optional; rows from older pages lack it): `{from, to, sumFrom, afterFrom}`, what Claude on the page read for that answer or view. Messages `#from` to `#to` word for word. When `sumFrom` is a number, the older messages from `#sumFrom` up to `#from` only as summary lines (a line per conversation, then per day); null: nothing older was summarized. When `afterFrom` is a number, the newer messages from `#afterFrom` on (after a date range with an end) only as one line per day; null or missing: none. An answer about summarized messages rests on summaries: check the messages before relying on its details.

## Threading and summary documents
A document holds at most 256 KiB, so since v1.17 threading and summary are collections. Only `catchup.py` writes them, through the manifest its build prints (the refresh skill's `references/writing-the-build.md`). The page and `catchup.py bootstrap` merge them into the single documents above.
- `threading/current`: `layout:2`, `block` (messages per block, 1000), `blocks` (the ids of its block documents), `to`, `note`, `builtAt`, and `convs` holding only conversations with no messages yet.
- `threading/b<start>-<hash>`: `start`, `convs:[{id,title}]` (conversations whose first message is in the block), `members:{conv:[i,…]}` and `links:{i:[parent,type]}` for the block's messages.
- `summary/current`: `layout:2`, `block`, `blocks`, `activeFrom`, `version`, `toI`, `generatedAt`, `fromI`, `mentionsNote`, and the conversations, `open`, `answered`, `mentions` and `deals` whose messages reach `activeFrom` (recent ones).
- `summary/b<start>-<hash>`: `start`, and the older items by the block of their messages: `convs` (by their last message), `open`, `answered`, `mentions`, `deals`, and `syn:{conv:[bullets]}` (a conversation's bullets from that block).
- Merging: links, members and bullets join in block order; `convs`, `open`, `answered` and `mentions` are `current`'s then the blocks', newest block first; `deals` the blocks' oldest first, then `current`'s.
- A block id carries a hash of its content: a changed block is written as a new document, and the old one is deleted once the write that stops naming it has landed. Blocks no `current` names, and any other documents in these collections, are never deleted.
- `summary.fromI` (pages from before v1.17): the first message the stored summary covers. Sessions before v1.17 dropped older conversations and moved it up; the page offers summaries of spans before it (`rangeSummaries`). A build keeps it as it is. `catchup.py restore-summary` moves it back to the backup's, or removes it when the summary then covers everything from #0 (no `fromI` means that).
- `backups/<name>-a`, `-b`, …: a copy of `summary/current` that a session before v1.17 saved before dropping items, split in parts to fit the cap: `{part:"a", of:2, what, savedAt, …}`. Part a holds the summary's fields (`version`, `fromI`, `toI`, `generatedAt`, `mentionsNote`, the lists) and the first conversations; later parts hold more of the lists (`convs`). Joined in part order they're the old single document. The page ignores this collection. `catchup.py restore-summary` reads it (the refresh skill's `references/restoring-a-summary.md`). Never delete it unless the user asks.
- A page set up before v1.17 has one `current` document each with no `layout`; it's still read, and the first build converts it.

## Versions
`meta/chat.versions` tells the page what to update: it can't see the helper (that lives in the Messenger tab) or fetch releases, so it compares these with its own `PAGE_VERSION` and `pageVersion`, and shows a short notice the user can dismiss.
```json
"versions": {"page": "2.7", "helper": "2.0", "refresh": "Nov 20, 9:04 AM", "browsers": {"Work Mac": {"helper": "2.0", "at": "2026-11-20T17:04:00Z"}}}
```
- `page`: `PAGE_VERSION` in this skill's `assets/page.html`.
- `helper`: `@version` in the refresh skill's `assets/helper.user.js`.
- `refresh`: exactly the string written to `lastRefresh` in the same update. A refresh that writes `lastRefresh` without it was run by a copy of the skill from before `versions`, and the page says so.
- `browsers`: one entry per Chrome, keyed by its name: the name `list_connected_browsers` gives the Chrome this run used (call it once if you haven't), or `"Chrome"` when it gives none (one key for every unnamed run; the page counts it only while it's the newest entry, since it may be any of the named ones). Write only this run's Chrome; `update` merges, so the others stay. The page ignores entries older than 30 days.
  - its `helper`: `data-mc-helper` as read on its Messenger tab at step 2, or `"none"` when no helper was installed and you injected it.
  - its `at`: when you read it (ISO time).
- **Write it with every `lastRefresh`** (step 7, the nothing-new path, troubleshooting's "nothing left to build"), in the same pinned `meta/chat` update: `{lastRefresh, coverage, versions:{page, helper, refresh, browsers:{"<name>":{helper, at}}}}`.
- **When you republish the page**, write `{pageVersion, versions:{page}}` together (the refresh skill's `references/updating-the-page.md`).
- Never write a higher `page` or `helper` than this skill ships to make a notice go away: the notice is the point.
- What the page shows: this tab is older than `pageVersion` (reload); `page` newer than the published page (a republish didn't land); `page` older than `pageVersion`, or `refresh` not equal to `lastRefresh` (an older copy of the skill ran: update the plugin); a Chrome's `helper` older than `helper`: below 1.5 it can't update itself (install once from the link), shown for every Chrome, worded with the day it was last used when that wasn't the last refresh; from 1.5 on (it should update itself, or check for updates now) only for the Chrome with the newest `at`, since one used before has most likely updated itself since. `"none"` and versions it can't read show nothing.

## What the page saves for Claude
The page promises the user that Claude sees these, so act on them. (Method ideas are checked after every refresh: the refresh skill's SKILL.md › Method ideas.)
- **Questions asked on the page** (`qa`): when the user refers to something they asked on the page, read `qa` (newest first) for context.
- **Notes from Claude** (`notes`): when the user asks how the page or a refresh works, or for an analysis worth keeping, answer in chat and also save it as `notes/<short-id>` (shape above). It appears under Views › Notes from Claude.
