# Database (ArtifactData on the user's page)

The full reference. The refresh skill's SKILL.md lists what a refresh needs.

- `meta/chat`: `kind:"messenger-catchup"`, `pageVersion`, `thread` (Messenger thread id), `chatUrl` (full chat URL), `threadName`, `shortName`, `ownerName`, `ownerAliases` (names others call them), `topic` (a few words on what the chat is about, such as "Pack buy/sell/trade"; setup asks, and a refresh fills it in once if it's missing), `outboxAuto`, `chatEvery` (the page's How often default for each chat, in minutes: below, under Several chats), `helperPost` (true lets the helper post approved replies; off unless the user asks Claude to turn it on: the refresh skill's `references/posting-with-helper.md`), `refreshPhrase`, `tz` (IANA), `firstCount` (the history size chosen at setup: how many messages the first capture reads), `firstDays` (an added chat only: how many days back its first capture reads, `firstCount` then capping it), `helper` ("installed" | "inject"), `chunkSize:82`, `lastI`, `lastMid`, `lastT`, `anchorMids` (newest 3 ids; reversed = STOPS), `caughtUpI`, `caughtUpAt`, `ownLastI`, `ownLastMid`, `markerMode` (`caught` | `own` | `time`), `markerSetAt`, `markerFrom`, `markerTo`, `lastRefresh` (when the refresh wrote it, in `tz`, as "Mon Nov 23, 9:04 AM", never an ISO time: `catchup.py versions TZ` prints it; below, under Versions), `coverage` (one short sentence the page shows after "Stored: N messages, #a to #b.", such as how far back the stored history goes; it ends with a period), `schedule` (`{mode, every, hours, tz}`, the user's choice, `hours` as `{from, to}`: `references/scheduling.md`), `replyCheck` (`{every, hours, tz, armId}`, scheduled reply checks, null or missing when none: `references/scheduling.md` › Reply checks), `ideasSeenAt`, `aliasesAskedAt` (when the user was asked which aliases count; the refresh skill's `references/people.md`). The page writes `lastI` … `ownLastMid` when it imports, and the marker fields when the user picks a catch-up start; Claude writes the rest.
- `meta/chat.versions` (Claude; with every `lastRefresh`, in the same update): what that refresh's skill ships and the helper each Chrome ran, so the page can say what to update (below, under Versions).
- `chunks/cNNNN` `{start, msgs:[...]}`: message fields `i` (number from 0), `t` ("Fri 8:41 AM"), `d` (date), `f` (sender as Messenger shows them: nickname or first name; the user = "You"), `fn` (full name from their avatar; helper 1.6+), `b` (text), `m` (Messenger id), `r` (replied-to name), `q` (quoted text), `pi`/`pmid`/`pq`/`perr` (reply parent), `p` (photo), `a` (link preview), `l` (links), `x` (reactions).
- `threading/*`: `current` plus the block documents it names; merged: `convs:[{id,title,members}]`, `links:{i:[parent,type]}` (r = Messenger link, rq = matched by quote, rg = photo reply best match, i = answers, c = same person continuing), `to`, `note`, `builtAt`.
- `summary/*`: the same; merged: `version:2`, `convs:[{id,tag,synopsis:[{t,refs}],outcome,key}]`, `open`, `answered`, `deals`, `mentions`, `toI`, `generatedAt` (optional `mentionsNote`, `fromI`).
- Deals (in `summary/*`): `{kind, tag, conv, text, refs, links?}`, and optionally `claims: [{i, who, n}]` (who claimed it: `i` a stored message, `who` that message's `f`, `n` how many, default 1; ordered by `i`, one per message) and `status` (`"sold"` or `"pending"`) always with `statusAt` (the message that closed it): the refresh skill's `references/writing-the-build.md` › Claims.
- On the page, a deal with `claims` shows "Claimed: Ben, Cy (2), Dee", each name opening its message (bad entries are skipped); a `status` shows "Sold" or "Pending" beside the deal (and in the card's header chip, in place of the tag), linking to `statusAt`, and a claim after `statusAt` reads "(after it was sold)" or "(after pending)". Other status values are ignored.
- `people/index` `{people:{"<full name>":{shown:[...],firstI,lastI}},scannedAt}`: written by the page from `fn`.
- `photos/*` (blocks `b<start>`; an old `index`, read only), `refresh/status` (lock and status line), `refresh/lastImport`, `refresh/importLock` (the page's import lease; never write it), `outbox/*` (replies and reactions queued on the page).
- `refresh/skipped` `{keys, why, at, run, last}`: the chats a run over every chat didn't reach, in the order left, `[]` when it reached all; `why`: `"time"` (a scheduled run's 15-minute limit; a run the user asked for has none) or `"stopped"` (a failure stopped it); `at` when it ended, `run` its `runAt`. `last` `{"<key>": ISO}`: when a run last refreshed each chat (that run's `runAt`; a chat that failed isn't recorded; a single "Refresh <name>" merges its own start in), which How often reads, and the page for each chat's next refresh. Only a run's end writes it (the refresh skill's `references/chats.md` › A run over every chat); the next run takes those chats right after the first chat, and the page says so on their lines. A scheduled run with no chat due writes only `refresh/status` `{state:"done",finishedAt,added:0,due:0}`, which the page shows.
- `refresh/schedule`: the schedule's live state, `armId` (the token in the current follow-up or recurring prompt), `nextAt`, `tool`, `lastRunAt`, `misses`, `problem` and `switchAskedAt` (shapes in `references/scheduling.md`). Only scheduling writes it. The page reads it, with `meta/chat.schedule` and `refresh/status`, to show the schedule under its status line: a summary ("Hourly, 7 AM–11 PM"), the next run from `nextAt` (left out when it falls outside the hours), a calm line when a chain has stopped (scheduling.md's "Chain stopped"; a chain with no `refresh/schedule` document has nothing armed), saying a refresh the user asks for offers the restart, or when `problem` is set alone, saying the next refresh the user asks for reports it, and one when a chain's `misses` is 2 or more.
- `photos/b<start>` (written only by the page, one per 500 messages: `b0`, `b500`, …): `{start, byK:{"<i>":{"<k>": "/_blob/<id>" | "/_blob/<id>#<n>" | null | {e}}}, pv, aids, h, tries, gifs:[i…]}`. Slot `k` of message `i` is a stored photo (`/_blob/<id>`; `<id>` is the asset id, the photo's own file; or `/_blob/<id>#<n>`, packed: item `n` of the day pack whose asset id is `<id>`, below), owed (`null`: not stored yet) or given up (`{e:"too_large"}`, `"unsupported_type"`, `"invalid_request"`, `"gave-up"` for an owed photo more than 300 messages behind the newest, `"no-backfill"` for one on messages #0–#2, which no backfill scan can reach, or `"no-fetch"` for one the helper couldn't get in 3 refresh runs). `aids` `{"<i>":{"<k>":"<attachment id>"}}` (helper 2.1 and later): Messenger's id for the photo in that slot; the page matches photos to slots by it, and by `k` for slots without one (everything stored before helper 2.1). `h` `{"<i>":{"<k>":"<12 hex>"}}`: the start of the SHA-256 of the photo's base64 as captured; a photo whose id changed is matched by it (and its slot takes the new id). `tries` `{"<i>":{"<k>":{n, run}}}`: how many refresh runs couldn't get that owed photo (`run` = `"run:"` plus the run id `full` was given, or for a capture without one the `meta/chat.lastRefresh` the last counted run saw). `gifs` lists messages that hold a GIF. `pv` `{"<i>":{"<k>":"/_blob/<id>#<n>"}}` (packed slots only): the photo's preview, item `n` of the preview pack `<id>`. See the refresh skill's `references/photos.md`.
- `photos/index` `{byI,byK,gifs}` (pages before v1.22): the old single document. The page still reads it, merged under the blocks, and never writes it again.
- `photos/packs` (written only by the page, R13): `{list:[{full, pv, day, part, n, bytes, pvBytes, at}], err, orphans, reclaim}`. One entry per pack: `full` and `pv` are the asset ids (bare, no `/_blob/`) of a day's full pack and its preview pack, `day` the chat's day (`YYYY-MM-DD`), `part` 1, 2, … when a day was split (about 12 MB of photos per part, or a photo stored later on a packed day), `n` how many photos it holds, `bytes` and `pvBytes` the two files' sizes, `at` when it was packed. `err` `{at, day, code, msg}`: the last try that failed (the originals were kept), or `null`. `orphans`: how many originals the page's delete was refused for that file (unused files; Cleanup finds them). `reclaim` (v1.31.3) `{n, at, checked, last, clean, swept}`: the page's sweep for originals left over after packing (pages up to v1.31.2 left them when a day's photos sat in more than one block; a delete that failed leaves some too): `n` how many it deleted, `at` when it last deleted one, `checked` how many `list` entries it has checked (`last`: the `full` of the last one, `null` for an entry with none), `clean` the `full` of packs made since that left nothing behind (not read again), `swept` the keys of its `photos/swept-<key>` documents. A full pack is a JSON file `{v:1, kind:"full", day, items:[{i, k, id, type, sha, b64}]}`: each photo's bytes exactly as stored (`b64`, base64), its original asset id, content type and SHA-256; a preview pack `{v:1, kind:"preview", day, items:[{i, k, type:"image/jpeg", w, h, b64}]}`, a JPEG at most 320 px on the long side per photo (`b64` null when the photo wouldn't decode), in the same order. See the refresh skill's `references/photos.md` › Storage.
- `photos/swept-<key>` (written only by the page, v1.31.3): what the leftover sweep found for one `photos/packs` entry whose pack didn't check out or whose originals it kept or couldn't delete; `<key>` is the entry's `full`, or `n<k>` for entry `k` when it has none. `{full, day, at, bad, lost, kept, own, refused}`: `bad` what was wrong with the pack (`missing`, `unreadable`, or the check that failed) or `null`; `lost` true when its photos can't be named from the pack (missing, unreadable, or an entry with no pack), and then **Cleanup deletes only duplicates** (the refresh skill's `references/photos.md` › Cleanup); `kept` the originals it keeps because the pack didn't pass (all its items; for a lost pack, those the old index names for the slots showing it) and `own` those whose bytes don't match their packed copy, both as `/_blob/<id>` strings, so they count as in use; `refused` the bare ids of originals whose delete was refused for that file (the page skips them; Cleanup may remove them).
- `refresh/packing` (written only by the page, v1.31.3): `{tab, at}` while an open copy of the page packs photos or sweeps leftover originals (it holds the import lease); written when the work starts, again every minute, and deleted when it stops. Never write it.
- `meta/chat.photoPack` (written by the page's Photo storage switch; off unless set): `{on, at}`. With `on` true, an open copy of the page that can store photos packs each finished day's photos (R13; the refresh skill's `references/photos.md` › Storage). Don't change it unless the user asks.
- `meta/chat.photosOwed` (written by the page): `{n, fromI, toI, at}`, the photos still owed across the chat (`n` slots from message `fromI` to `toI`), or `null`. The next refresh backfills them (the refresh skill's `references/photos.md` › Backfill).
- `meta/chat.assetUsage` (written by the page with each import): `{files, bytes, maxFiles, maxBytes, at}`, the page's photo storage against its limits (on claude.ai 5,000 files and 1 GiB). The page warns from 80% of either. With several chats, `byChat` `{"<key>": {files, bytes}}` is each chat's share, from its last import (the page names the biggest in the warning).
- `meta/chat.chats` (F1; written by the page, and once by the refresh's upgrade): the page's chats, below under Several chats. The page also writes `outboxAuto` and `chatEvery` from Settings ⚙ › Your chats.
- `refresh/lastImport` (written by the page on each paste): `at`, `src`, `ok`, `msg` (the toast), `dry`, `sha`, `count`, `lock`, `fresh`, `chunks`, `repaired`, and `state`: `uploading` (messages saved, photos storing; `beat` is its heartbeat, every 10 s) → `done` | `partial` (stopped, `stop` says why: `rate_limited`, `unavailable`, `timeout`, `lease`, `index`, `auth`, `quota`, `no_assets`); or `refused` (a check failed, nothing saved) or `failed`. With photos: `photos` `{total, todo, done, skipped, failed, bytes}`, `stored` `[{i,k,id}]` (uploaded by this paste), `owed` `[{i,k}]` (this capture's photos still owed, those the helper couldn't get included), `retry` `[{i,k,n}]` (owed photos the helper couldn't get, `n` runs so far), `skipOwed` `[{i,k}]` (photos the helper skipped that the page doesn't hold stored: owed again), `gaveUp` `[{i,k,e}]`, `backfill` (true when it stored photos owed from before), `usage` (as `assetUsage`).
- `outbox/r<ms>` (one per queued reply or reaction; the refresh skill's `references/outbox.md`): `kind` (`"react"` for a reaction, which has `emoji` instead of `text`, and `remove`: `true` takes the user's `emoji` off the message, F38; absent for a reply), `mentions` (a reply's tagged people: full names written in `text` as "@" plus the name; `[]` when none, and absent on rows from before 1.44), `i`, `mid` (Messenger id; may be null: mark the row `failed`, "no Messenger id"), `to` (the sender as Messenger shows them, `f`), `snip` (their message with whitespace collapsed, cut to 120 characters ending "…", or "[photo]"), `text` (the reply, trimmed, line breaks kept), `state`, `queuedAt`; then `cancelledAt` or `dismissedAt` (page), `sentAt`, `sentMid`, `error` (Claude). `state`: `queued` → `cancelled` (page) | `sending` | `failed` (Claude); `sending` → `sent` | `failed` | `unconfirmed` (Claude); `failed`/`unconfirmed` → `dismissed` (page or Claude) | `sent` (Claude, when the user says it went out). `sent` always has both `sentAt` (a real time) and `sentMid` (null only when the user said it went out and it isn't in the saved messages).
- `backups/*`: copies of the summary saved by sessions before v1.17 (below, under Threading and summary documents).
- Written by the page: `qa/*` `{q,a,at,scope,toI}` (questions asked on the page's Ask tab, which the user can remove there: the page deletes them; `scope` is `all` (always, since F32; older rows may say `window`), or `deeper` for a Look deeper answer), `views/*` (`kind:"view"`: a view the user built, `{title,intro,sections,prompt,at,made,toI,sent,auto}`, which the user can rename (`title`), rebuild (new content, `at`, `toI` and `sent`; `made` stays the first build's) and remove there (the page deletes it, so a view that's gone was removed on purpose: don't bring it back). With `auto` true ("Keep up to date") the page rebuilds the view itself while it's open, once an import has stored messages newer than its `toI`; Claude's refresh does nothing for it. `autoAt`: when the page last did; `autoAfter`: the `refresh/status.finishedAt` of the refresh that stored them, when one did; `autoErr` `{at,code,msg,toI}`: that update failed (`msg`: the error's message, for one without a code) and the old content stays; `autoBusy` `{tab,at}`: an open copy of the page is updating it. `kind:"idea"`: a method idea left for Claude, `{prompt,at}`), `rangeSummaries/*` (summaries the page wrote for a past span; a span too long for one request is read in parts and saved once, merged, when every part is done, with `parts` set to how many; from more than 4 parts, or a merge over 64 KB, it's condensed by one more request per batch of conversations: `condensed` is `true`, or `"partly"`/`false` when a batch fell back to trimmed bullets). Written by Claude: `notes/*` `{title, when, at, intro?, table?:{cols,rows}, sections?:[{h,items:[{b?,t}]}], footer?}` (see What the page saves for Claude).
- `daySummaries/d<YYYY-MM-DD>` (one per day; only `catchup.py` writes them, through a build's or the backfill's manifest; the page reads them all: the By day tab shows them, a card per day, newest first, each bullet's `refs` opening its messages, with a Copy for chat button; Ask's day lines and its `day_summaries` tool read them for older days): each day's fuller summary `{day, fromI, toI, n, at, full, fullToI, final, sections:[{h, bullets:[{t, refs}]}], open:[{t, refs}]}`, topic sections (a heading `h` each) with bullets citing messages of that day, then `open`, what was still open (the page's "Still open"). The day is the messages' `d`: the date in the browser's time zone when the helper read them (not necessarily `meta/chat.tz`), never going back (a message dated before the one before it counts in that one's day). `fromI`, `toI` and `n` are the day's stored messages it covers, `at` when it was written (ISO time). The day in progress is updated at each refresh that builds (`full` and `final` false: the page labels it in progress); once the day has ended it's rewritten from all its messages (`full`, through `fullToI`), and `final` when a later day was already stored then: never written again (a day rewritten before a later day was stored, with nothing stored for it after that, is marked final unchanged by the first build after one is). Messages still dated with a day that ended in `meta/chat.tz` come as updates (`full` and `fullToI` kept) until a later day is stored and it's rewritten as final. See the refresh skill's `references/day-summaries.md`.
- `digests/m<YYYY-MM>` (older pages; one per month; written by refreshes before v1.32.0, never since; the page reads them for days without a day summary, in By day and in Ask's day lines; never delete them): per-day digests `{month, days:{"<YYYY-MM-DD>": {bullets:[{t, refs}], fromI, toI, n, at, final}}}`, a few short bullets per finished day, each citing messages of that day, its day counted as for `daySummaries`. `fromI`, `toI` and `n` are the day's stored messages when it was written; `final`: a later day was already stored then.
- `reports/d<YYYY-MM-DD>` (one per day; only `catchup.py` writes them, through a build's manifest; the page's By day tab shows them: the day in progress lists its runs when it has no summary yet; a day with a summary, or an older digest, lists them collapsed under it): each refresh's report `{day, runs:[{at, fromI, toI, n, bullets:[{t, refs}]}], dropped?}`, runs in message order. A run is the part of one refresh's build on that day (the messages' `d`, as for `daySummaries`, so a refresh over midnight adds a run to both days): `at` when it was built (ISO time), `fromI`, `toI` and `n` its messages of that day, and up to 8 `bullets` of the report it gave in chat, each citing 1–10 of those messages (`refs`). `dropped` (when present): how many older runs left the document, which keeps a day's newest 40 within 128 KiB. A build with nothing new, and the first build, save none. Other fields are kept as they are. See the refresh skill's `references/reports.md`.
- `captions/b<start>` (one per 500 messages, like `photos/b<start>`: `b0`, `b500`, …; only `catchup.py` writes them, through a build's manifest or `catchup.py captions`; the page reads them): `{start, byK:{"<i>":{"<k>":"caption"}}}`, one line of at most 200 characters per stored photo, slot `k` of message `i` as in `photos/b<start>`, saying what the photo shows (the item, its brand or model when the photo or the messages around it name it, colors, details, readable text). The page searches them with the message's text and shows them on the photo. Merged slot by slot: a write never drops another caption in the block. See the refresh skill's `references/photos.md` › Looking.
- `sent` on `qa/*` and `views/*` (optional; rows from older pages lack it): `{from, to, sumFrom, afterFrom, digests}`, what Claude on the page read for that answer or view. Messages `#from` to `#to` word for word. When `sumFrom` is a number, the older messages from `#sumFrom` up to `#from` only as summary lines (a line per conversation, then per day); null: nothing older was summarized. When `afterFrom` is a number, the newer messages from `#afterFrom` on (after a date range with an end) only as one line per day; null or missing: none. `digests` (when present) `{n, from, to}`: `n` of those day lines carried that day's summary (`daySummaries/*`, or an older digest, `digests/*`), the first starting at `#from`, the last ending at `#to`. An answer about summarized messages rests on summaries: check the messages before relying on its details. **Searches (F32)**: where the page could hand Claude its search tools, `sent` also has `searches` `[{q, n, from?, to?, sender?}]` (each search Claude ran over every stored message and photo caption: its words, its filters, and `n` matches) and `reads` `[[a,b],…]` (the stretches it read word for word with them); details beyond `#from`–`#to` came from those. **A Look deeper answer** (`scope:"deeper"`, the second step after an answer that rested on summaries) has `sent: {from, to, stretches, wanted}` instead: only the runs in `stretches` (`[[a,b],…]`) were read word for word, nothing else from the chat apart from the earlier answer, so `#from` to `#to` are just their outer bounds, not all read; `wanted` is what Claude asked for, wider where a run was too long to send whole.

## Several chats
One page can hold several Messenger chats (F1). The owner adds, tags, pauses and removes them on the page; the refresh skill's `references/chats.md` says how a refresh handles them.
- `meta/chat.chats` `{"<key>": {name, tag, color, order, state, home?, url?, thread?, start?, photos?, auto?, every?, addedAt, reason?, deletedAt?}}`: one entry per chat, keyed by its fixed key (1-6 lowercase letters and digits, never reused). The first chat has `home:true`. `tag` (at most 8 characters, unique on the page) is how citations name it and the owner can rename it; `color` 1-4; `order` the chats' order after the first chat, which always comes first (Settings › Your chats moves them up or down; a chat without one comes last; runs, the title's chat list and All chats follow it); `state` `active` | `pending` (added, not read yet) | `paused` | `hidden` (removed, kept) | `deleted` (removed with its documents and photos); `url` and `thread` the Messenger link and thread id; `start` the history size to read first (300, 1000 or 3000); `photos` false: store none; `auto` true or false overrides `outboxAuto` for that chat (missing or null: the page default); `every` how often a scheduled run refreshes it, in minutes (0: every run; 120, 240 or 1440; never on the first chat, refreshed at every run), overriding `meta/chat.chatEvery` (missing or null: the page default; `chatEvery` missing or 0: every scheduled run; a run the user asks for refreshes every chat); `reason` why a pending chat couldn't be read. Adding a chat writes exactly one entry, `state:"pending"`, with `name`, `tag`, `color`, `order`, `url`, `thread`, `start`, `photos`, `addedAt` and `auto` only when chosen. A page without `chats` holds one chat (its first).
- The first chat keeps the page's own documents (`meta/chat`, `chunks/*`, `threading/*`, … `outbox/*`, `refresh/lastImport`). An added chat `KEY` has `meta/chat-KEY` (its own fields, plus `key`), `refresh/lastImport-KEY`, and collections `KEY_chunks`, `KEY_threading`, `KEY_summary`, `KEY_digests`, `KEY_reports`, `KEY_photos`, `KEY_captions`, `KEY_people`, `KEY_outbox` and `KEY_rangeSummaries`, shaped as the first chat's.
- Shared: `meta/chat`'s page-wide fields, `refresh/status`, `refresh/skipped`, `refresh/importLock`, `refresh/schedule`, `refresh/packing`, `notes/*`, and `qa/*` and `views/*`, whose rows carry `chat: KEY` for an added chat.

## Threading and summary documents
A document holds at most 256 KiB, so since v1.17 threading and summary are collections. Only `catchup.py` writes them, through the manifest its build prints (the refresh skill's `references/writing-the-build.md`). The page and `catchup.py bootstrap` merge them into the single documents above.
- `threading/current`: `layout:2`, `block` (messages per block, 1000), `blocks` (the ids of its block documents), `to`, `note`, `builtAt`, `rev` (the write's revision, shared with `summary/current`; a relink with no move, `bullets` or `dealEdit` sets `summaryRev` to summary's instead), and `convs` holding only conversations with no messages yet.
- `threading/b<start>-<hash>`: `start`, `convs:[{id,title}]` (conversations whose first message is in the block), `members:{conv:[i,…]}` and `links:{i:[parent,type]}` for the block's messages.
- `summary/current`: `layout:2`, `block`, `blocks`, `activeFrom`, `version`, `toI`, `generatedAt`, `rev`, `fromI`, `mentionsNote`, and the conversations, `open`, `answered`, `mentions` and `deals` whose messages reach `activeFrom` (recent ones).
- `summary/b<start>-<hash>`: `start`, and the older items by the block of their messages: `convs` (by their last message), `open`, `answered`, `mentions`, `deals`, and `syn:{conv:[bullets]}` (a conversation's bullets from that block).
- Merging: links, members and bullets join in block order; `convs`, `open`, `answered` and `mentions` are `current`'s then the blocks', newest block first; `deals` the blocks' oldest first, then `current`'s.
- A block id carries a hash of its content: a changed block is written as a new document, and the old one is deleted once the write that stops naming it has landed. Blocks no `current` names, and any other documents in these collections, are never deleted.
- `summary.fromI` (pages from before v1.17): the first message the stored summary covers. Sessions before v1.17 dropped older conversations and moved it up; the page offers summaries of spans before it (`rangeSummaries`). A build keeps it as it is. `catchup.py restore-summary` moves it back to the backup's, or removes it when the summary then covers everything from #0 (no `fromI` means that).
- `backups/<name>-a`, `-b`, …: a copy of `summary/current` that a session before v1.17 saved before dropping items, split in parts to fit the cap: `{part:"a", of:2, what, savedAt, …}`. Part a holds the summary's fields (`version`, `fromI`, `toI`, `generatedAt`, `mentionsNote`, the lists) and the first conversations; later parts hold more of the lists (`convs`). Joined in part order they're the old single document. The page ignores this collection. `catchup.py restore-summary` reads it (the refresh skill's `references/restoring-a-summary.md`). Never delete it unless the user asks.
- `catchup.py` moves a built message between conversations (`move`) by rewriting the blocks that hold it and the summary items that follow it; a conversation left empty is dropped. Nothing else is ever dropped.
- A page set up before v1.17 has one `current` document each with no `layout`; it's still read, and the first build converts it.

## Versions
`meta/chat.versions` tells the page what to update: it can't see the helper (that lives in the Messenger tab) or fetch releases, so it compares these with its own `PAGE_VERSION` and `pageVersion`, and shows a short notice the user can dismiss.
```json
"lastRefresh": "Fri Nov 20, 9:04 AM",
"versions": {"page": "2.7", "helper": "2.0", "refresh": "Fri Nov 20, 9:04 AM", "browsers": {"Work Mac": {"helper": "2.0", "at": "2026-11-20T17:04:00Z"}}}
```
- **Start from `python3 catchup.py versions TZ`** (`TZ` = `meta/chat.tz`, run as you write step 7's last batch).
