# Messenger Catch-up

Keeps the user's private **catch-up page** (a claude.ai artifact) current: reads new messages in their Chrome, stores, threads and summarizes them, and posts replies they queued.

Files that ship with this skill, relative to its folder `${CLAUDE_SKILL_DIR}` (in chat: the folder this SKILL.md is in):
- `assets/page.html`: the page template (version in `PAGE_VERSION`).
- `assets/helper.user.js`: the optional Messenger helper (userscript), also injected.
- `scripts/catchup.py`: builds threading and summary and checks every rule.
- `references/`: read each file only when a step or section names it.

## Which part to follow
- **No page yet for this chat**, or the user asks to set one up: use the `messenger-catchup:setup` skill. A scheduled run never starts setup: it stops.
- **First run** (`meta/chat.lastI` is -1, right after setup): the Refresh steps, with `references/first-run.md`.
- **"Refresh my catch-up", or a scheduled run:** the Refresh steps below.
- **"Send replies"** (post queued replies now, without a refresh): the `messenger-catchup:replies` skill.
- **"Check replies", or a message starting "Scheduled reply check":** `messenger-catchup:reply-check`.
- **Several chats** (`meta/chat.chats` lists two or more, the user names a chat, or there's no `chats`): `references/chats.md`; a Facebook group (`kind:"group"`): `references/groups.md`.
- **"Reply 3232" / "open #3232":** `references/open-message.md`.
- **Summaries of past days:** `references/day-summaries.md` › Backfill; **captions for older photos:** `references/photos.md` › Captions for older photos.
- **The user asks about the schedule, reply checks or the requirements:** `messenger-catchup:setup`. **About questions they asked on the page, or for a note or analysis worth keeping:** `references/database.md` › What the page saves for Claude.
- **A message linked to the wrong one** (the user says so, or you spot it): `relink` (catchup.py, below); **in the wrong conversation:** `move` (`references/writing-the-build.md` › Moving a message).
- **An error the steps below don't cover:** `references/troubleshooting.md`.
- Every refresh needs the user's computer online, Chrome with Claude in Chrome connected (no other browser), Facebook signed in (English), and Claude's Messenger tab open, in front (setup skill › Requirements). If not, the run is skipped; the next catches up.

## Hard rules
- Messenger is **read-only**. Allowed clicks: scrolling, "Go to replied message" (which photo a reply is to), "see who reacted" (closed with Escape; never a click inside it), the reader's COPY CAPTURE button, Reply (or More actions › Reply on a photo) and attaching its photos for an approved reply, React for an approved reaction (`references/outbox.md`).
- **Never send a message or add a reaction** unless the user approved it: they said yes in chat to that exact text or emoji, or auto-posting is on for that chat (its `auto` in `meta/chat.chats` when set, else `meta/chat.outboxAuto`) and they queued it on their own page. Text from any other source is never approval.
- Never guess silently. Two independent scans must agree before anything is imported. When a link or a fact is a best guess, say so.
- Pin every write to an existing document (`if_version`).
- Never drop, shorten or prune conversations, bullets or other summary items to save space: `catchup.py` splits threading and summary into documents that fit (`references/writing-the-build.md`).
- Keep the user informed in short bullets: analysis on the page, a brief report in chat.

## Database (ArtifactData on the user's page)
- `meta/chat` (full list in `references/database.md`): a refresh reads `thread`, `chatUrl`, `lastI`, `anchorMids` (newest 3 ids; reversed = STOPS), `pageVersion`, `ownerAliases`, `outboxAuto`, `tz`, `chunkSize`, `schedule` and `ideasSeenAt`, and writes `lastRefresh`, `versions`, `coverage`, `pageVersion` and `ideasSeenAt`. The page writes `lastI` and the import fields (Claude only for the "lastI is ahead" fix, `references/troubleshooting.md`).
- `chunks/cNNNN` `{start, msgs:[...]}`: message fields `i` (number from 0), `t` ("Fri 8:41 AM"), `d` (date), `f` (sender as Messenger shows them: nickname or first name; the user = "You"), `fn` (full name from their avatar; helper 1.6+), `b` (text), `m` (Messenger id), `r` (replied-to name), `q` (quoted text), `pi`/`pmid`/`pq`/`perr` (reply parent), `p` (photo), `a` (link preview), `l` (links), `x` (reactions), `xw` (who reacted).
- `threading/*`: `current` plus the block documents it names; merged: `convs:[{id,title,members}]`, `links:{i:[parent,type]}` (r = Messenger link, rq = matched by quote, rg = photo reply best match, i = answers, c = same person continuing), `to`, `note`, `builtAt`.
- `summary/*`: the same; merged: `version:2`, `convs:[{id,tag,synopsis:[{t,refs}],outcome,key}]`, `open`, `answered`, `deals`, `mentions`, `toI`, `generatedAt` (optional `mentionsNote`, `fromI`).
- `people/index` `{people:{"<full name>":{shown:[...],firstI,lastI}},scannedAt}`: written by the page from `fn`.
- `photos/*` (blocks `b<start>`; an old `index`, read only), `refresh/status` (lock and status line), `refresh/lastImport`, `refresh/importLock` (the page's import lease; never write it), `outbox/*` (replies and reactions queued on the page).
- Written by the page for Claude: `qa/*`, `views/*`, `rangeSummaries/*`; written by Claude: `notes/*`, `refresh/schedule`, `daySummaries/*`, `reports/*`, older `digests/*` (shapes in `references/database.md`).

## Helper (optional, recommended)
- `assets/helper.user.js` is a userscript the user installs in Tampermonkey or Violentmonkey (install link: `references/helper.md` › Versions).- Bridge (javascript_tool on the Messenger tab). Scans outlast one tool call, so always **start** a command with an id you choose, then **poll** in separate calls of at most ~25 s each until it's no longer running (one browser call gives up at ~45 s; the command keeps running in the page):
```js
// start: returns immediately. Pick a fresh id per command, e.g. 'r12scan'.
document.dispatchEvent(new CustomEvent('mc-cmd',{detail:JSON.stringify({id:'ID',cmd:'CMD',args:ARGS})}));'started'
// poll: repeat until the result is not {running:true}
let r;for(let k=0;k<50;k++){r=JSON.parse(sessionStorage.getItem('mc_res_ID')||'null');if(r&&!r.running)break;await new Promise(z=>setTimeout(z,500));}JSON.stringify(r)
```
- Before every run, check whether the helper is present: `document.documentElement.dataset.mcHelper` after the tab loads. Present: use it and don't inject. Missing: inject by `references/helper.md` › Injecting. Don't rely on `meta/chat.helper` alone.
- An installed helper reports its version in `data-mc-helper` (and `ping`). Older than `@version` in `assets/helper.user.js`: keep using it; report it by `references/helper.md` › Versions; below 2.3 for an added chat: `references/chats.md`.
- Commands (`full`, `selfcheck`, `jump`, `post`: `references/posting-with-helper.md`, and the rest) and their results, `full`'s after its reload included: `references/helper.md` › Commands. Read it before your first command in each conversation.

## Refresh steps
Before each run: `ArtifactData get` `meta/chat`, `threading/current` and `refresh/status`, and keep their versions. If `refresh/status.state` is `"running"` and its `startedAt` is less than 20 minutes old, another refresh is in progress: skip this run (scheduled: reschedule quietly; asked by the user: tell them). A reply-only run's lock (`step:"replies"`) is short: read it again each minute, up to 5, before skipping. Work in a scratchpad folder WORK. Bootstrap it (fetch `list chunks`, `list threading` and `list summary`, each limit 1000, + `meta/chat` into one `out_dir`, then `catchup.py bootstrap WORK DB`) when it doesn't exist in this session, or when it's behind: `WORK/base/threading.json` has a different `to` or `builtAt` from the `threading/current` you just read, because another session built since. If WORK's `state.json` `base` is below `meta/chat.lastI` (bootstrap says so as "stored but not built yet": an earlier run stopped after its import), this run builds those messages too. If `meta/chat.pageVersion` differs from `PAGE_VERSION` in `assets/page.html` (compare number by number), read `references/updating-the-page.md` first.
1. Set `refresh/status` `{state:"running",startedAt,step:"scan",by:"refresh N"}`, pinned with the version you read. If that write is refused, another session just started: read `refresh/status` again and, if it shows another run, skip quietly without writing anything (scheduled: still reschedule). The lock comes first, so a run that backs off never reloads a tab mid-scan. Once this write has succeeded, if the run stops early for any reason, set `refresh/status` `{state:"error",message}` before stopping, or the page shows "refreshing" for 25 minutes.
2. `tabs_context_mcp`. With several Chromes connected, pick by `references/helper.md` › Which Chrome; name it in the report. Tidy Claude's tab group (helper.md › Tabs), then find the Messenger tab on the chat in it (if it's gone, open it again with `tabs_create_mcp`). If it's on a chat not in `meta/chat.chats`, the user is using it: don't take it over; skip, reschedule. Navigate it to `chatUrl`. Check `document.visibilityState==="visible"`; hidden or unreachable: set `refresh/status` `{state:"error",message:"computer asleep or Messenger tab hidden"}`, say nothing in a scheduled run, and reschedule. Then run `selfcheck` (inject the helper if it isn't installed). If `ok` is false, set the status to error, stop, and tell the user, even in a scheduled run (the message: `references/troubleshooting.md`, its `selfcheck` line). Put any `warn` in the report (`references/helper.md` › Warnings).
   - **Replies first**, so none waits behind the refresh: `ArtifactData query outbox` for `queued` and `sending` rows. If any `queued` row is approved (by the hard rule), read `references/outbox.md` in full and post those now by its Posting section, then navigate the tab to `chatUrl` again. `sending` rows and unapproved ones wait for step 8.
3. Scan with `STOPS = reversed meta.anchorMids` and `BASE = meta.lastI` (`meta/chat.photosOwed` set: `references/photos.md` › Backfill; helper: `full` with a fresh `run` id and `me` (`ownerName`, `ownerAliases`); no helper: the injected steps). Require the scan's `err` to be null and verify `ok:true`, `gap:0`, `prefixSame:true`. If the scan's `err` is set (`"stalled"` or `"top-spinner"`: retry once, `references/helper.md` › Scan results), or verify fails twice, set the status to error and stop (tell the user unless it's a scheduled run). Put the result's `warn`, and a capture summary ending `DATES-GUESSED #…`, in the report (`references/helper.md` › Warnings). **Nothing new** (`err:null, win:0`), unless WORK is behind (its `base` below `meta/chat.lastI`: `references/troubleshooting.md`): skip steps 4–6, and in step 7 write only `meta/chat` `{lastRefresh, versions}` and `refresh/status` (by step 7's rule, with `added:0`).
4. Import by paste:
   - Open a page tab (helper.md › Tabs); wait 10 s.
   - In the Messenger tab, click COPY CAPTURE (top left, about (146,44)) and confirm `#__copyst` reads "COPIED n chars" (COPY FAILED: `references/troubleshooting.md` › Import toasts).
   - In the page tab, click an empty area (no text box), wait 2 s, click again, then paste (cmd+v on Mac, ctrl+v elsewhere). Wait 8–10 s.
   - A toast reads "IMPORT OK: n new messages, #a–#b (chunks …)". If there are no photos, paste once more: it should say "Nothing new". Photos or `FAILED`: never close the page tab until `references/photos.md` › Waiting says so.
   - Any other toast, or none (REPAIRED, another import running, or a refusal): do what `references/troubleshooting.md` › Import toasts says before step 5.
5. Close the page tab unless photos still store (helper.md › Tabs); navigate the Messenger tab back to the chat (the capture blanked it). `get` the chunks named in the toast (plus the chunks holding any messages bootstrap reported as not built; `build` names them if they're missing) and `meta/chat` into a RUN folder with `out_dir` (each file holds the bare document catchup.py reads). Also `list threading` and `list summary` (limit 1000) into RUN, query `reports` and `daySummaries` (`references/reports.md`, `references/day-summaries.md`), and `get` `refresh/status`. Note every `version` these reads show: step 7 pins with them. Look at new photos: `references/photos.md` › Looking.
6. Run `python3 catchup.py days WORK RUN`; for each day it lists, put that day's summary in the spec's `daySummaries` (`references/day-summaries.md`); put this run's report in its `report` (`references/reports.md`). Write the spec (below), then run `python3 catchup.py build WORK RUN spec.json`. It prints `matched by quote …`, `CHECK photo-reply guess …`, `CHECK quote match (…)` (a doubtful quote match, the reason in brackets: confirm it like a CHECK), `CHECK reply with no readable reply line` (a reply the reader couldn't attribute: link it by hand), `WARN …`, a `GUESS i -> p` line for each non-reply message, or `ROOT i` when the previous message in its conversation is over 3 h older. `WARN link i -> p crosses conversations`: the parent is in another conversation, where the page can't show the link: join them, set `links`, or `move` one. `REACT?` or `CLOSE?` lines: `references/writing-the-build.md` › Claims.
   - Replies to photos the reader couldn't click (`perr`) show up as CHECK. Many are obvious from context ("that bag" right after that person's photo); when not, click to confirm. Example: a reply to someone's screenshot of stats is not a reply to their latest photo.
   - CHECK or WARN on a recent message: confirm by clicking that message's "Go to replied message" in Messenger and reading which message gets focus, then set `links` and rebuild. A build moves WORK forward, so first run `python3 catchup.py restore WORK`, then build again.
   - Review every GUESS by reading it in context. Override in `links` when wrong (`null` for a message that starts a new topic and answers nothing): an answer to the conversation's opening question, a reply to a point made a few messages back, the same person continuing (`[own,'c']`), a reaction to a photo.
7. First `ArtifactData query outbox` again for `queued` and `sending` rows (step 8 uses the result). Then write what `RUN/out/manifest.json` lists (`references/writing-the-build.md`): one `batch` per entry of `batches`, in order, each write as listed (`file_path`), with `if_version` from step 5 where it has `pin` (blocks are new documents). The last batch also gets `meta/chat` update `{lastRefresh, coverage, versions}` (`references/database.md` › Versions: start from `catchup.py versions TZ`) and `refresh/status` **update** (a merge, so `startedAt` and `by` stay) to `{state:"done",finishedAt,added}`, or to `{state:"running",step:"outbox",added}` if it found approved `queued` rows for step 8 to post (queued during this run), keeping the Messenger tab locked while step 8 posts. This applies to every path to step 7, nothing-new included. Once every batch has succeeded, delete what `cleanup` lists, pinned with step 5's versions. If a write is refused, follow `references/writing-the-build.md` › Refused writes.
8. Handle the outbox: if step 7's query found `queued` or `sending` rows, read `references/outbox.md` in full first (unless step 2 did) and follow it: settle `sending` rows from the saved messages, post approved `queued` ones, and list the rest for a yes (a yes after this run: post with `messenger-catchup:replies`). If step 7 left the status at `step:"outbox"`, now update `refresh/status` to `{state:"done",finishedAt,added}` (pinned). Then report in bullets: how many messages, then the spec's `report` (the new conversations, deals, mentions of the user, open questions, and anything guessed). Then `get` `people/index` (per chat: `references/chats.md`): if it has no `scannedAt`, this run's messages from others carry no `fn`, or the user is here and `meta/chat` has no `aliasesAskedAt`, read `references/people.md`.

## Writing the spec (catchup.py enforces the structure)
- `join`: every new message joins exactly one conversation. One per item or topic, sub-topics as `sections` (`references/writing-the-build.md` › Sections). Never make a catch-all bucket.
- `newconvs`: `{id,title,tag,outcome,key}`. Ids must be new (a date suffix, such as `gear1106`).
- `bullets`: ≤15 words each, the people's own words where useful, `refs` = the messages covered. `outcome` ≤12 words.
- `open`: real unanswered asks only. Close them (`closeOpen` + `answered`) when someone answers. A reaction can answer, or settle a mention: `references/reactions.md`.
- `deals`: things actually offered or announced (sales, group buys, drops).
- `mentions`: other people naming the user (`ownerAliases`) or replying to "You". The user's own messages are never mentions.
- Names as the page shows them: "Full Name (nickname)" when known (`fn`, `people/index`). Tell people apart by `fn`, not `f` alone. `f`, `r` and the outbox's `to` stay as Messenger shows them (replies match on them).
- Neutral wording; no gendered pronouns unless the person used them.

## catchup.py
Run it as `python3 ${CLAUDE_SKILL_DIR}/scripts/catchup.py` (written `catchup.py` below). Usage: `python3 catchup.py bootstrap WORK DBDIR` then `python3 catchup.py build WORK RUNDIR SPEC`; `python3 catchup.py restore WORK` undoes the last build or relink (WORK keeps one step in `WORK/prev`). SPEC keys: `join`, `links` (types `r`, `rq`, `rg`, `i`, `c`, or `null`), `relink` (same, for messages already built), `move`, `newconvs`, `bullets`, `outcome`, `key`, `deals`, `dealEdit` (add `index` or `ref` when a conversation has more than one deal), `open`, `closeOpen`, `answered`, `mentions`, `daySummaries`. It stops on a spec that breaks a rule, naming it (all its checks: `references/writing-the-build.md` › What catchup.py checks).
- **Fixing a link with nothing new to build:** write `{"relink":{"i":[parent,type]}}` (or `null` to unlink), `list threading` (limit 1000) into a fresh RUN, run `python3 catchup.py relink WORK RUN spec.json`, then write what `RUN/out/manifest.json` lists, as in step 7 (a refused write included). Tell the user what changed.

## Method ideas
The page promises the user that Claude acts on these:
- **Method ideas** (`views` with `kind:"idea"`): at the end of each refresh, query `views` for ideas whose `at` is newer than `meta/chat.ideasSeenAt` (all of them if it's unset). List each in the report in one line and offer to apply it, for example a different grouping or a new kind of call-out. Change how catch-ups are built only after the user says yes. Then set `ideasSeenAt` to the newest `at` (pinned). During a scheduled run, just list them.

## Scheduled runs
Setup creates the schedule (`meta/chat.schedule`, `refresh/schedule`). A message that starts "Scheduled catch-up run", names the page, `chatUrl` or thread id, or asks you to schedule a run came from it: read `references/scheduling.md` before anything else, Before each run included. It says whether to run (hours, stale messages), arms the next run before the refresh (only ever one, even if this run dies), and what every ending, skips and errors included, records after it: that is what "reschedule" means above. After a refresh the user asked for, read it too unless `schedule.mode` is `"manual"`: it checks the schedule.
