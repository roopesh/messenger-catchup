# Architecture

How the pieces fit together, as of Nov 11, 2026 (v1.17.0: threading and summary stored as block documents). Line numbers date from Nov 6 (Phase 8) and have drifted; search by name.

Related docs: [STATUS.md](STATUS.md) (start here) · [BACKLOG.md](BACKLOG.md) · [DECISIONS.md](DECISIONS.md) · [LEARNINGS.md](LEARNINGS.md)

## The four parts

They ship as a plugin (v1.15.0): the repo is a marketplace (`.claude-plugin/marketplace.json`, name `rando-tools`) listing the plugin in `plugin/` (`plugin/.claude-plugin/plugin.json`, name `messenger-catchup`, version = `VERSION`). It has two skills (v1.16.0): `setup` (`plugin/skills/setup/`, once per chat: requirements, the page, the questions, the schedule) and `refresh` (`plugin/skills/refresh/`, every run). The paths below are inside the refresh skill. Setup hands the first capture to refresh, which reads `references/first-run.md` when `meta/chat.lastI` is -1. A skill can only count on its own folder, so setup carries copies of the page and `references/database.md`, generated by `tools/sync.py` and checked by a test. Skill files refer to each other relative to their folder (`${CLAUDE_SKILL_DIR}`).

| Part | Runs where | Job |
|---|---|---|
| `SKILL.md` | Claude (cloud) | The procedure for every run: hard rules, core database fields, the helper bridge, the refresh, spec writing, method ideas, the scheduling chain. Claude carries out every step; nothing else orchestrates. |
| `references/*.md` | Claude, on demand | `first-run.md` (the first capture after setup), `updating-the-page.md`, `outbox.md` (posting queued replies), `open-message.md`, `database.md` (full reference, `qa`/`notes`), `troubleshooting.md`. `SKILL.md` says when to read each (v1.9.0, BACKLOG C7). |
| `assets/helper.user.js` | The user's Messenger tab (userscript, or injected by Claude) | Scroll back and read messages (scan), confirm them by ID (verify), build the capture JSON (capture), jump links. |
| `assets/page.html` | claude.ai artifact, in the user's browser | The catch-up page. Also the **importer**: checks a pasted capture and writes it to the database. |
| `scripts/catchup.py` | Claude's code sandbox | Builds threading and summary from Claude's spec, asserts the rules, and writes the documents that changed plus a manifest of what to write (block layout, v1.17.0). |

There is no server. The artifact database (ArtifactData) is the only store, and both Claude and the page read and write it.

## One refresh, end to end

```
 Claude (cloud)                 Messenger tab (user's Chrome)            Catch-up page (artifact)
 ──────────────                 ─────────────────────────────            ────────────────────────
 get meta/chat ───────────────────────────────────────────────────────────▶ (db)
 set refresh/status running
 mc-cmd full{stops,base,run} ─▶ mcScan: scroll up until a STOP id is seen
                                quote-match text replies, click photo replies
                                save window to sessionStorage.__mcsave
                                reload ─▶ resumePipe ─▶ mcVerify (ID-only pass,
                                          fast then slow) ─▶ mcCapture
                                page body replaced by COPY CAPTURE button
 poll mc_result (≤25 s calls) ◀─ {stage:'captured', run}
 click COPY CAPTURE ─────────▶ clipboard ─────────────────────────────────▶ paste anywhere
                                                                           importCore: checksum, numbering,
                                                                           overlap, fields; write chunks,
                                                                           read back, update meta/chat,
                                                                           upload photos, photos/index
 read refresh/lastImport ◀──────────────────────────────────────────────── refresh/lastImport
 get touched chunks + meta/chat, list threading + summary into RUN/
 write spec.json; catchup.py build WORK RUN spec.json  ->  RUN/out/manifest.json
 batch write per manifest: new blocks (unpinned), threading/current +
   summary/current (if_version), meta/chat, refresh/status; then cleanup
 handle outbox (jump{mid,reply} + insertText + Enter)
```

Why the clipboard: the page can't receive messages from the Messenger tab, can't read the clipboard itself, and can't fetch Facebook images. A user-style paste is the one channel that works (LEARNINGS.md › claude.ai artifacts).

## Helper (`assets/helper.user.js`)

All code sits inside one IIFE guarded by `window.__mcHelper` / `data-mc-helper` (line 11), so a userscript plus an injected copy never run twice.

| Function | Line | What it does |
|---|---|---|
| `mcDate(label, now)` | 18 | A message's date from its time label (time only, Yesterday, weekday or 3+ letter prefix, month name or prefix with optional year; a year-less future date means last year). `null` when unreadable; the capture then borrows the previous message's date and lists it as `DATES-GUESSED`. Exposed as `window.__mcDate` for tests. |
| `mcScan(STOPS, FIRST)` | 28 | Waits for `[role="log"]`, scrolls the inner scroller up 0.6 screen every 500 ms, merges each batch of `[data-message-id]` into `R.order` (a gap counter rises if a batch shares no id with what's known). Stops 3 steps after the anchor is seen: a STOP id, or for a first run the message before the newest `count`, or `__top__` when the chat is shorter. Then matches text replies by quote (`how:'q'`) and clicks "Go to replied message" only for photo/attachment replies. Saves `{win, info, parents, anchor}` to `sessionStorage.__mcsave`. Link clicks are blocked while a scan runs (one listener, registered at load). |
| `mcVerify()` | 79 | After a reload: ID-only pass (fast 0.6/500 ms, then slow 0.35/900 ms if needed). OK when `gap==0` and the new window starts with exactly the scanned window (`prefixSame`). `extra` = messages that arrived since the scan; they are *not* captured (next run gets them). |
| `mcCapture(BASE)` | 87 | Turns each saved DOM record into a message object (fields below), numbering from `BASE+1`. Parses sender, body, quote, reactions, links (strips tracking params), attachment title, date (`dOf`) and time. Fetches photos as base64. Builds the capture, then **replaces the page body** with the COPY CAPTURE button (`#__copy`, status `#__copyst`). |
| `jump()` | 124 | Handles `#mcjump=<mid>[&noreply]`: scrolls to bottom, then up until the message exists, outlines it, hovers it and clicks "Reply to this message". Shows status in `#mcjump-tip`. |
| `avatar(e)` | — | The sender's full name: alt text of the ~28 px square image at the message's left edge (v1.6). |
| `mcSelfcheck()` | — | `selfcheck` (v1.8): confirms the chat log, message ids, scroller, `At <time>, <name>: ` labels, reply links and "Original message:" quotes are present (`missing`), and that avatars and date labels read (`warn`). Run at refresh step 2. |
| `mcPeople(a)` | — | `people{count,maxMs}` (v1.7): read-only scroll back collecting `[shown, full, n]` for the one-time name backfill. |
| `probe(anchor)` | 151 | Quick check: visibility, loaded count, whether the anchor is on screen. |
| `full(a)` / `resumePipe()` | 156 / 158 | Scan → `mc_pipe` in sessionStorage → reload → (on load) verify → capture → `mc_result`. `full` clears `mc_result` first; results carry `run`. |
| Bridge | 167 | `document` event `mc-cmd` with `{id, cmd, args}`; result in `sessionStorage['mc_res_'+id]` (`{running:true}` until done). |

Browser state it uses: `sessionStorage` keys `__mcsave`, `mc_pipe`, `mc_result`, `mc_res_<id>`; globals `__rf`, `__v`, `__capText`, `__mcHelper`, `__mcJumping`.

### Capture format (`kind: "mc-capture"`)
```
{kind, base, anchor, count, sha, msgs:[...], gifs:[i...], photos:[{i,k,type,b64}], phsha}
sha   = SHA-256 hex of JSON.stringify(msgs)
phsha = SHA-256 hex of JSON.stringify(photos)
```
Each message may carry `fn` (helper 1.6+): the sender's full name, read from the alt text of their avatar (the ~28 px square image at the message's left edge). `f` stays the name Messenger prints (a nickname or the first name), which is what reply lines and the outbox match on. The page keeps `fn` (a string of 80 characters or fewer, never on "You") and folds it into `people/index`.

The page accepts only `mc-capture` (the old `cc-capture` kind was dropped on Nov 6) and two optional flags: `dry` (check everything, write nothing) and `lab` (store photos but don't link them).

### Copies of the helper (keep in sync)
The helper exists **twice**: the file itself, and its `jump()` body as a URL-encoded bookmarklet in the page's `#jump-bm` (`%` → `%25`). `tools/sync-helper.py` regenerates the bookmarklet from the file, and `npm test` fails (`--check`) when they drift. Until v1.8.0 the page also embedded an HTML-escaped copy of the whole userscript (`#jump-us`, "Copy userscript"). Now the page links to `releases/latest/download/helper.user.js`, which `tools/release.sh` attaches to every release, and the userscript's `@updateURL`/`@downloadURL` point there so it updates itself (BACKLOG F8). The version string appears four times in the helper (header, `__mcHelper`, `data-mc-helper`, `ping`). See BACKLOG C2.

## Page (`assets/page.html`)

- **Capabilities:** `db`, `assets` (photo uploads), `sample` (Ask Claude, Views, range summaries). Published by Claude with `capabilities: {"db":{}, "assets":{}, "sample":{}}`.
- **Config:** everything chat-specific comes from `meta/chat` via `applyCfg()` (line 500). `PAGE_VERSION` is at line 493.
- **Boot:** subscribes with `onSnapshot` to `meta/chat`, the `summary` collection, `chunks`, `qa`, `views`, `notes`, `outbox`, `refresh/status`, `rangeSummaries`, `people/index`, `photos/index` and the `threading` collection. Every chunk change rebuilds the full in-memory message list (`rebuild`). `mergeThreading` and `mergeSummary` turn each collection back into the single objects `S.threading` and `S.summary` that every view reads (old single documents are used as they are), so nothing else knows about blocks.
- **Tabs:** Summary · Ask Claude · Messages · Views, plus a fixed "Refreshing" section with helper setup and the manual Import box.

### Catch-up window (`winRange`, line 546)
`meta/chat.markerMode` picks the start point:
- `caught`: after `caughtUpI` ("Mark caught up" button sets it to the newest message).
- `own`: after the user's last message (`ownLastI`, kept current by the importer).
- `time`: `markerFrom` / optional `markerTo` (local `YYYY-MM-DDTHH:MM`), compared against each message's `ts` built from `d` + `t`.
Everything (summary cards, counts, mentions, open questions) filters to the window. The date inputs never rebuild while focused and save 1.5 s after the last keystroke, on Enter, or on blur (EXPERIMENTS.md §6).

### Summary (v3 cards, `renderSummaryV2`, line 757)
"Your replies" (outbox) → "Needs you" (mentions) → filter chips (All / Open / Deals / Answered) → one card per conversation (`convCard`, line 724) with open/deal/answered call-outs, outcome, bullets that open the thread at their messages, and a lazily built thread → collapsed "Links shared".

### Threading display (`convTree`, line 703)
One tree for cards and the Messages tab. `r`/`rq`/`rg`/`i` links nest under their parent; `c` (same person continuing) sits right after the earlier message at the same level; depth is capped at 3. **A link only nests when its parent is in the same conversation**; otherwise the message shows as a root.

### Importer (`importCore`, line 957)
The page's database has **no version-checked writes and no transactions** (runtime contract: last-writer-wins). So since v1.2.0 the importer protects itself in three ways:
- **Import lease:** before writing, it takes a 2-minute cooperative lease on `refresh/importLock` (`acquire`, holder = a per-tab id), so two open copies of the page can't import at once. Renewing it from the same tab is fine. If the runtime has no `acquire`, it imports without a lease (`lock:"unsupported"` in `refresh/lastImport`).
- **Fresh reads:** `meta/chat` and the newest chunk (`orderBy("start","desc").limit(1)`) are read from the store, not from the page's snapshots, which can lag or come from cache.
- **Repair:** if the newest chunk ends *after* `meta/chat.lastI`, an earlier import saved and read back its messages but stopped before updating `meta/chat`. The importer counts them in (`lastI`, `lastMid`, `lastT`, `anchorMids`, `ownLastI`) and prefixes its message with `REPAIRED: #a–#b (chunk …)`. If the chunk ends *before* `lastI`, it refuses and says what to set.

Checks, in order: JSON → `kind` → message checksum → photo checksum → lease → stored state (consecutive newest chunk, chunk end vs `lastI`) → consecutive numbers → no gap after `lastI` → overlapping messages match the stored ids → required fields (`f`, `m`, `t`, `d` as a date) → photo shape. A first import must start at `#0`. **Nothing, not even a repair, is written until every check passes.** It then:
1. writes the repair, if any
2. appends to the newest chunk, rolling to a new `cNNNN` at `chunkSize` (82)
3. **reads each chunk back and compares**
4. updates `meta/chat` (`lastI`, `lastMid`, `lastT`, `anchorMids`, `ownLastI`, `ownLastMid`)
5. uploads photos and merges `photos/index`

Every outcome goes to `refresh/lastImport`. A dry run reports what it would do, including "Would repair", and writes nothing.

### Outbox
"Reply here" writes `outbox/r<timestamp>` `{i, mid, to, snip, text, state:"queued", queuedAt}`; Cancel sets `state:"cancelled"`. Claude moves rows to `sending` → `sent` (`sentAt`, `sentMid`), `failed` (`error`) or `unconfirmed` (sent but never found in the chat; never reposted). Failed and unconfirmed rows have a Dismiss button (`state:"dismissed"`), and they stay listed until resolved.

### Range summaries (pages carried over from the original chat)
- `renderRangeSummary` / `writeRangeSummary`: when the catch-up window is set by date (`markerMode:"time"`) and starts before the summary's `fromI`, the page offers to have Claude (through the page's `sample`) summarize exactly that span, and saves it in `rangeSummaries/r<lo>_<hi>`.
- `fromI` is the first message the stored summary covers. Only pages from before v1.17.0 have it: the original page's summary started there (checked live Nov 7: `fromI` 1654, two saved spans), and by Nov 11 refresh sessions had moved it to 2797 while dropping older conversations to stay under the document cap (BACKLOG B43). `catchup.py` keeps it and never moves it; nothing is dropped any more. New pages never show range summaries.
- The removed legacy code (C1, v1.7.3): the in-page Refresh trigger (`REFRESH_TASK`, `startRefresh`, `fire_trigger`), the summary v1 renderer, and `dayMap`/`meta.dates`. Every stored message carries `d`; checked live: 3,992 of 3,992.

## Build tool (`scripts/catchup.py`)

- `bootstrap WORK DBDIR`: loads all chunks, asserts numbering has no gaps and `meta.lastI` matches, merges the `threading` and `summary` collections (either layout, below), writes `WORK/all.json`, `WORK/base/{threading,summary}.json` (the merged state), `WORK/base/layout.json` (which documents exist, `activeFrom`), `WORK/state.json` (`base`, `stops`, `tz`). WORK's base is the last *built* message (threading's `to`). Messages stored after it (from a run that stopped after its import) are built by the next RUN, and `build` names the chunks to fetch if they're missing.
- `build WORK RUN SPEC`: loads new messages from `RUN/chunks` (must be exactly `base+1…`), applies the spec, picks default links, runs the asserts, splits the state into block documents and checks that they merge back into it and that none is over 240 KiB, writes the documents that changed to `RUN/out/{threading,summary}/` with `RUN/out/manifest.json` (and the merged state in `RUN/out/merged/`, for checking), copies the WORK it started from to `WORK/prev/`, then **advances WORK**. If step 5 listed the collections into RUN, it first checks that the stored `current` documents are still the ones WORK was built from. Building the same RUN again fails with "RUN already built into WORK … run: catchup.py restore WORK".
- `relink WORK OUT SPEC` (v1.12.0): corrects links on messages an earlier build threaded, when there's nothing new to build. SPEC holds only `relink` `{i:[parent,type]|null}`, and the same key works inside a build spec. It writes `OUT/manifest.json` and the threading documents it names (no cleanup; the next build's does it), then advances WORK's threading, keeping `WORK/prev`.
- `restore WORK`: puts `WORK/prev/` back and removes it (one step of undo). Used after a refused DB write or to rebuild with a corrected spec. `bootstrap` clears any stale `WORK/prev/`.
- Default link for each new message, in order: Messenger parent in window (`pi` → `r`, or `rq` if quote-matched in the browser) → Messenger parent by id from history (`pmid`) → quote match on stored history (`resolve`: same author, 300-message window, latest wins; the first 20 normalized chars as a prefix → `rq`; a quote under 12 chars must equal the whole text, and a long quote found only inside a text is accepted, both printed as `CHECK quote match (…)`; empty or "Photo"-type quote → author's latest media → `rg` + CHECK) → previous member of its conversation if ≤3 h older (`c` same author, else `i`, printed as GUESS) → none (ROOT).
- Asserts: WORK isn't behind the database; conv ids new; every new message joined exactly once; every message from the lowest member up is in exactly one conversation; links point backward; bullets ≤15 words; outcomes ≤12; bullet/key/open/answered refs belong to their conversation; deals name a real conversation; `meta/chat` was updated by the import; every output document is at most 240 KiB ("… would be N bytes, over the 245760-byte limit … Never drop or shorten …", nothing written).
- Timestamps (`builtAt`, `generatedAt`) come from the system clock in `meta.tz` (falls back to America/Los_Angeles).

### Threading and summary layout (v1.17.0, BACKLOG B43)
A database document holds at most 256 KiB, and threading (about 25 bytes a message) and summary (about 50) grow with the chat, so each is a collection. Full field list: the refresh skill's `references/database.md`.
- `threading/current` `{layout:2, block:1000, blocks:[ids], to, note, builtAt, convs:[conversations with no messages yet]}`; `threading/b<start>-<hash>` `{start, convs:[{id,title}] starting in the block, members:{conv:[i…]}, links:{i:[p,t]}}`.
- `summary/current` `{layout:2, block, blocks, activeFrom, version, toI, generatedAt, fromI?, mentionsNote?, convs, open, answered, mentions, deals}` holds what's at or after `activeFrom` (the start of the block before the newest, moved up a block while `current` is over 96 KiB; it never moves back). `summary/b<start>-<hash>` holds older items by the block of their messages: `convs` (by last message), `open` (ask), `answered` (newest of ask and refs), `mentions` (newest ref), `deals` (first ref), and `syn:{conv:[bullets]}`, a conversation's bullets by the block they cite.
- Each list's key is a running maximum from its oldest end, so every document holds one unbroken run of each list, and merging (`catchup.merge_threading`/`merge_summary`, the page's `mergeThreading`/`mergeSummary`) gives back the exact single documents, order included. `catchup.py` asserts that round trip on every build.
- Ids carry a hash of the content. A changed block is a new document; `current` switches to it in the same batch, and the old one is deleted afterwards (`cleanup`). An interrupted run leaves `current` naming intact blocks, and a retry finds the blocks it already created. Only documents that look like blocks (`b000000-0123abcd`) are ever deleted.
- The old layout (one `current` each, no `layout`) is read by the page and by bootstrap; the first build converts it. Setup still seeds the old empty documents.
- Measured: the largest document stays at most 85 KB from 6,400 to 50,000 messages (EXPERIMENTS.md §13).

### Message fields
`i` number from 0 · `t` "Fri 8:41 AM" · `d` "YYYY-MM-DD" · `f` sender ("You" = owner) · `b` text · `m` Messenger id · `r` replied-to name · `q` quoted text (≤160) · `pi` parent number in the store · `pq` 1 when the parent was quote-matched · `pmid` / `pl` parent id and label when outside the capture window · `perr` why a photo-reply click failed (`notfound`, `nobtn`, `nofocus`) · `p` attachment id of a photo · `a` link-preview / attachment title (≤220) · `l` outside links · `x` reactions. The page adds `ts` in memory.

### Link types
`r` Messenger's own reply link · `rq` reply matched by quote · `rg` photo reply, best match · `i` answers (Claude's judgment) · `c` same person continuing · `null` in a spec = deliberately no link.
