## The four parts

They ship as a plugin (v1.15.0): the repo is a marketplace (`.claude-plugin/marketplace.json`, name `rando-tools`) listing the plugin in `plugin/` (`plugin/.claude-plugin/plugin.json`, name `messenger-catchup`, version = `VERSION`). It has four skills: `setup` (`plugin/skills/setup/`, once per page: requirements, the page, the questions, the schedule, reply-check scheduling), `refresh` (`plugin/skills/refresh/`, every run; it posts approved queued replies before its scan, then refreshes every chat and group on the page), `replies` (`plugin/skills/replies/`, "send replies": posts the approved queued replies and stops, with no scan, import or build, so a reply goes out within a minute or two at a fraction of a refresh's cost) and `reply-check` (`plugin/skills/reply-check/`, "check replies": a `SKILL.md` of about 1 KB with no files of its own; one read of `meta/chat` plus one outbox query per active chat, handing a waiting reply to `replies`; cheap enough to schedule every few minutes, v1.34.0, v1.37.0). The paths below are inside the refresh skill. Setup hands the first capture to refresh, which reads `references/first-run.md` when `meta/chat.lastI` is -1. A skill can only count on its own folder, so setup carries copies of the page, `references/database.md` and `references/scheduling.md`, and replies copies of `references/outbox.md`, `references/posting-with-helper.md`, `references/helper.md`, `references/database.md` and `assets/helper.user.js`, all generated by `tools/sync.py` and checked by a test. Skill files refer to each other relative to their folder (`${CLAUDE_SKILL_DIR}`).

| Part | Runs where | Job |
|---|---|---|

Claude carries out every step; nothing else orchestrates. |
| `references/*.md` | Claude, on demand | `chats.md` (several chats: which chat a run is for, a pending chat's first refresh, `run-plan`), `groups.md` (Facebook groups), `first-run.md` (the first capture after setup), `updating-the-page.md`, `outbox.md` and `posting-with-helper.md` (posting queued replies and reactions), `open-message.md`, `helper.md` (the bridge, tabs, which Chrome, versions, warnings), `photos.md`, `day-summaries.md`, `reports.md`, `people.md`, `writing-the-build.md`, `reactions.md` (what reactions mean; the page carries a copy of its table, B67), `restoring-a-summary.md`, `database.md` (full reference), `scheduling.md`, `troubleshooting.md`. `SKILL.md` says when to read each (v1.9.0, BACKLOG C7); a test checks it names every one. |

There is no server. The artifact database (ArtifactData) is the only store, and both Claude and the page read and write it.

## One refresh, end to end

```
 Claude (cloud)                 Messenger tab (user's Chrome)            Catch-up page (artifact)
 ──────────────                 ─────────────────────────────            ────────────────────────
 get meta/chat ───────────────────────────────────────────────────────────▶ (db)
 set refresh/status running
 query outbox; post approved ─▶ replies first (jump{mid,reply} + insertText
   queued replies                + Enter, or post): before the scan
 mc-cmd full{stops,base,run} ─▶ mcScan: scroll up until a STOP id is seen
                                quote-match text replies, click photo replies
                                save window to sessionStorage.__mcsave
                                reload ─▶ resumePipe ─▶ mcVerify (ID-only pass,
                                          fast then slow) ─▶ mcCapture
                                page body replaced by COPY CAPTURE button
 poll mc_result (≤25 s calls) ◀─ {stage:'captured', run}
 click COPY CAPTURE ─────────▶ clipboard ─────────────────────────────────▶ paste anywhere
                                                                           importCore: checksum, numbering,
                                                                           overlap, fields; write chunks,
                                                                           read back, update meta/chat;
                                                                           storePhotos: one upload at a time,
                                                                           each indexed in photos/b<start>
 read refresh/lastImport ◀──────────────────────────────────────────────── refresh/lastImport (uploading,
 (wait while its beat moves: photos.md)                                    beat, then done | partial)
 get touched chunks + meta/chat, list threading + summary into RUN/
 write spec.json; catchup.py build WORK RUN spec.json  ->  RUN/out/manifest.json
 batch write per manifest: new blocks (unpinned), threading/current +
   summary/current (if_version), meta/chat, refresh/status; then cleanup
 handle outbox: settle sending rows from the saved chunks, post rows
   queued during the run, list the rest for a yes
```

"Send replies" (the `replies` skill) runs only the outbox part: query `outbox` (nothing queued: done, one read), check approval, take the run lock (`refresh/status`, `step:"replies"`; a live refresh lock: leave the tab alone), find the Messenger tab, `selfcheck`, post, release. It reads no new messages, so `sending` rows wait for the next refresh's settle check.

Why the clipboard: the page can't receive messages from the Messenger tab, can't read the clipboard itself, and can't fetch Facebook images. A user-style paste is the one channel that works (LEARNINGS.md › claude.ai artifacts).

## Several chats and groups (F1 stages A and B, v1.35.0–v1.40.0; F25 G1, v1.47.0–v1.48.0)
- **One page, several chats:** `meta/chat.chats` maps a fixed key to each chat or group (`name`, `tag`, `color`, `order`, `state`, `url`, `every`, `auto`, …). The first chat (`home`) keeps the page's own documents; an added chat `KEY` has `meta/chat-KEY`, `refresh/lastImport-KEY` and `KEY_chunks`, `KEY_threading`, `KEY_summary`, `KEY_photos`, `KEY_outbox`, … shaped as the first chat's. Shared: `refresh/status`, `refresh/skipped`, `refresh/schedule`, the import lease, `notes`, and `qa`/`views` (rows carry `chat`). The page's title is the picker; **All chats** has a Summary tab (a card per chat) and an Ask tab across chats (v1.55.0, F1 stage C part 1: lines and citations as `[key#n]`, shown as the chat's tag and number; the search tools take a chat key; the answer is saved in `qa` with `scope:"chats"`). All chats listens to each live chat's whole `summary` collection and counts Needs you with the same `needsIn` as the chat's own Summary (v1.56.1, B56). Until the reader picks a view (`S.viewPicked`), the page shows what a fresh load would, so it turns to All chats when a second chat becomes active. Settings ⚙ adds, tags, orders, pauses and removes chats without Claude.
- **A run over every chat:** `catchup.py run-plan` gives the order (the first chat, then chats the last run didn't reach, then by `order`, pending chats last). A scheduled run (`--scheduled`) stops starting chats after 15 minutes and skips chats not due by their How often (`every`, else `meta/chat.chatEvery`, measured from `refresh/skipped.last`); a run the user asks for refreshes all of them. One Messenger tab is navigated from chat to chat; every capture names its `thread`, and the page refuses one pasted into the wrong chat. Procedure: `references/chats.md`.
- **Facebook groups:** a group is a `chats` entry with `kind:"group"`. A refresh reads the notifications page once (`notifs`, never opening one), then each group's New posts and Recent activity feeds (`groupFeed`), each changed post's comments and, from helper 4.3, its own author and text (`groupPost`, which also opens posts stored without them), and pastes one `groupCapture`. The page stores `KEY_posts/p<postId>` and `KEY_comments/p<postId>`, numbers posts #pN once and comments #pN/cM in order, and shows a group's Summary (Needs you) and Posts tabs. Facebook is read-only for groups: the helper never clicks inside a post. Procedure: `references/groups.md`.

### Capture format (`kind: "mc-capture"`)
```
{kind, base, anchor, count, sha, msgs:[...], gifs:[i...], photos:[{i,k,aid?,type,b64}], phsha, phfail:[{i,k,aid?,e}], phskip:[{i,k,aid?}], run?, rx?:[{m,x?,xw?}], rxsum?}
sha   = SHA-256 hex of JSON.stringify(msgs)
phsha = SHA-256 hex of JSON.stringify(photos)
```
Helper 2.1 (R15, R16): `aid` is Messenger's attachment id from the photo's `messenger_media` link; `phfail` lists the photos it couldn't get (`e` `fetch`, or `unloaded` for an image that never loaded during the scan); `phskip` the ones the `skip` option (passed to `full` or `capture`) left out; `run` the run id `full` was given. Older helpers send none of these.
Helper 4.1 (B69): `rx` holds the reactions read again on stored messages, by Messenger id: the `rxBack` stored messages from the newest (to the catch-up marker, newest first, at most 400 and 60 s) and the `rxIds` messages found by id with who reacted (at most 20 and 45 s); an entry without `x` has no reactions now. `rxsum` is "N:hex": N the stored messages read, hex the first 16 hex of the SHA-256 of `JSON.stringify([the range's entries without xw, the by-id entries])`; a later scan that read at least N compares the newest N, so a recheck cut short by time doesn't capture on every quiet run. A mention the owner answered with their own yes or no reaction leaves Needs you on the page at once (`needsIn`: `xw` "You" or a reaction sent from the page; for a chat not on screen only the latter) and is marked `answered` by the build's `settle`. The page updates those stored messages' `x`/`xw` in place in their chunks, nothing else, and keeps `rxsum` in `meta/chat.rxSum`; a scan with nothing new whose digest equals the `rxSum` it was given (`rx.same`) captures nothing, and one that differs captures `rx` alone (`count` 0, `rxOnly` in the result, no reload or verify). Procedure: `references/reactions.md` › Late reactions.

**Which id, and how sure (R16, Nov 13):** each photo in a message sits in its own `a[href*="messenger_media"]` link whose `attachment_id=<digits>` names the photo. The helper has read that parameter (the first photo's, as the message's `p`) since v1.1, which was written against the real markup, and the page's photo marker (`[photo]`, "📷 photo") comes from it, so the link and the parameter are well established (fairly sure). Nothing in the repo records live markup, and this change wasn't checked on the live page. That every photo of a multi-photo message has its own link with its own id is modeled in the mock and expected from Messenger's grid, but hasn't been checked on the live page; if photos of one message share an id, the helper drops that message's ids (they match by position, as before 2.1) and warns. If ids turn out to change between visits, the page still finds a stored photo by a 12-hex content hash (`h`). The fbcdn image URL is not used: its query string (signature, expiry) changes between visits. Photos in `[aria-label^="Open photo"]` elements without a link get no id and match by `k`.
Each message may carry `fn` (helper 1.6+): the sender's full name, read from the alt text of their avatar (the ~28 px square image at the message's left edge). `f` stays the name Messenger prints (a nickname or the first name), which is what reply lines and the outbox match on. The page keeps `fn` (a string of 80 characters or fewer, never on "You") and folds it into `people/index`.

The page accepts only `mc-capture` (the old `cc-capture` kind was dropped on Nov 6) and two optional flags: `dry` (check everything, write nothing) and `lab` (store photos but don't link them).

### Copies of the helper (keep in sync)
The helper exists **twice**: the file itself, and its `jump()` body as a URL-encoded bookmarklet in the page's `#jump-bm` (`%` → `%25`). `tools/sync.py` (called `sync-helper.py` until the setup skill's copies joined it) regenerates the bookmarklet and the page's `HELPER_VERSION` from the file, and `npm test` fails (`--check`) when they drift. Until v1.8.0 the page also embedded an HTML-escaped copy of the whole userscript (`#jump-us`, "Copy userscript"). Now the page links to `releases/latest/download/helper.user.js`, which `tools/release.sh` attaches to every release, and the userscript's `@updateURL`/`@downloadURL` point there so it updates itself (BACKLOG F8). The version string appears four times in the helper (header, `__mcHelper`, `data-mc-helper`, `ping`). See BACKLOG C2.

## Page (`assets/page.html`)

- **Capabilities:** `db`, `assets` (photo uploads), `sample` (Ask Claude, Views, range summaries). Published by Claude with `capabilities: {"db":{}, "assets":{}, "sample":{}}`.
- **Config:** everything chat-specific comes from `meta/chat` via `applyCfg()` (line 500). `PAGE_VERSION` is at line 493.
- **Boot:** subscribes with `onSnapshot` to `meta/chat`, the `summary` collection, `chunks`, `qa`, `views`, `notes`, `outbox`, `refresh/status`, `refresh/schedule` (v1.24.0, F14), `rangeSummaries`, `daySummaries` (v1.32.0, F29: read only, the whole collection, into `S.daySums` by day, for the By day tab, Ask's and Views' day lines and the `day_summaries` tool, all of which read it synchronously; about 0.5 MB for 55 days of history. Windowed loading for very long histories is a backlog item, F33), `digests` (v1.25.0, F16: read only, into `S.digests` by day, the older per-day digests, for days without a summary), `reports` (F27: read only, into `S.reports` by day, for the By day tab; `watchReports`, whose failure leaves the summaries as they are), `people/index`, the `photos` collection (merged by `mergePhotos`) and the `threading` collection. With the `assets` capability it also lists assets once, read only, for the storage warning. Every chunk change rebuilds the full in-memory message list (`rebuild`). `mergeThreading` and `mergeSummary` turn each collection back into the single objects `S.threading` and `S.summary` that every view reads (old single documents are used as they are), so nothing else knows about blocks.
- **Keeping the reader's place (v1.19.0, BACKLOG B39):** a snapshot of new data redraws the Summary and Messages tabs from scratch inside `keepPlace`, which notes the message whose reply is being written (else the first row or card on screen) and its height on screen, redraws, and scrolls it back to the same height; open summary threads keep their inner scroll. Which Messages conversations the reader opened or closed is kept in `S.convOpen` (the summary's threads in `S.openThr`); only untouched ones follow the first-four default. An `outbox` change redraws nothing: `outboxChanged` refills the "reply queued" chips (`.pt[data-pt]`), the Summary's "Your replies" (`#ob-slot`) and closes the composer whose reply was queued.
- **Show older messages by day (v1.25.0, BACKLOG F15):** with Show older on and no filter, the Messages tab holds a span of whole days (`S.older`, by message number, so a redraw for new data keeps it; a new window starts it again): the window and the day before it, then one more day each time an end of the span (`.edge.more`, an IntersectionObserver with `root: document` and a 600 px margin, plus a button) comes near the screen. `olderStep` draws only that day: rows inserted in the timeline (`flatAdd`, which draws the rows at the boundary again so a run of bubbles across midnight is one block, as a full redraw draws it; "Not grouped yet" too); in the threaded layout `convStep` redraws the conversations with a message in that day (`convEl`; prepended ones go first, in order) and adds the rest to "Not grouped yet" (`restEl`). It keeps the reader's place with `placeOf(true)`, which works at the top of the page too. `goMsg` loads a day that isn't in the span (`olderInclude`): joined to it when next to it, else on its own. A filter searches everything stored, as before. While on, the toolbar sticks under the tabs (`--navh`, kept current by a ResizeObserver on the tabs).
- **Tabs:** for a chat, Summary · Ask Claude · Messages · By day · Views · Stats (under 560 px they share the bar's width, smaller, with "Ask" for "Ask Claude"); for a group, Summary · Posts. With several chats, All chats (`#v-all`) has its own Summary (a card per chat and group) and Ask tabs. Settings ⚙ (since F43 a list: For all chats, a row per chat and group, Change the order, Add a chat, Add a group, each opening its own screen; `S.setScreen` holds the one open), the photo storage box, and a fixed "Refreshing" section with helper setup and the manual Import box.
- **By day (v1.26.0, BACKLOG F24; day summaries v1.32.0, F29):** `renderDays` draws a card per day (`dayCard`), newest first, 30 days at a time (a "Show N more days" button adds the next 30 and moves focus to the first added card): the days with a summary (`daySumOf`: a `daySummaries` document with at least one bullet worth showing), a digest or a refresh run. Each card: the day's own date (`dayTitle`, "Sat, Nov 14", with the year when it isn't this year in `meta/chat.tz`) and its stored count (`dayCounts`). A day with a summary is a `.ds-day` card: a state line (`sumState`, a chip and when it was written by `runTime`: "In progress · updated 9:04 AM" with "so far" on the count; "Final · written Mon 1:10 AM" for `final`, or `full` with nothing after its rewrite once a later day is stored and no message of that day stored after it (`dayCounts().end`); "Day ended · updated …; rewritten as one piece at a refresh that brings new messages" for a day that ended before its final rewrite; "Day ended · rewritten/updated …" for a day that ended in the chat's zone while messages still carry its date). The minute tick redraws the tab, and the date in the chat's zone (`dsToday`) is in its memo key, so the state follows midnight without a reload, then each section's heading (`h4`) over its bullets, then "Still open" (`open`), every bullet as text followed by all its `refs` as citation links that call `goMsg`, as Ask's do. A day without a summary shows its older digest's bullets (at most 10 numbers each), as before. Both get **Copy for chat** (`copyRow`, `chatText`): plain text for the owner to paste into the chat, the day as a title (" (so far)" on the day in progress), each heading and its bullets as "• …", Still open, and no message numbers (`noRefs` also drops a bracketed "[#123]" written into a bullet); it uses the page's `copyText` (the clipboard, else `execCommand`), says "Copied." in a `role=status` line, and where both fail says so and shows the text selected in a read-only box to copy by hand. One line on top (`daysWhy`) says how summaries are kept, names the days after the newest summary still waiting ("… gets its summary at the next refresh") and what older days have (their digest, or no summary: ask Claude for summaries of past days). Drawn only while the tab is open (route, the snapshots, `rebuild` and the minute tick call it; it skips a redraw when its inputs are unchanged). It waits until both the `daySummaries` and `digests` snapshots have answered (so a day never shows its digest a moment before its summary); with no database (`S.daySumsIn = "nodb"`), it says they can't load in this view; when the summaries' listener fails, it shows the digests under a line saying so, or the error when both fail; with nothing stored, how summaries are written.
- **Each refresh's report on By day (BACKLOG F27):** `renderDays` also draws `S.reports` (`reports/d<YYYY-MM-DD>`, below). ### Importer (`importCore`, line 957)
The page's database has **no version-checked writes and no transactions** (runtime contract: last-writer-wins). So since v1.2.0 the importer protects itself in three ways:
- **Import lease:** before writing, it takes a 2-minute cooperative lease on `refresh/importLock` (`acquire`, holder = a per-tab id), so two open copies of the page can't import at once. Renewing it from the same tab is fine. If the runtime has no `acquire`, it imports without a lease (`lock:"unsupported"` in `refresh/lastImport`).
- **Fresh reads:** `meta/chat` and the newest chunk (`orderBy("start","desc").limit(1)`) are read from the store, not from the page's snapshots, which can lag or come from cache.
- **Repair:** if the newest chunk ends *after* `meta/chat.lastI`, an earlier import saved and read back its messages but stopped before updating `meta/chat`. The importer counts them in (`lastI`, `lastMid`, `lastT`, `anchorMids`, `ownLastI`) and prefixes its message with `REPAIRED: #a–#b (chunk …)`. If the chunk ends *before* `lastI`, it refuses and says what to set.

Checks, in order: JSON → `kind` → message checksum → photo checksum → lease → stored state (consecutive newest chunk, chunk end vs `lastI`) → consecutive numbers → no gap after `lastI` → overlapping messages match the stored ids → required fields (`f`, `m`, `t`, `d` as a date) → photo shape. A first import must start at `#0`. **Nothing, not even a repair, is written until every check passes.** It then:
1. writes the repair, if any
2. appends to the newest chunk, rolling to a new `cNNNN` at `chunkSize` (82)
3. **reads each chunk back and compares**
4. updates `meta/chat` (`lastI`, `lastMid`, `lastT`, `anchorMids`, `ownLastI`, `ownLastMid`)
5. hands the photos to `storePhotos` (v1.22.0, R2), still under the lease:
   - **placeholders:** a `null` slot in its `photos/b<start>` block for every photo not stored yet, plus new GIFs, and `meta/chat.photosOwed` `{n, fromI, toI, at}` for every owed slot in the chat; then `refresh/lastImport` `state:"uploading"`
   - **uploads, one at a time:** each races `uploadTimeoutMs` (90 s); uploads go oldest first. On success that one slot is written at once with `update({byK:{i:{k:"/_blob/<id>"}}})` (`set` only creates a missing block; `gifs` are merged with a fresh read, since `update` replaces arrays), so a tab closed mid-upload loses at most the photo in flight, and a slot another tab wrote meanwhile survives. Before each block write, and before its one retry, the lease is renewed; if another tab holds it (ours lapsed), nothing more is written, `refresh/lastImport` included (`stop:"lease"`)
   - **heartbeat:** a timer every `beatMs` (10 s) renews the lease for `leaseMs` (60 s) and, only while it's held, rewrites `refresh/lastImport` with a new `beat`, so a dead tab's lease lapses within a minute
   - **error codes** (`assets.d.ts`): only `store_unavailable` retries once after 2 s (`upstream_error` includes an unanswered call, so a retry could store a photo twice; it, `transform_error` and unknown codes stop with `unavailable`); `rate_limited` waits 30 s and retries once; `too_large`, `unsupported_type`, `invalid_request` give that photo up (`{e:code}`) and go on; `quota_or_state`, `upstream_auth`, a timeout, the lease, a refused block write and a view without assets stop with `state:"partial"` and a `stop` code
   - **slots (v1.24, R16):** each capture entry finds its slot with `resolveSlots`: by `aid` when a slot of its message records the same id (`aids` in the block), then for a photo by its content hash (`h`: its slot takes the new id, nothing is uploaded), otherwise by `k`; a slot recording another id is never taken (the photo gets the message's next free slot), and no two entries share one. A new photo records its `aid` with its placeholder; slots stored before helper 2.1 have none and keep matching by `k`, unchanged.
   - **fetch failures (v1.24, R15):** a `phfail` entry with no slot gets an owed `null` slot. Each owed slot of a message in the capture that the capture didn't bring (a `phfail`; with a 2.1 capture also one neither brought nor skipped) counts a try in `tries[i][k]` `{n, run}`, once per run (the capture's `run`, else `meta/chat.lastRefresh`); a `phskip` whose slot isn't stored or given up is owed again, listed in `skipOwed` and counted; at `fetchTries` (3) it becomes `{e:"no-fetch"}`. `refresh/lastImport.retry` lists the ones still being tried.
   - **end:** owed slots this capture doesn't hold become `{e:"gave-up"}` when more than `owedWindow` (300) messages behind `lastI`, or `{e:"no-backfill"}` on messages #0–#2 (a backfill scan needs 3 stored messages before it); a failed `photosOwed` write is ignored (the slots are on record); `photosOwed` is rewritten (or `null`); `assets.list()` gives `usage`, kept in `refresh/lastImport.usage` and `meta/chat.assetUsage` (written when it changed), with a warning at 80% of either limit
   - The timings live in `IMPORT_TUNE`; tests shorten them through `window.__mcImportTune`, which production never sets. `mergePhotos` merges the old `photos/index` (its `byK`, or `byI` by position) under the blocks; the page shows the merge (`S.photos`, `S.gifs`) and checks "already stored" by slot against it.

Every outcome goes to `refresh/lastImport`, with `state` `uploading` → `done` | `partial`, or `refused` / `failed`. A dry run reports what it would do, including "Would repair" and how many photos it would store, and writes nothing.

### Day packs (page 3.6, R13)
A page holds at most 5,000 asset files. With `meta/chat.photoPack.on` (the Photo storage box's switch, `#phstore`; only a view with `assets` can change it), a loop in each open tab with `db` and `assets` (`packTick`) packs one finished day at a time, oldest first:
- **Ready:** a day (the messages' `d`) that ended at or before the start of yesterday in `meta/chat.tz` (`tzDayBack(1)`), with no owed (`null`) slot on any of its messages and at least one plain `/_blob/<id>` slot (`packDays`).
- **When:** never while this tab imports, while `refresh/status` is `running` with `startedAt` in the last 20 minutes, or while `refresh/lastImport` is `uploading` with a `beat` in the last 10 minutes (an older one is a closed tab's). It then takes the import lease as holder `<tab>:pack` (so even this tab's own paste waits: "Another import is running … or the page is packing photos"), renews it every `beatMs` while it packs that day, and lets it lapse after (`ttlMs` 1000). Next step: 3 s after a day, 1 minute while something holds it up, 10 minutes with nothing to pack, and after an error 1 minute doubling to an hour.
- **Packing:** the day's slots are read fresh under the lease (`packFresh`); each original is fetched from `/_blob/<id>` with its bytes, content type and SHA-256 (a missing file is left as it is for this page view, `PK.skip`). Parts of about 12 MB of photos (`partBytes`; an upload takes at most 20 MiB) each become a full pack `{v:1, kind:"full", day, items:[{i,k,id,type,sha,b64}]}` and a preview pack `{v:1, kind:"preview", day, items:[{i,k,type,w,h,b64}]}` (canvas, at most 320 px on the long side, JPEG 0.72, never upscaled; a GIF's first frame), both uploaded as `application/json`, fetched back and checked item by item against the originals (`packCheck`). A mismatch deletes both new packs and keeps everything as it was.
- **Repoint, then delete:** per block, an `update` of only the slots that still hold their original: `byK[i][k] = "/_blob/<full>#<n>"`, `pv[i][k] = "/_blob/<preview>#<n>"`, then read back. Then `photos/packs` gets the entry (merged with a fresh read), and only the originals no re-read slot still uses are deleted, one at a time; a failed delete adds to `photos/packs.orphans`. Usage is read again and written to `meta/chat.assetUsage`.
- **Display:** `mergePhotos` returns `pvI` beside `byI`. `setPhoto` shows a plain slot by its URL as before, and a packed one as a `data:` URL from its pack (`loadPack`, `fetch` + JSON, cached per page view: 60 preview packs, 4 full packs): the preview inline, the full pack in the lightbox (the preview first while it loads). A pack that won't load leaves a "Photo couldn't load" tile. A `#n` value is never an image URL.
- Tests shorten the timings and sizes with `window.__mcPackTune` (section `packs`).

Summary: Heading: point [#12, #15]; point [#20] | Heading: … | Still open: … [#41]` (`daySumLine`) when the day has a summary, else into the older `… Digest: bullet [#12, #15] | …` (`digestLine`), each only when the line covers at least the document's `fromI..toI` (a scope starting or a cut falling mid-day keeps the title-only line); refs outside the day or not stored are dropped, a point left with none is skipped, and each point is one line (`oneLine`) of at most 400 characters (a digest bullet 240). A summary has no length limit, so its line takes whole points while they fit in `cap` bytes, its line break counted (`DAYSUM_LINE` 4,096 in Ask's and Views' older history; `TOOL_BYTES` less 512 in the `day_summaries` tool) and ends with "(+N more points)"; when not one point fits, the first one's text is cut to fit with its numbers kept, and with less than 24 bytes for it there's no line at all (the digest or the title-only line instead), so a line never passes its cap or claims a point it doesn't show. `dayScan` never lets a day go back: a message dated before the one before it (the browser's zone changed between captures) counts in that one's day, as `catchup._days` does, so each summary's day is one run. In `digest()`, title-only day lines stay the floor (every older message keeps a line); conversation lines leave room (`keep`) for exactly what a newest-first swap would add within `min(dgMax, the room over the floor)` (0 when nothing fits, so nothing is held back for nothing), `dgMax` being `DIGEST_SHARE` (0.5) of the summaries' share of the whole budget, fixed across `packHistory`'s rounds so they don't shrink it; then whole days before the cut swap in their short line, newest first, a day that doesn't fit skipped for the older ones after it, and then those their full line the same way (a day the cut splits keeps its title-only line). `dayLineOf(x, kind)` builds a day's lines when the swap first asks, kept with the scan's day object through packHistory's rounds (a `WeakMap`): `short` is never longer than the day's digest (its summary cut to the digest's bytes, else the digest; without a digest, the summary within `DAYSUM_SHORT` 1,024), so older history never covers fewer days than the digests did; `full` is the summary within `DAYSUM_LINE`. Each day's lines are built at most once per prompt, and full lines only for days that took a short one. `finish` records `P.digests` `{n, from, to}` (both kinds), which "What you have", `sentNote` ("Day summaries for N days (Oct 2–20).") and `sent.digests` (the field name older rows have) report. `dayLines(fromI, toI, cap, budget)` gives the same per-day lines, built a day at a time and stopping at `budget` bytes with `.next`, the day to continue from; the `day_summaries` tool calls it with one result's bytes (each day's line at most `DAYSUM_LINE` over several days, a single day up to the result) and returns `next`.
- `renderRangeSummary` / `writeRangeSummary`: when the catch-up window is set by date (`markerMode:"time"`) and starts before the summary's `fromI`, the page offers to have Claude (through the page's `sample`) summarize exactly that span, and saves it in `rangeSummaries/r<lo>_<hi>`. A summary has to read every message in its span. A span whose prompt is over the cap is read in parts (v1.25.0, F18): `rangeParts` splits it, oldest first, into runs whose prompts each fit (estimated per message, then checked against the real prompt), with no cap on how many; the box says how many parts and shows "Writing part n of N" with a Stop button. Each part is one `sample.json` call, normalized like a one-request reply (`rangeDoc`); a part that fails is tried once more (`prompt_too_large` splits what's left again at 80% of the bytes sent, which is that retry). Each part after the first also gets the earlier parts' open questions (`EARLIER OPEN QUESTIONS`, newest first within a room `splitRange` keeps aside, `earlierRoom`) and may list them in `answered`. `mergeRange` joins the parts: conversations by id in first-seen order (bullets concatenated, the newest outcome and tag, key numbers a rank at a time: each part's first pick, then each part's second, up to 4), mentions by their numbers, answered and open by the question (open dropped when a part answered it, or `repliedTo` finds a reply to it: an `r`, `rq`, `rg` or `i` link from someone other than the asker; `c` never counts, and a single-request summary uses the same rule), deals by conversation, kind and text with their numbers joined. From more than 4 parts, or a merge over 64 KB, `condenseRange` sends the merge back per conversation (`condensePrompt`, in batches that each fit one request) to be condensed to 3–6 bullets, an outcome, 2–4 key numbers and settled open/answered; a batch that fails twice keeps its merged conversations with trimmed bullets (`condensed` `"partly"` or `false`). Whatever comes out is trimmed until its JSON is under `SAVE_MAX` (256 KiB less 8 KiB). Model output is checked by `rangeClean` against `Map`s, never plain objects, so ids like `__proto__` are just unknown. Parts done live only in the tab (`RJ`); nothing is saved until every part is, so Stop, a failure (the box names the part's span) or a closed tab leaves nothing half-written, and "Write the rest" goes on from the first part not done. The merged document carries `parts`. `saveRange` never swallows a failed save: the summary stays on screen (`S.rangeUnsaved`) with "Written, but not saved (code)" and Save it again, or "too big to save".
- **Open-ended windows** (a date range with no end): `rangeKey` includes the newest message, so new messages change the key. A run in progress for another key is shown as "Writing a summary for #a–#b…" with Stop (never an idle button that does nothing), and `rangeSumFor` lets the window use the newest summary with the same start that ends earlier, saying "This summary covers #a–#b … It doesn't include the N newer messages after #b" with a "Write it again through #z" button. Keys stay exact spans (a start-only key would make an old summary look complete). Pressing it again after a stopped run of the same start goes on from that run's done parts.
- `fromI` is the first message the stored summary covers. Only pages from before v1.17.0 have it: the original page's summary started there (checked live Nov 7: `fromI` 1654, two saved spans), and by Nov 11 refresh sessions had moved it to 2797 while dropping older conversations to stay under the document cap (BACKLOG B43). A build keeps it and never moves it; nothing is dropped any more. `restore-summary` (below) moves it back to what a saved backup covers. New pages never show range summaries.
- The removed legacy code (C1, v1.7.3): the in-page Refresh trigger (`REFRESH_TASK`, `startRefresh`, `fire_trigger`), the summary v1 renderer, and `dayMap`/`meta.dates`. Every stored message carries `d`; checked live: 3,992 of 3,992.

## Build tool (`scripts/catchup.py`)

- `bootstrap WORK DBDIR`: loads all chunks, asserts numbering has no gaps and `meta.lastI` matches, merges the `threading` and `summary` collections (either layout, below), writes `WORK/all.json`, `WORK/base/{threading,summary}.json` (the merged state), `WORK/base/layout.json` (which documents exist, `activeFrom`), `WORK/state.json` (`base`, `stops`, `tz`). WORK's base is the last *built* message (threading's `to`). Messages stored after it (from a run that stopped after its import) are built by the next RUN, and `build` names the chunks to fetch if they're missing.
- `build WORK RUN SPEC`: loads new messages from `RUN/chunks` (must be exactly `base+1…`), applies the spec, picks default links, runs the asserts, splits the state into block documents and checks that they merge back into it and that none is over 240 KiB, writes the documents that changed to `RUN/out/{threading,summary}/` with `RUN/out/manifest.json` (and the merged state in `RUN/out/merged/`, for checking), copies the WORK it started from to `WORK/prev/`, then **advances WORK**. If step 5 listed the collections into RUN, it first checks that the stored `current` documents are still the ones WORK was built from. Building the same RUN again fails with "RUN already built into WORK … run: catchup.py restore WORK".
- `relink WORK RUN SPEC` (v1.12.0; RUN since v1.17.0): corrects links on messages an earlier build threaded, when there's nothing new to build. RUN holds a fresh `list threading`; SPEC holds `relink` `{i:[parent,type]|null}` (and, since v1.23.0, `move` with its `newconvs`, below; since v1.26.0, `bullets` and `dealEdit`, BACKLOG F21), and the same keys work inside a build spec. With `bullets` or `dealEdit` (alone or with a move) it reads the summary listing and writes both collections; they go through the build's own `_add_bullets`, `_deal_edits`, `_gained` (where `index` is refused) and `_not_dropped`, after the move, and `_check_summary` checks every ref, so a claim moved to its offer gets its bullet and `claims` entry in the same write. It writes `RUN/out/manifest.json` and the threading documents it names, then advances WORK's threading, keeping `WORK/prev`.
- `move` (v1.23.0, BACKLOG F20): a spec key `{"<i>": "<conv id>" | "new"}`, in a build spec (applied after `relink` and `newconvs`, before the new messages join) or through `relink WORK RUN SPEC`, which then also takes `newconvs`, reads the summary listing and writes both collections. `_move` takes the message and its Messenger replies (`r`, `rq`, `rg`, transitively) within its old conversation; guessed children (`i`, `c`) stay, re-pointed to the moved message's old parent (printed `LEFT`). It refuses unknown, unbuilt or already-placed messages, unknown targets, overlapping groups and a moved message whose own link doesn't end in the target. Summary items follow: an emptied conversation is dropped from threading and summary and everything keyed to it goes to the target (bullets merged by cited message, `_merge_by_ref`); otherwise items whose refs all moved go along and the rest lose the moved refs. `_check_summary` then checks every ref, as a build does.
- `rev` (v1.23.0): `_stamp` puts one token (hex seconds, then a random part) in `threading/current` and `summary/current` on every build, move and `restore-summary`; a relink with no move, `bullets` or `dealEdit` writes threading only, with `summaryRev` naming summary's. When the revs disagree (or only one document has one), bootstrap runs `_problems`, the build's `_check_summary` as messages that never raise: a pair that fits is accepted and the next write restamps both; one that doesn't is refused, and `--rollback` runs `_heal` (every summary item filed under the conversation threading has its messages in, a summary-only conversation dropped once empty, nothing else dropped) and marks WORK `repair`, so the next build, or `relink` with `{}`, writes both documents. `rev` is one of the `SEEN` fields `_fresh` compares. A relink that moved records the conversations it touched in `state.json` (`moved`), and the next build refuses a `dealEdit` `index` there.
- Claims (v1.23.0, BACKLOG F19): when RUN's `meta/chat.topic` or `threadName` matches `trade_topic` (a build with no `topic` prints a NOTE), `build` prints `REACT?` for each new message `claim_word` matches (a fixed list: "In", "in for N", "Dibs", "Mine", "I'll take it", "Sold", "PM'd", "DM sent", "Interested"; raffle spots excluded) with `react_candidates`: up to 3 posts by others (by `fn` when both have it) within 3 days (by `_min`): photos and refs of a deal with no `status` first, then `looks_like_offer` texts, newest first in each; raffle posts are marked. Claims and closes are never candidates. `close_word` ("Sold", "SPF", "pending") after the author's own post prints `CLOSE?`. Nothing is linked: Claude decides (`references/writing-the-build.md` › Claims). Deals carry optional `claims [{i, who, n}]` and `status`/`statusAt`, checked by `_check_deal` on every build.
- `restore WORK`: puts `WORK/prev/` back and removes it (one step of undo). Used after a refused DB write or to rebuild with a corrected spec. `bootstrap` clears any stale `WORK/prev/`.
- `restore-summary WORK RUN BACKUPDIR [DECISIONS] [--dry-run]` (v1.18.1, BACKLOG F10): joins the summary copy a pre-1.17 session saved in `backups/<name>-a`, `-b`, … (refusing missing or mismatched parts) and merges into WORK's summary what it lacks: conversations by id (old string synopses split into bullets as the page's `synItems` does), bullets in front of a continued conversation's own, answers, deals and mentions back in their places (`_anchor_merge`: each missing item goes after the backup item before it), and `fromI` back to the backup's. Open questions missing from both `open` and `answered` need DECISIONS (`open`, or an answer with refs); without it the command writes `RUN/out/restore-open.json` and nothing else. Items that don't fit threading are skipped and listed. The write goes through `layout_docs`, `_roundtrip`, `_plan` and `_write_out` like a build, sets `generatedAt` (so a stale WORK sees the change), and advances WORK (`restore` undoes it). Procedure: the refresh skill's `references/restoring-a-summary.md`.
- Day summaries (v1.32.0, BACKLOG F29): the spec key `daySummaries` `{"YYYY-MM-DD": {sections:[{h, bullets:[[text, [refs]], …]}], open:[[text, [refs]], …]}}` is checked by `_sum_entries` (a real date with stored messages, by `_days`: a message's `d`, the browser's date when the helper read it, carried forward when missing and never going back; not `final`; needed, by `_sum_needs`: a day that ended (a later day stored, or before today in `meta.tz` by `_today`, `NOW` in tests; with no tz database only a later day counts) and isn't `full` yet, or is `full` and gained messages since its rewrite (`fullToI`) now that a later day is stored (`final`); otherwise messages stored after its `toI` (`update`: the day in progress, or one that ended by the clock while the browser still dates messages with it) or none yet (`new`); so no message waits, and a day is rewritten twice at most however far `meta.tz` runs ahead of the browser; a day older than all of a query of the newest is refused, since it may exist unlisted (`_query_reach`: not when the listing is WHOLE, or fewer came back than the limit, `DAY_QUERY` 5 or the number in `.limit`; reports use the same rule); only `sections` and `open`; at least one section, each a one-line heading and at least one bullet; every bullet one line with no control characters or U+2028/U+2029, citing at least one stored message of that day; no word, bullet or ref caps) into a whole document `{day, fromI, toI, n, at, full, fullToI?, final, sections, open}` (`at`: `_now_iso`; a `final` kind writes `full` and `fullToI` (the day's last message) and `final` when a later day was stored; an update to an ended day keeps them). `_sum_spec` refuses the old `digests` key, adds the documents to `docs` and `listing` (`FIXED_IDS` makes `_plan` put them first and `_pins` pin those step 5's query held; `_too_big` says to write a day too big for a document in fewer bullets), and the build line says what it wrote and what's still due. With no summary yet, the newest finished day is due with the newest day unless RUN's `list digests` (listed on that first refresh) covers it (`_with_digest`). `_sum_finalize` marks final, unchanged but for `final`, a listed day rewritten after it ended before a later day was stored, with nothing stored for it since, once a later day is (a build and the backfill both do). `days WORK RUN [--backfill] [--max=N]` (`_sum_due`) lists what's due and writes each day's file to `RUN/out/days/<day>.txt`: a refresh, the days after the newest summary (none: the newest day) and any listed one that needs writing, oldest first, `DAY_DUE_MAX` 3, as `UPDATE` (the summary so far in the spec's form, `_sum_spec_form`, and only the messages after its `toI`), `NEW` or `FINAL` (all the day's messages); a backfill, finished days that need their final summary, newest first, up to `BACKFILL_DAYS` 5 and `BACKFILL_MSGS` 2,000. The backfill needs the whole collection: listed a page at a time (a list returns at most `PAGE` 1,000) with an empty `daySummaries/.all` (`WHOLE`) after the last page, which `_per_day(..., whole=True)` requires, since a day missing from a cut-off listing would look unsummarized and be written over unpinned. `day-summaries WORK RUN SPEC` writes only rewrites of days that ended (backing up what it replaces, and a hash (`_hash`, shared with `_bid`) of every listed day, in `RUN/out/backup/`; WORK doesn't move), and `check-day-summaries WORK RUN AFTER` checks a fresh whole listing (`_sum_later`: a written day may since have been updated by a refresh, reaching further with its rewrite no shorter, or marked final; anything else lost content or went back): every listed day still there and a final one unchanged, every written day as written (or made final since). Refreshes no longer write `digests/m<YYYY-MM>` (F16, v1.25.0–v1.31.1); the page still reads them. Procedures: the refresh skill's `references/day-summaries.md`.
- Reports (BACKLOG F27): the spec key `report` `[[text, [refs]], …]` (or `[]`) is this run's chat report, saved for By day. `_report_entries` checks it (at most `REPORT_BULLETS` 8; each one line of at most `REPORT_WORDS` 25 words and `REPORT_BYTES` 300 bytes, citing 1–`REPORT_REFS` 10 messages, all among the messages this build adds) and splits it by `_days` (the day summaries' day rule) into one run per day the build's messages cover, `{at, fromI, toI, n, bullets}` (`at`: `_now_iso`, `NOW` in tests), each bullet going to the days it cites with only that day's refs. `_report_docs` merges each into `reports/d<YYYY-MM-DD>` as RUN's query holds it (other fields kept), replacing any run whose `fromI..toI` overlaps (a rebuild after a refused or partly applied write), in `fromI` order, keeping the newest `REPORT_RUNS` 40 within `REPORT_DOC` 128 KiB and counting the rest in `dropped`. `_report_spec` requires `report` when RUN has a `reports/` folder (step 5's query: `order_by day desc`, limit `DAY_QUERY` 5; read by `_per_day`, as day summaries are), except on the first build (WORK's base -1), refuses a query of 5 reports all after the run's first day (it may miss that day), and adds the documents to `docs` and `listing`; `FIXED_IDS` makes `_plan` put them first with the day summaries and `_pins` pin those the query held. Without the folder and without `report`, a build saves none and says so. Procedure: the refresh skill's `references/reports.md`.
- Default link for each new message, in order: Messenger parent in window (`pi` → `r`, or `rq` if quote-matched in the browser) → Messenger parent by id from history (`pmid`) → quote match on stored history (`resolve`: same author, 300-message window, latest wins; the first 20 normalized chars as a prefix → `rq`; a quote under 12 chars must equal the whole text, and a long quote found only inside a text is accepted, both printed as `CHECK quote match (…)`; empty or "Photo"-type quote → author's latest media → `rg` + CHECK) → previous member of its conversation if ≤3 h older (`c` same author, else `i`, printed as GUESS) → none (ROOT).
- Asserts: WORK isn't behind the database; conv ids new; deal claims point at stored messages by the name stored on them, once each, with a positive count; every new message joined exactly once; every message from the lowest member up is in exactly one conversation; links point backward; bullets ≤15 words; outcomes ≤12; bullet/key/open/answered refs belong to their conversation; deals name a real conversation; `meta/chat` was updated by the import; every output document is at most 240 KiB ("… would be N bytes, over the 245760-byte limit … Never drop or shorten …", nothing written).
- Timestamps (`builtAt`, `generatedAt`) come from the system clock in `meta.tz` (falls back to America/Los_Angeles).

### Threading and summary layout (v1.17.0, BACKLOG B43)
A database document holds at most 256 KiB, and threading (about 25 bytes a message) and summary (about 50) grow with the chat, so each is a collection. Full field list: the refresh skill's `references/database.md`.
- `threading/current` `{layout:2, block:1000, blocks:[ids], to, note, builtAt, convs:[conversations with no messages yet]}`; `threading/b<start>-<hash>` `{start, convs:[{id,title}] starting in the block, members:{conv:[i…]}, links:{i:[p,t]}}`.
- `summary/current` `{layout:2, block, blocks, activeFrom, version, toI, generatedAt, fromI?, mentionsNote?, convs, open, answered, mentions, deals}` holds what's at or after `activeFrom` (the start of the block before the newest, moved up a block while `current` is over 96 KiB; it never moves back). `summary/b<start>-<hash>` holds older items by the block of their messages: `convs` (by last message), `open` (ask), `answered` (newest of ask and refs), `mentions` (newest ref), `deals` (first ref), and `syn:{conv:[bullets]}`, a conversation's bullets by the block they cite.
- Each list's key is a running maximum from its oldest end, so every document holds one unbroken run of each list, and merging (`catchup.merge_threading`/`merge_summary`, the page's `mergeThreading`/`mergeSummary`) gives back the exact single documents, order included. `catchup.py` asserts that round trip on every build.
- Ids carry a hash of the content. A changed block is a new document; `current` switches to it in the same batch, and the blocks the replaced `current` named that the new one doesn't are deleted afterwards (`cleanup`). An interrupted run leaves `current` naming intact blocks, and a retry finds the blocks it already created. Blocks no `current` names are never deleted (they may be all that's left of a build another writer's `current` replaced); bootstrap reports them.
- Build and relink read step 5's listing of the whole collections in RUN and refuse a partial one. Bootstrap stops when threading's `to` and summary's `toI` differ (a last batch that half landed); `--rollback` drops threading's extra messages from WORK so the next build redoes them. The page shows a notice when a block `current` names stays missing.
- The old layout (one `current` each, no `layout`) is read by the page and by bootstrap; the first build converts it. Setup still seeds the old empty documents.
- Measured: the largest document stays at most 85 KB from 6,400 to 50,000 messages (EXPERIMENTS.md §13).

### Message fields
`i` number from 0 · `t` "Fri 8:41 AM" · `d` "YYYY-MM-DD" · `f` sender ("You" = owner) · `b` text · `m` Messenger id · `r` replied-to name · `q` quoted text (≤160) · `pi` parent number in the store · `pq` 1 when the parent was quote-matched · `pmid` / `pl` parent id and label when outside the capture window · `perr` why a reply has no parent (`notfound`, `nobtn`, `nofocus`, `wrongfocus`, and from helper 2.0 `noreplyline`: the "X replied to Y" line couldn't be read) · `p` attachment id of a photo · `a` link-preview / attachment title (≤220) · `l` outside links · `x` reactions (count and emoji) · `xw` who reacted, `[[name or "You", emoji], ...]` (helper 4.0, B67). The page adds `ts` in memory.

### Link types
`r` Messenger's own reply link · `rq` reply matched by quote · `rg` photo reply, best match · `i` answers (Claude's judgment) · `c` same person continuing · `null` in a spec = deliberately no link.
