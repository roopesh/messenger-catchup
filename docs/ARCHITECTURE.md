# Architecture

How the pieces fit together, as of Nov 11, 2026 (v1.17.0: threading and summary stored as block documents). Line numbers date from Nov 6 (Phase 8) and have drifted; search by name.

Related docs: [STATUS.md](STATUS.md) (start here) · [BACKLOG.md](BACKLOG.md) · [DECISIONS.md](DECISIONS.md) · [LEARNINGS.md](LEARNINGS.md)

## The four parts

They ship as a plugin (v1.15.0): the repo is a marketplace (`.claude-plugin/marketplace.json`, name `rando-tools`) listing the plugin in `plugin/` (`plugin/.claude-plugin/plugin.json`, name `messenger-catchup`, version = `VERSION`). It has two skills (v1.16.0): `setup` (`plugin/skills/setup/`, once per chat: requirements, the page, the questions, the schedule) and `refresh` (`plugin/skills/refresh/`, every run). The paths below are inside the refresh skill. Setup hands the first capture to refresh, which reads `references/first-run.md` when `meta/chat.lastI` is -1. A skill can only count on its own folder, so setup carries copies of the page, `references/database.md` and `references/scheduling.md`, generated by `tools/sync.py` and checked by a test. Skill files refer to each other relative to their folder (`${CLAUDE_SKILL_DIR}`).

| Part | Runs where | Job |
|---|---|---|
| `SKILL.md` | Claude (cloud) | The procedure for every run: hard rules, core database fields, the helper bridge, the refresh, spec writing, method ideas, and when to read `references/scheduling.md` (the scheduling tools, stale follow-ups, arming the next run). Claude carries out every step; nothing else orchestrates. |
| `references/*.md` | Claude, on demand | `first-run.md` (the first capture after setup), `updating-the-page.md`, `outbox.md` (posting queued replies), `open-message.md`, `database.md` (full reference, `qa`/`notes`), `troubleshooting.md`. `SKILL.md` says when to read each (v1.9.0, BACKLOG C7). |
| `assets/helper.user.js` | The user's Messenger tab (userscript, or injected by Claude) | Scroll back and read messages (scan), confirm them by ID (verify), build the capture JSON (capture), jump links. |
| `assets/page.html` | claude.ai artifact, in the user's browser | The catch-up page. Also the **importer**: checks a pasted capture and writes it to the database. |
| `scripts/catchup.py` | Claude's code sandbox | Builds threading and summary from Claude's spec, asserts the rules, and writes the documents that changed plus a manifest of what to write (block layout, v1.17.0). |

There is no server. The artifact database (ArtifactData) is the only store, and both Claude and the page read and write it.

## One refresh, end to end

```

                                          fast then slow) ─▶ mcCapture
                                page body replaced by COPY CAPTURE button

                                                                           importCore: checksum, numbering,
                                                                           overlap, fields; write chunks,
                                                                           read back, update meta/chat;
                                                                           storePhotos: one upload at a time,
                                                                           each indexed in photos/b<start>
 read refresh/lastImport ◀──────────────────────────────────────────────── refresh/lastImport (uploading,
 (wait while its beat moves: photos.md)                                    beat, then done | partial)
 get touched chunks + meta/chat, list threading + summary into RUN/
 write spec.json; catchup.py build WORK RUN spec.json  ->  RUN/out/manifest.json

   summary/current (if_version), meta/chat, refresh/status; then cleanup

```

Why the clipboard: the page can't receive messages from the Messenger tab, can't read the clipboard itself, and can't fetch Facebook images. A user-style paste is the one channel that works (LEARNINGS.md › claude.ai artifacts).

### Capture format (`kind: "mc-capture"`)
```
{kind, base, anchor, count, sha, msgs:[...], gifs:[i...], photos:[{i,k,aid?,type,b64}], phsha, phfail:[{i,k,aid?,e}], phskip:[{i,k,aid?}], run?}
sha   = SHA-256 hex of JSON.stringify(msgs)
phsha = SHA-256 hex of JSON.stringify(photos)
```
Helper 2.1 (R15, R16): `aid` is Messenger's attachment id from the photo's `messenger_media` link; `phfail` lists the photos it couldn't get (`e` `fetch`, or `unloaded` for an image that never loaded during the scan); `phskip` the ones the `skip` option (passed to `full` or `capture`) left out; `run` the run id `full` was given. Older helpers send none of these.

**Which id, and how sure (R16, Nov 13):** each photo in a message sits in its own `a[href*="messenger_media"]` link whose `attachment_id=<digits>` names the photo. The helper has read that parameter (the first photo's, as the message's `p`) since v1.1, which was written against the real markup, and the page's photo marker (`[photo]`, "📷 photo") comes from it, so the link and the parameter are well established (fairly sure). Nothing in the repo records live markup, and this change wasn't checked on the live page. That every photo of a multi-photo message has its own link with its own id is modeled in the mock and expected from Messenger's grid, but hasn't been checked on the live page; if photos of one message share an id, the helper drops that message's ids (they match by position, as before 2.1) and warns. If ids turn out to change between visits, the page still finds a stored photo by a 12-hex content hash (`h`). The fbcdn image URL is not used: its query string (signature, expiry) changes between visits. Photos in `[aria-label^="Open photo"]` elements without a link get no id and match by `k`.
Each message may carry `fn` (helper 1.6+): the sender's full name, read from the alt text of their avatar (the ~28 px square image at the message's left edge). `f` stays the name Messenger prints (a nickname or the first name), which is what reply lines and the outbox match on. The page keeps `fn` (a string of 80 characters or fewer, never on "You") and folds it into `people/index`.

The page accepts only `mc-capture` (the old `cc-capture` kind was dropped on Nov 6) and two optional flags: `dry` (check everything, write nothing) and `lab` (store photos but don't link them).

### Copies of the helper (keep in sync)
The helper exists **twice**: the file itself, and its `jump()` body as a URL-encoded bookmarklet in the page's `#jump-bm` (`%` → `%25`). `tools/sync-helper.py` regenerates the bookmarklet from the file, and `npm test` fails (`--check`) when they drift. Until v1.8.0 the page also embedded an HTML-escaped copy of the whole userscript (`#jump-us`, "Copy userscript"). Now the page links to `releases/latest/download/helper.user.js`, which `tools/release.sh` attaches to every release, and the userscript's `@updateURL`/`@downloadURL` point there so it updates itself (BACKLOG F8). The version string appears four times in the helper (header, `__mcHelper`, `data-mc-helper`, `ping`). See BACKLOG C2.

## Page (`assets/page.html`)

- **Capabilities:** `db`, `assets` (photo uploads), `sample` (Ask Claude, Views, range summaries). Published by Claude with `capabilities: {"db":{}, "assets":{}, "sample":{}}`.
- **Config:** everything chat-specific comes from `meta/chat` via `applyCfg()` (line 500). `PAGE_VERSION` is at line 493.
- **Boot:** subscribes with `onSnapshot` to `meta/chat`, the `summary` collection, `chunks`, `qa`, `views`, `notes`, `outbox`, `refresh/status`, `refresh/schedule` (v1.24.0, F14), `rangeSummaries`, `digests` (v1.25.0, F16: read only, into `S.digests` by day), `people/index`, the `photos` collection (merged by `mergePhotos`) and the `threading` collection. With the `assets` capability it also lists assets once, read only, for the storage warning. Every chunk change rebuilds the full in-memory message list (`rebuild`). `mergeThreading` and `mergeSummary` turn each collection back into the single objects `S.threading` and `S.summary` that every view reads (old single documents are used as they are), so nothing else knows about blocks.
- **Keeping the reader's place (v1.19.0, BACKLOG B39):** a snapshot of new data redraws the Summary and Messages tabs from scratch inside `keepPlace`, which notes the message whose reply is being written (else the first row or card on screen) and its height on screen, redraws, and scrolls it back to the same height; open summary threads keep their inner scroll. Which Messages conversations the reader opened or closed is kept in `S.convOpen` (the summary's threads in `S.openThr`); only untouched ones follow the first-four default. An `outbox` change redraws nothing: `outboxChanged` refills the "reply queued" chips (`.pt[data-pt]`), the Summary's "Your replies" (`#ob-slot`) and closes the composer whose reply was queued.
- **Show older messages by day (v1.25.0, BACKLOG F15):** with Show older on and no filter, the Messages tab holds a span of whole days (`S.older`, by message number, so a redraw for new data keeps it; a new window starts it again): the window and the day before it, then one more day each time an end of the span (`.edge.more`, an IntersectionObserver with `root: document` and a 600 px margin, plus a button) comes near the screen. `olderStep` draws only that day: rows inserted in the timeline (`flatAdd`, which draws the rows at the boundary again so a run of bubbles across midnight is one block, as a full redraw draws it; "Not grouped yet" too); in the threaded layout `convStep` redraws the conversations with a message in that day (`convEl`; prepended ones go first, in order) and adds the rest to "Not grouped yet" (`restEl`). It keeps the reader's place with `placeOf(true)`, which works at the top of the page too. `goMsg` loads a day that isn't in the span (`olderInclude`): joined to it when next to it, else on its own. A filter searches everything stored, as before. While on, the toolbar sticks under the tabs (`--navh`, kept current by a ResizeObserver on the tabs).
- **Tabs:** Summary · Ask Claude · Messages · Views, plus a fixed "Refreshing" section with helper setup and the manual Import box.

### Catch-up window (`winRange`, line 546)
`meta/chat.markerMode` picks the start point:
- `caught`: after `caughtUpI` ("Mark caught up" button sets it to the newest message).
- `own`: after the user's last message (`ownLastI`, kept current by the importer).
- `time`: `markerFrom` / optional `markerTo` (local `YYYY-MM-DDTHH:MM`), compared against each message's `ts` built from `d` + `t`.
Everything (summary cards, counts, mentions, open questions) filters to the window. The date inputs never rebuild while focused and save 1.5 s after the last keystroke, on Enter, or on blur (EXPERIMENTS.md §6).

### Summary (v3 cards, `renderSummaryV2`, line 757)
"Your replies" (outbox) → "Needs you" (mentions) → filter chips (All / Open / Deals / Answered) → one card per conversation (`convCard`, line 724) with open/deal/answered call-outs (a deal's `claims` as a "Claimed:" line, `claimsLine`, and its `status` as a "Sold"/"Pending" label, `statusTag`), outcome, bullets that open the thread at their messages, and a lazily built thread → collapsed "Links shared".

### Threading display (`convTree`, line 703)
One tree for cards and the Messages tab. `r`/`rq`/`rg`/`i` links nest under their parent; `c` (same person continuing) sits right after the earlier message at the same level; depth is capped at 3. **A link only nests when its parent is in the same conversation**; otherwise the message shows as a root.
- **Blocks (v1.19.0, B42):** a run of `c` messages from the same sender, each at most 5 minutes after the last (`RUN_MS`, `sameRun`), renders as one block (`blockOf`, `.grp`), as Messenger shows a person's bubbles: one header, each bubble's text or photos beneath it. Each bubble is still a `.msg` row with its own id (`#m<i>`, or `data-i` in summary threads) and quiet number, so search, jumps and `#n` links find it; like every message row, its actions (`.acts`) float in on hover, show on keyboard focus, and appear under it on a tap where there's no hover. Replies to any bubble nest under the block. The timeline and "Not grouped yet" group the same way with `flatRows` (next in the list and a `c` link; without threading, the same sender and not a Messenger reply). The Messages filter takes `#123` for message 123.
- **Context line (v1.19.0, B40):** when a conversation's first shown message links to a message that isn't shown in it (threading put a reply in a new conversation, or the conversation started before the window), `ctxLine` shows that message first as a quoted block: which conversation it's in and "Show #n →" (a jump), then the message rendered by `msgRow` with `{ctx: true}` (no row id, no Reply here): sender, time, full text, photos. `runAround` adds the rest of its run of bubbles, so a text and its photo show together. A parent that isn't stored shows the reply's `r` and `q` and says so. In the Messages tab's threaded layout and on Summary cards.

### Importer (`importCore`, line 957)
The page's database has **no version-checked writes and no transactions** (runtime contract: last-writer-wins). So since v1.2.0 the importer protects itself in three ways:
- **Import lease:** before writing, it takes a 2-minute cooperative lease on `refresh/importLock` (`acquire`, holder = a per-tab id), so two open copies of the page can't import at once. Renewing it from the same tab is fine. If the runtime has no `acquire`, it imports without a lease (`lock:"unsupported"` in `refresh/lastImport`).
- **Fresh reads:** `meta/chat` and the newest chunk (`orderBy("start","desc").limit(1)`) are read from the store, not from the page's snapshots, which can lag or come from cache.
- **Repair:** if the newest chunk ends *after* `meta/chat.lastI`, an earlier import saved and read back its messages but stopped before updating `meta/chat`. The importer counts them in (`lastI`, `lastMid`, `lastT`, `anchorMids`, `ownLastI`) and prefixes its message with `REPAIRED: #a–#b (chunk …)`. If the chunk ends *before* `lastI`, it refuses and says what to set.

Checks, in order: JSON → `kind` → message checksum → photo checksum → lease → stored state (consecutive newest chunk, chunk end vs `lastI`) → consecutive numbers → no gap after `lastI` → overlapping messages match the stored ids → required fields (`f`, `m`, `t`, `d` as a date) → photo shape. A first import must start at `#0`. **Nothing, not even a repair, is written until every check passes.** It then:
1. writes the repair, if any
2. appends to the newest chunk, rolling to a new `cNNNN` at `chunkSize` (82)
3. **reads each chunk back and compares**
4. updates `meta/chat` (`lastI`, `lastMid`, `lastT`, `anchorMids`, `ownLastI`, `ownLastMid`)
5. hands the photos to `storePhotos` (v1.22.0, R2), still under the lease:
   - **placeholders:** a `null` slot in its `photos/b<start>` block for every photo not stored yet, plus new GIFs, and `meta/chat.photosOwed` `{n, fromI, toI, at}` for every owed slot in the chat; then `refresh/lastImport` `state:"uploading"`
   - **uploads, one at a time:** each races `uploadTimeoutMs` (90 s); uploads go oldest first. On success that one slot is written at once with `update({byK:{i:{k:"/_blob/<id>"}}})` (`set` only creates a missing block; `gifs` are merged with a fresh read, since `update` replaces arrays), so a tab closed mid-upload loses at most the photo in flight, and a slot another tab wrote meanwhile survives. Before each block write, and before its one retry, the lease is renewed; if another tab holds it (ours lapsed), nothing more is written, `refresh/lastImport` included (`stop:"lease"`)
   - **heartbeat:** a timer every `beatMs` (10 s) renews the lease for `leaseMs` (60 s) and, only while it's held, rewrites `refresh/lastImport` with a new `beat`, so a dead tab's lease lapses within a minute
   - **error codes** (`assets.d.ts`): only `store_unavailable` retries once after 2 s (`upstream_error` includes an unanswered call, so a retry could store a photo twice; it, `transform_error` and unknown codes stop with `unavailable`); `rate_limited` waits 30 s and retries once; `too_large`, `unsupported_type`, `invalid_request` give that photo up (`{e:code}`) and go on; `quota_or_state`, `upstream_auth`, a timeout, the lease, a refused block write and a view without assets stop with `state:"partial"` and a `stop` code
   - **slots (v1.24, R16):** each capture entry finds its slot with `resolveSlots`: by `aid` when a slot of its message records the same id (`aids` in the block), then for a photo by its content hash (`h`: its slot takes the new id, nothing is uploaded), otherwise by `k`; a slot recording another id is never taken (the photo gets the message's next free slot), and no two entries share one. A new photo records its `aid` with its placeholder; slots stored before helper 2.1 have none and keep matching by `k`, unchanged.
   - **fetch failures (v1.24, R15):** a `phfail` entry with no slot gets an owed `null` slot. Each owed slot of a message in the capture that the capture didn't bring (a `phfail`; with a 2.1 capture also one neither brought nor skipped) counts a try in `tries[i][k]` `{n, run}`, once per run (the capture's `run`, else `meta/chat.lastRefresh`); a `phskip` whose slot isn't stored or given up is owed again, listed in `skipOwed` and counted; at `fetchTries` (3) it becomes `{e:"no-fetch"}`. `refresh/lastImport.retry` lists the ones still being tried.
   - **end:** owed slots this capture doesn't hold become `{e:"gave-up"}` when more than `owedWindow` (300) messages behind `lastI`, or `{e:"no-backfill"}` on messages #0–#2 (a backfill scan needs 3 stored messages before it); a failed `photosOwed` write is ignored (the slots are on record); `photosOwed` is rewritten (or `null`); `assets.list()` gives `usage`, kept in `refresh/lastImport.usage` and `meta/chat.assetUsage` (written when it changed), with a warning at 80% of either limit
   - The timings live in `IMPORT_TUNE`; tests shorten them through `window.__mcImportTune`, which production never sets. `mergePhotos` merges the old `photos/index` (its `byK`, or `byI` by position) under the blocks; the page shows the merge (`S.photos`, `S.gifs`) and checks "already stored" by slot against it.

Every outcome goes to `refresh/lastImport`, with `state` `uploading` → `done` | `partial`, or `refused` / `failed`. A dry run reports what it would do, including "Would repair" and how many photos it would store, and writes nothing.

### Outbox
"Reply here" writes `outbox/r<timestamp>` `{i, mid, to, snip, text, state:"queued", queuedAt}`; Cancel sets `state:"cancelled"`. Claude moves rows to `sending` → `sent` (`sentAt`, `sentMid`), `failed` (`error`) or `unconfirmed` (sent but never found in the chat; never reposted). Failed and unconfirmed rows have a Dismiss button (`state:"dismissed"`), and they stay listed until resolved.

### Prompt budget (Ask, Views; v1.22.0, BACKLOG F6 and R4)
`sample()` refuses a prompt over `sample.limits().maxPromptBytes`: every turn's content together, in UTF-8 bytes. The page reads the cap at load (`sampleCap`; 262,144 when `limits` is missing, rejects, hangs past a second, or answers 8 KiB or less or not a number; never more than 262,144) and keeps a 4 KiB margin (`MARGIN`).
- **`packHistory`** (scope, the window's newest `fHi`, the fixed bytes, the summaries' share): word for word from `fHi` back, one run `#rawLo..#rawHi`, until the budget less the summaries' share (35% with "include older", 20% otherwise) is used; what the summaries don't need goes back to messages. Messages after the window (a date range with an end, older ones included) are one line per day, within 10% of the budget (`AFTER_SHARE`; past it the newest days go and the prompt says so). `lineFor` runs only for lines that go in, plus one; the pass is linear and only runs on Ask or Build view.
- **The digest** of what's older than `#rawLo`: level 1, one line per conversation (newest last message first; text from `S.summary`'s outcome or last bullet or plain-text synopsis, else a range summary with the same id, else "no summary; N messages from …"; range-summary conversations threading lacks are placed by the numbers they cite; runs of ungrouped messages get "N messages, not grouped"), added while they plus day lines for what they leave out fit. Lines describe only messages older than `#rawLo` (ranges and Key numbers stop there). Units come newest message first, so every conversation not taken ends at or before the first one that didn't fit: level 2, one line per day, runs up to that one's newest message, so every older message is in a day line or its own conversation's line (overlap is fine). Level 2: one line per day (`[#a–#b, Oct 3] N messages. Busiest: …`) back to the first stored message. If even the day lines don't fit, the oldest go and the prompt says "Nothing before #N is included." Lines print oldest first, each starting with the stored messages it covers, so a citation of any number jumps to a real message.
- **Ask** (`askPrompt`): "What you have" says which numbers are word for word and which are summaries; the rules ask Claude to say when a point comes from a summary. Chat turns: the last 9 at most, oldest pairs dropped while they're over a quarter of the cap; a question over half the cap isn't sent. **Views** (`viewPrompt`) use the same builder with the window as scope. `fitPrompt` measures the final prompt and drops the oldest lines if an estimate was off. A prompt whose fixed text can't fit, or that leaves no room for any message, is refused on the page (`too_long`); a view request over half the cap is never sent, as for questions. On `prompt_too_large` (nothing was sent), `sendFitted` retries once at 80% of the bytes it just sent. One question at a time: a second click on Ask while one is on its way does nothing.
- **Look deeper** (v1.25.0, F17): under an Ask answer whose prompt had summary lines (`P.before` or `P.after`), a button runs two plain requests (no `tools`). Step 1 (`deeperPickPrompt`, `sample.json`) sends the question, the first answer and those lines (newest first while they fit) and asks for `{"stretches":[{from,to,focus,why}]}`; `deeperStretches` validates it (anything else is "couldn't be read", nothing more sent), clamps each to stored messages, cuts out what was read word for word and what an earlier stretch covers, and keeps at most 3. Step 2 (`deeperPrompt`) sends them word for word with the question and the first answer: each stretch takes what's left of the budget, whole or the part around its `focus` (from its start without one) that fits, and the note says when one was cut or left out. Both steps go through `sendFitted`, so `prompt_too_large` retries once at 80%. Stop cancels either step. The answer is saved in `qa/*` with `scope:"deeper"` and `sent: {from, to, stretches, wanted}`. It reads only `P.before`/`P.after` (`{a, b, text, bytes}` lines, digest day lines included), so step 1 sees whatever Ask sent, digests where they went in, without depending on how packHistory builds them.
- **The note** under an answer or built view says what was read ("Read #a–#b word for word. Older than #a: summaries only.", or "Your window has N messages: read the newest M …"), and `qa/*` and `views/*` save it as `sent: {from, to, sumFrom, afterFrom}`.

### Range summaries (pages carried over from the original chat)
- **Per-day digests** (v1.25.0, BACKLOG F16): `digestText(x)` turns a day line into `[#a–#b, Oct 3] N messages. Digest: bullet [#12, #15] | …` when `S.digests` has that day and the line covers at least the digest's `fromI..toI` (a scope starting or a cut falling mid-day keeps the title-only line); refs outside the day or not stored are dropped, a bullet left with none is skipped, and each bullet is one line (control characters and runs of spaces become one space) of at most 240 characters. `dayScan` never lets a day go back: a message dated before the one before it (the browser's zone changed between captures) counts in that one's day, as `catchup._days` does, so each digest's day is one run. In `digest()`, title-only day lines stay the floor (every older message keeps a line); conversation lines leave room (`keep`) for exactly what a newest-first swap would add within `min(dgMax, the room over the floor)` (0 when no digest fits, so nothing is held back for nothing), `dgMax` being `DIGEST_SHARE` (0.5) of the summaries' share of the whole budget, fixed across `packHistory`'s rounds so they don't shrink it; then whole days before the cut swap in their digest, newest first, while it fits (a day the cut splits keeps its title-only line). `finish` records `P.digests` `{n, from, to}`, which "What you have", `sentNote` ("Day digests for N days (Oct 2–20).") and `sent.digests` report. `dayLines(fromI, toI)` gives the same per-day lines to other prompts.
- `renderRangeSummary` / `writeRangeSummary`: when the catch-up window is set by date (`markerMode:"time"`) and starts before the summary's `fromI`, the page offers to have Claude (through the page's `sample`) summarize exactly that span, and saves it in `rangeSummaries/r<lo>_<hi>`. A summary has to read every message in its span. A span whose prompt is over the cap is read in parts (v1.25.0, F18): `rangeParts` splits it, oldest first, into runs whose prompts each fit (estimated per message, then checked against the real prompt), with no cap on how many; the box says how many parts and shows "Writing part n of N" with a Stop button. Each part is one `sample.json` call, normalized like a one-request reply (`rangeDoc`); a part that fails is tried once more (`prompt_too_large` splits what's left again at 80% of the bytes sent, which is that retry). `mergeRange` joins the parts: conversations by id in first-seen order (bullets concatenated, the newest outcome and tag, key numbers deduplicated, first two and last two past 4), mentions by their numbers, answered and open by the question (open dropped when answered or linked to), deals by conversation, kind and text with their numbers joined. Parts done live only in the tab (`RJ`); nothing is saved until every part is, so Stop, a failure (the box names the part's span) or a closed tab leaves nothing half-written, and "Write the rest" goes on from the first part not done. The merged document carries `parts`.
- `fromI` is the first message the stored summary covers. Only pages from before v1.17.0 have it: the original page's summary started there (checked live Nov 7: `fromI` 1654, two saved spans), and by Nov 11 refresh sessions had moved it to 2797 while dropping older conversations to stay under the document cap (BACKLOG B43). A build keeps it and never moves it; nothing is dropped any more. `restore-summary` (below) moves it back to what a saved backup covers. New pages never show range summaries.
- The removed legacy code (C1, v1.7.3): the in-page Refresh trigger (`REFRESH_TASK`, `startRefresh`, `fire_trigger`), the summary v1 renderer, and `dayMap`/`meta.dates`. Every stored message carries `d`; checked live: 3,992 of 3,992.

## Build tool (`scripts/catchup.py`)

- `bootstrap WORK DBDIR`: loads all chunks, asserts numbering has no gaps and `meta.lastI` matches, merges the `threading` and `summary` collections (either layout, below), writes `WORK/all.json`, `WORK/base/{threading,summary}.json` (the merged state), `WORK/base/layout.json` (which documents exist, `activeFrom`), `WORK/state.json` (`base`, `stops`, `tz`). WORK's base is the last *built* message (threading's `to`). Messages stored after it (from a run that stopped after its import) are built by the next RUN, and `build` names the chunks to fetch if they're missing.
- `build WORK RUN SPEC`: loads new messages from `RUN/chunks` (must be exactly `base+1…`), applies the spec, picks default links, runs the asserts, splits the state into block documents and checks that they merge back into it and that none is over 240 KiB, writes the documents that changed to `RUN/out/{threading,summary}/` with `RUN/out/manifest.json` (and the merged state in `RUN/out/merged/`, for checking), copies the WORK it started from to `WORK/prev/`, then **advances WORK**. If step 5 listed the collections into RUN, it first checks that the stored `current` documents are still the ones WORK was built from. Building the same RUN again fails with "RUN already built into WORK … run: catchup.py restore WORK".
- `relink WORK RUN SPEC` (v1.12.0; RUN since v1.17.0): corrects links on messages an earlier build threaded, when there's nothing new to build. RUN holds a fresh `list threading`; SPEC holds `relink` `{i:[parent,type]|null}` (and, since v1.23.0, `move` with its `newconvs`, below), and the same keys work inside a build spec. It writes `RUN/out/manifest.json` and the threading documents it names, then advances WORK's threading, keeping `WORK/prev`.
- `move` (v1.23.0, BACKLOG F20): a spec key `{"<i>": "<conv id>" | "new"}`, in a build spec (applied after `relink` and `newconvs`, before the new messages join) or through `relink WORK RUN SPEC`, which then also takes `newconvs`, reads the summary listing and writes both collections. `_move` takes the message and its Messenger replies (`r`, `rq`, `rg`, transitively) within its old conversation; guessed children (`i`, `c`) stay, re-pointed to the moved message's old parent (printed `LEFT`). It refuses unknown, unbuilt or already-placed messages, unknown targets, overlapping groups and a moved message whose own link doesn't end in the target. Summary items follow: an emptied conversation is dropped from threading and summary and everything keyed to it goes to the target (bullets merged by cited message, `_merge_by_ref`); otherwise items whose refs all moved go along and the rest lose the moved refs. `_check_summary` then checks every ref, as a build does.
- `rev` (v1.23.0): `_stamp` puts one token (hex seconds, then a random part) in `threading/current` and `summary/current` on every build, move and `restore-summary`; a relink with no move writes threading only, with `summaryRev` naming summary's. When the revs disagree (or only one document has one), bootstrap runs `_problems`, the build's `_check_summary` as messages that never raise: a pair that fits is accepted and the next write restamps both; one that doesn't is refused, and `--rollback` runs `_heal` (every summary item filed under the conversation threading has its messages in, a summary-only conversation dropped once empty, nothing else dropped) and marks WORK `repair`, so the next build, or `relink` with `{}`, writes both documents. `rev` is one of the `SEEN` fields `_fresh` compares. A relink that moved records the conversations it touched in `state.json` (`moved`), and the next build refuses a `dealEdit` `index` there.
- Claims (v1.23.0, BACKLOG F19): when RUN's `meta/chat.topic` or `threadName` matches `trade_topic` (a build with no `topic` prints a NOTE), `build` prints `REACT?` for each new message `claim_word` matches (a fixed list: "In", "in for N", "Dibs", "Mine", "I'll take it", "Sold", "PM'd", "DM sent", "Interested"; raffle spots excluded) with `react_candidates`: up to 3 posts by others (by `fn` when both have it) within 3 days (by `_min`): photos and refs of a deal with no `status` first, then `looks_like_offer` texts, newest first in each; raffle posts are marked. Claims and closes are never candidates. `close_word` ("Sold", "SPF", "pending") after the author's own post prints `CLOSE?`. Nothing is linked: Claude decides (`references/writing-the-build.md` › Claims). Deals carry optional `claims [{i, who, n}]` and `status`/`statusAt`, checked by `_check_deal` on every build.
- `restore WORK`: puts `WORK/prev/` back and removes it (one step of undo). Used after a refused DB write or to rebuild with a corrected spec. `bootstrap` clears any stale `WORK/prev/`.
- `restore-summary WORK RUN BACKUPDIR [DECISIONS] [--dry-run]` (v1.18.1, BACKLOG F10): joins the summary copy a pre-1.17 session saved in `backups/<name>-a`, `-b`, … (refusing missing or mismatched parts) and merges into WORK's summary what it lacks: conversations by id (old string synopses split into bullets as the page's `synItems` does), bullets in front of a continued conversation's own, answers, deals and mentions back in their places (`_anchor_merge`: each missing item goes after the backup item before it), and `fromI` back to the backup's. Open questions missing from both `open` and `answered` need DECISIONS (`open`, or an answer with refs); without it the command writes `RUN/out/restore-open.json` and nothing else. Items that don't fit threading are skipped and listed. The write goes through `layout_docs`, `_roundtrip`, `_plan` and `_write_out` like a build, sets `generatedAt` (so a stale WORK sees the change), and advances WORK (`restore` undoes it). Procedure: the refresh skill's `references/restoring-a-summary.md`.
- Digests (v1.25.0, BACKLOG F16): the spec key `digests` `{"YYYY-MM-DD": [[text, [refs]], …]}` is checked by `_digest_entries` (a real date with stored messages, by `_days`: a message's `d`, the browser's date when the helper read it, carried forward when missing and never going back; the day finished, i.e. a later day stored or before today in `meta.tz` (`_today`, `NOW` in tests; with no tz database `_today` is None and only a later day counts); no digest yet, or one that isn't `final` (written before a later day was stored) whose day gained messages, now that a later day is: so a day is digested twice at most, however far `meta.tz` runs ahead of the browser; 1–8 bullets, ≤15 words and ≤240 bytes, one line with no control characters or U+2028/U+2029, each citing 1–10 messages of that day) and written by `_digest_docs` into `digests/m<YYYY-MM>` (the listed month plus the new days, each with `final`); `_plan` puts digest documents first and `_pins` pins those the listing holds. `days`, `digests` and a build with `digests` require RUN's `digests/` folder (step 5's listing, or an empty folder for an empty collection), as `_listing` does for threading. `days WORK RUN [--backfill] [--max=N]` (`_due`) lists the days due and writes their messages to `RUN/out/days/<day>.txt`: a refresh, finished days after the newest digest (none: the newest finished day) and any that gained messages, oldest first, `DUE_MAX` 3; a backfill, every finished day that needs one, newest first, up to `BACKFILL_DAYS` 10 and `BACKFILL_MSGS` 2,000. `digests WORK RUN SPEC` writes only digests (backing up the listed months and the days they held in `RUN/out/backup/` first; WORK doesn't move), and `check-digests WORK RUN AFTER` compares a fresh listing with the backup and what was written. A build prints how many digests it wrote and which days are still due. Procedures: the refresh skill's `references/digests.md`.
- Default link for each new message, in order: Messenger parent in window (`pi` → `r`, or `rq` if quote-matched in the browser) → Messenger parent by id from history (`pmid`) → quote match on stored history (`resolve`: same author, 300-message window, latest wins; the first 20 normalized chars as a prefix → `rq`; a quote under 12 chars must equal the whole text, and a long quote found only inside a text is accepted, both printed as `CHECK quote match (…)`; empty or "Photo"-type quote → author's latest media → `rg` + CHECK) → previous member of its conversation if ≤3 h older (`c` same author, else `i`, printed as GUESS) → none (ROOT).
- Asserts: WORK isn't behind the database; conv ids new; deal claims point at stored messages by the name stored on them, once each, with a positive count; every new message joined exactly once; every message from the lowest member up is in exactly one conversation; links point backward; bullets ≤15 words; outcomes ≤12; bullet/key/open/answered refs belong to their conversation; deals name a real conversation; `meta/chat` was updated by the import; every output document is at most 240 KiB ("… would be N bytes, over the 245760-byte limit … Never drop or shorten …", nothing written).
- Timestamps (`builtAt`, `generatedAt`) come from the system clock in `meta.tz` (falls back to America/Los_Angeles).

### Threading and summary layout (v1.17.0, BACKLOG B43)
A database document holds at most 256 KiB, and threading (about 25 bytes a message) and summary (about 50) grow with the chat, so each is a collection. Full field list: the refresh skill's `references/database.md`.
- `threading/current` `{layout:2, block:1000, blocks:[ids], to, note, builtAt, convs:[conversations with no messages yet]}`; `threading/b<start>-<hash>` `{start, convs:[{id,title}] starting in the block, members:{conv:[i…]}, links:{i:[p,t]}}`.
- `summary/current` `{layout:2, block, blocks, activeFrom, version, toI, generatedAt, fromI?, mentionsNote?, convs, open, answered, mentions, deals}` holds what's at or after `activeFrom` (the start of the block before the newest, moved up a block while `current` is over 96 KiB; it never moves back). `summary/b<start>-<hash>` holds older items by the block of their messages: `convs` (by last message), `open` (ask), `answered` (newest of ask and refs), `mentions` (newest ref), `deals` (first ref), and `syn:{conv:[bullets]}`, a conversation's bullets by the block they cite.
- Each list's key is a running maximum from its oldest end, so every document holds one unbroken run of each list, and merging (`catchup.merge_threading`/`merge_summary`, the page's `mergeThreading`/`mergeSummary`) gives back the exact single documents, order included. `catchup.py` asserts that round trip on every build.
- Ids carry a hash of the content. A changed block is a new document; `current` switches to it in the same batch, and the blocks the replaced `current` named that the new one doesn't are deleted afterwards (`cleanup`). An interrupted run leaves `current` naming intact blocks, and a retry finds the blocks it already created. Blocks no `current` names are never deleted (they may be all that's left of a build another writer's `current` replaced); bootstrap reports them.
- Build and relink read step 5's listing of the whole collections in RUN and refuse a partial one. Bootstrap stops when threading's `to` and summary's `toI` differ (a last batch that half landed); `--rollback` drops threading's extra messages from WORK so the next build redoes them. The page shows a notice when a block `current` names stays missing.
- The old layout (one `current` each, no `layout`) is read by the page and by bootstrap; the first build converts it. Setup still seeds the old empty documents.
- Measured: the largest document stays at most 85 KB from 6,400 to 50,000 messages (EXPERIMENTS.md §13).

### Message fields
`i` number from 0 · `t` "Fri 8:41 AM" · `d` "YYYY-MM-DD" · `f` sender ("You" = owner) · `b` text · `m` Messenger id · `r` replied-to name · `q` quoted text (≤160) · `pi` parent number in the store · `pq` 1 when the parent was quote-matched · `pmid` / `pl` parent id and label when outside the capture window · `perr` why a reply has no parent (`notfound`, `nobtn`, `nofocus`, `wrongfocus`, and from helper 2.0 `noreplyline`: the "X replied to Y" line couldn't be read) · `p` attachment id of a photo · `a` link-preview / attachment title (≤220) · `l` outside links · `x` reactions. The page adds `ts` in memory.

### Link types
`r` Messenger's own reply link · `rq` reply matched by quote · `rg` photo reply, best match · `i` answers (Claude's judgment) · `c` same person continuing · `null` in a spec = deliberately no link.
