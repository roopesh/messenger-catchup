# Status and handoff

**Read this first** when picking the project up. Last updated Nov 27, 2026 (US Pacific). What changed in each release is in [CHANGELOG.md](../CHANGELOG.md); what's open is in [BACKLOG.md](BACKLOG.md). Every PR updates the release line below (a test checks it names `VERSION`), and a release that changes what users see or how the project works updates the rest of this file too.

## Where things stand
- **Release: v1.66.0** (page `PAGE_VERSION` 8.3, helper 4.4). It's a plugin, `messenger-catchup`, installed from this repo as a marketplace (`rando-tools`); installs update when the plugin's version changes. Every release is a git tag plus a GitHub release with the plugin ZIP and `helper.user.js` attached; installed helpers (1.5+) update themselves from the latest release.
- **Four skills:** `setup` (once per page: requirements, the page, the questions, the schedule; also changes the schedule and schedules reply checks), `refresh` (every run; posts approved replies first, then refreshes every chat and group), `replies` ("send replies": posts what's queued and stops) and `reply-check` ("check replies": one read of `meta/chat` plus one outbox query per active chat, handing a waiting reply to `replies`; schedulable hourly, the shortest interval the schedulers allow). A skill can only count on its own folder, so setup and replies carry copies that `npm run sync` makes.

- **Replies and reactions:** the page queues replies (with "@" mentions and attached photos) and reactions in `outbox/*` (per chat, `KEY_outbox`). They post at the start of every refresh, through "send replies", or after a scheduled reply check. Approval is the page's `outboxAuto` or a chat's own `auto`, else a yes in chat. Helper posting (`helperPost`, opt-in) posts in one call and is the only way to post real mentions and photos, and a group's comments (G3a). Your replies lists only replies still waiting on something.
- **Scheduling (R6):** a chain of one-time follow-ups, else a recurring task kept only if it's tied to this computer, else manual. Each prompt carries an `armId`, so only one chain runs, and a chain run arms the next as it starts (`references/scheduling.md`; the owner's calls are in DECISIONS.md › Scheduling).
- **Update notices:** each refresh records in `meta/chat.versions` what its skill ships and the helper each Chrome ran, keyed by Claude in Chrome's device id with the Chrome's name alongside (B55: the names can swap when the extension reconnects). The page compares them with its own versions and names the Chrome whose helper is behind.
- **Tabs during a run:** one Messenger tab in Claude's tab group serves every chat. The page tab opens only to paste and closes at the end of the run, unless photos are still storing (B61).

### Workflow and enforcement
- **Workflow:** every change goes branch → PR → version bump → CI → squash-merge → `main`'s CI → `tools/release.sh`. Nothing is committed to `main` directly. The steps are in [CLAUDE.md](../CLAUDE.md) and below.
- **Enforcement:** GitHub branch protection on `main`: changes only through a PR, `test` and `version-bump` must pass, the branch must be up to date, linear history, no force-push or deletion, admins included. CI's `pr-only` job flags any commit on `main` that didn't come from a merged PR, and a local `pre-push` hook (`npm run setup`) blocks direct pushes. `tools/release.sh` refuses to tag unless `main`'s CI for that commit passed on its first attempt (`tools/ci-green.sh`). Every PR's body carries a `Docs:` line (the docs it updated, or `none needed — <reason>`), and the `docs` workflow (`tools/docs_check.py`) fails without it or when a named doc wasn't changed.

### In use
- The owner's page runs the released plugin from the marketplace on a schedule. It picks up a new page or skill at its next refresh after a merge: check `meta/chat.pageVersion` and `meta/chat.versions` there (read-only) before saying a release works for them.
- **Repo:** public, `github.com/roopesh/messenger-catchup`, branch `main`. **Never commit real names, nicknames, chat names or message text from anyone's chat**: tests and docs use the mock cast (Ana, Ben, Cy, Dee, You).

## Test suites
`npm test` checks formatting, runs the Python suites beside the sim, then the page tests: about 2 minutes on the owner's Mac. CI runs the same on every PR; its runner has 4 CPUs, so it runs fewer cases at a time. The sim runs its cases `SIM_JOBS` at a time (default three times the CPU count) and the page its sections `PAGE_JOBS` at a time (default the CPU count); each case's or section's lines print together under a `--- name (seconds)` header, and `=1` runs them one by one.

## Working on it

### Run the tests
From the repo root:
```sh
npm ci             # once per clone or worktree: Playwright, Prettier, Lexical (pinned in package-lock.json)
npm run setup      # once: Playwright's Chromium, the pre-push hook, .venv with pinned Ruff
npm run fmt        # before committing: Prettier + Ruff, then npm run sync
npm test           # format check, Python suites and sim side by side, page (about 2 minutes)
```
Exit code 0 means everything passed. The page suite reads `tests/out/sim_caps.json`, which the sim writes, so run `test:sim` before `test:page` when you run them separately. `tests/out/` is gitignored. In a new git worktree, see DEVELOPMENT.md › Working in a git worktree.

### Try `catchup.py` locally
```sh
python3 plugin/skills/refresh/scripts/catchup.py bootstrap WORK DBDIR      # DBDIR: chunks/*.json, threading/*.json, summary/*.json, meta/chat.json
python3 plugin/skills/refresh/scripts/catchup.py build WORK RUNDIR spec.json  # writes RUNDIR/out/manifest.json and the documents it names
```
`build` advances WORK in place; `restore WORK` undoes one build. Add `--chat=KEY` for an added chat. `tests/test_catchup.py` has an `Env` class that builds these folders, and `Live` (with `FakeDB`) runs whole refreshes against a database with the real limits, so it's the quickest way to try a spec. `tests/synth.py` makes large synthetic histories.

### Change the helper
1. Edit `plugin/skills/refresh/assets/helper.user.js`.
2. `npm run fmt` formats and then runs `npm run sync`, which regenerates the page's bookmarklet and `HELPER_VERSION` from the helper, and the setup and replies skills' copies. `npm test` fails if you forget.
3. To release a new helper version, bump all four version strings (header `@version`, `window.__mcHelper`, `data-mc-helper`, `ping`; a test checks they agree; minor stays one digit, 3.9 → 4.0). The sync then changes the page, so its `PAGE_VERSION` rises too. Installed copies update themselves from the release, which `tools/release.sh` attaches the userscript to.
4. `npm test`.

### Change the page
1. Edit `plugin/skills/refresh/assets/page.html`. It has no `<!doctype>…<body>` skeleton, because the Artifact tool adds that at publish time (the page test adds the same one). Bump `PAGE_VERSION` whenever the page changes; a test enforces it.
2. Claude republishes a user's page when `meta/chat.pageVersion` is older (SKILL.md, before each run). The database survives a republish.
3. `npm test`. The page suite loads the real file.
4. Before calling it done, check it on claude.ai on a scratch artifact of your own (CLAUDE.md › Page changes).

### Every change: PR, version, merge, release
1. Branch from an up-to-date `main`.
2. Make the change. Bump `VERSION`, `package.json` (`npm version X.Y.Z --no-git-tag-version` updates the lockfile too) and `plugin/.claude-plugin/plugin.json`, add a `CHANGELOG.md` entry, and update the release line at the top of this file. MAJOR / MINOR / PATCH rules are in [CLAUDE.md](../CLAUDE.md). `npm test` fails if these disagree.
3. `npm test`, then `gh pr create`. Fill in the template's checklist (`.github/pull_request_template.md`).
4. `gh pr checks --watch` until CI (`test`, `version-bump`) is green, then `gh pr merge --squash --delete-branch` and `git switch main && git pull`. Watch `main`'s own CI run too (`gh run list --branch main --limit 1`, `gh run watch <id>`).
5. `tools/release.sh`: checks `main`'s CI passed on its first attempt, tags `vX.Y.Z` on the merge commit, builds the plugin ZIP from the tag (the `plugin/` folder), checks its version, and publishes the GitHub release with the changelog entry and the userscript.
6. Marketplace installs update from `main` once the plugin's version changes (step 2). ZIP uploads (Customize › Plugins › Upload plugin) don't update themselves.

## Gotchas worth knowing before you touch anything
- The reader is tied to Facebook's English labels and markup. When a scan suddenly fails, check those first (LEARNINGS.md › Messenger DOM; the helper's warnings name what it couldn't find).
- Claude in Chrome tool calls die at about 45 s. Anything long is started and then polled in calls of 25 s or less.
- The capture step **replaces the Messenger tab's page** with the COPY CAPTURE button. Navigate back to the chat afterwards.
- Timestamps in status docs must come from the tool clock, not memory (LEARNINGS.md › Tooling).
- Pin every Claude-side write to an existing document with `if_version`. New block documents have no version; step 7 writes exactly what `RUN/out/manifest.json` lists.
- A database document holds at most 256 KiB, and a batch at most 50 writes and 1 MiB (LEARNINGS.md › Page database). Never store something that grows with the chat in one document.
